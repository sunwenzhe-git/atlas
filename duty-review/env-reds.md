# 已知环境红登记簿（duty-review/env-reds.md）

> **只记「这台机器 / 这套环境」的既有失败**：在干净基线副本上同样复现、与当前改动无关的红。
> 用途 = 回答「全量回归又红了，这次是不是我改坏的」，并让同一个现场只被诊断一次。
>
> 账本分工（一个失败只占一个落点）：

| 落点 | 装什么 | 生命周期 |
|---|---|---|
| `duty-review/env-reds.md`（本文件） | 本机 / 环境态既有红 | 转绿或环境恢复即删行 |
| `duty-review/bugs.md` | 产品行为缺陷（按环分类） | 完全确认修复后删除 |
| `duty-review/QUEUE.md` | 需要人拍板 / 值得盯的少数条目 | 结案入归档区 |
| `DESIGN.md` §12 / `shared/gates.md` | 正式决策 / 门 | 长期 |

- 本文件不随包分发（`package.json` 的 `files` 不含 `duty-review/`）；零脚本、零依赖，离线可读。
- **无机器门**：判据靠人 / agent 按本文执行，如实登记为纪律面，不假装是门。

## 1. 收入 / 不收

**收入**（三条同时成立才可登记）：

1. **可复现**：给出命令、失败节点与失败指纹（停在第几步 / 哪条断言 / 退出形态）；
2. **非本批引入**：给出干净基线的对照命令与结果——同一环境下冒同样的红；
3. **环境前提可陈述**：写清依赖哪种机器状态（外部服务可达性、运行时 / 浏览器、端口、系统负载等）。根因未定位不拦登记，但前提至少要写到「这台机器 + 当前运行时组合」这一层。

**不收**：

- 第一次出现、复跑就绿的红 ⇒ 按 `bugs.md` E2E 段「首跑不坐实、复跑复现才改判缺陷」处理，不进本表；
- 代码里已有显式 `skipif` / `skip` 的项（理由在测试里，重复登记 = 双账）；
- 已修复 / 环境已恢复的项（删行，历史归 git）；
- 产品行为缺陷 ⇒ 归 `bugs.md`。

## 2. 命中判定（三条全中才算「既有环境红」）

1. 同一测试节点（或同一命令段的同一批节点）；
2. 失败指纹一致（同一停顿步 / 同一错误形态，**不是同一文件就算**）；
3. 环境前提仍成立（例：前提是「外部服务不可达」，服务恢复后本条即失效）。

**任一不中 ⇒ 按新红排查，不得用本表消红。** 同一节点换了指纹 = 新缺陷，最容易被「反正一直红」吞掉；本表最大的风险就是这条遮蔽，故写成硬判据。

## 3. 生命周期

- **每次再见到同红**：只更新「最近复验」日期，其余字段不动；
- **转绿 / 环境恢复**：删行即出表，理由写进提交信息；本文件是当前态，不积墓碑；
- **复验期限**：每条必填，默认登记日 + 30 天。到期未复验 ⇒ 每日巡检在 `QUEUE.md` 观察室挂一行，按三选一收口：复验仍红 ⇒ 写明为何继续接受并延期；转绿 ⇒ 删行；前提变了但红还在 ⇒ 按新红处理；
- **换机后不复现**：按「转绿」处理（前提已不存在），删行。
