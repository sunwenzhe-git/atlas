# atlas apply — 需求式跨环增量

> 本环为 atlas 独立 skill `atlas-apply` 的执行契约，位于 `.atlas/apply/reference.md`。
> 执行前先读共享契约：`.atlas/shared/global-rules.md`、`stack-profile.md`、`single-source.md`、`layout.md`、`knowledge.md`。
> 本环**跨四环**，是 atlas 里唯一的编排件：它只做「按需求跨环增量」与「按序全量」两件事，环内逻辑一律引用各环自己的契约，不在此复制正文。

## 0. 一句话

把「一条需求」灌进项目级应然资产：读 Trellis 需求卡 → 推导影响面 → 按 `prd → e2e` 增量更新 → 跑机器校验 → 出报告；更新完成后，Trellis 才去实现。四种模式：`apply <需求ID>`（需求式增量）、`apply adopt`（既有项目**一次性接入开户**）、`all`（按序跑三环全量；E1，原型环已移除 `3508 §92`）与 **`backfill`（回流原语：把已裁决的回填条目分组攒批灌入上游，§5.2）**。

- **单向衔接**：需求 → 项目级资产（应然，实现之前）→ 实现（Trellis Execute）。apply 不写业务代码。
- 本环**不重实现**各环逻辑：各环正文归各自契约（`.atlas/rings/*/reference.md`）。
- 本环**不产** PRD 正文、用例、结构事实、业务代码；越界即失败。

## 1. 模式与触发

| 模式 | 语义 | 触发 |
|---|---|---|
| `apply <需求ID>` | **需求式跨环增量**：只改动本次需求影响的 PRD 章节 / E2E 分片与索引页面表；更新完才进实现 | 由 Trellis Plan 阶段的 `#### 1.6 项目级资产更新` 步骤 `[required · once]` 调用（见 §7） |
| `all` | **按序全量**：`structure → prd → e2e` 逐一走各环自己的全量流程，建立 / 刷新整套项目级资产 | `origin: greenfield` 的新项目接入、或需重建基线时手动触发 |
| **`adopt`** | **一次性接入开户**（2026-09-26 补；2026-09-27 补域级最小集）：既有项目接入时**只跟 `structure` 全量**，再按「最小必填集」把 `product/prd/` 开起来——全局 `prd.md` 落 `范围形态：变更` + `覆盖度` + `基线`，**并为域清单里每个域开一份「开户最小集」域级 PRD**（`rings/prd/reference.md` §4）；**不预设** E2E——它由后续每条需求按下面的门增量长出（E1：原型环已移除） | `origin: adopt` 的项目**第一次**接入时手动触发；此后每条需求走 `apply <需求ID>` |
| **`backfill`** | **回流原语**（2026-09-28 补，`3509 §99`；详见 §5.2）：把**已裁决**的回填条目按「上游目标 + 改动类型」分组、攒批灌入上游应然资产与配置，跨环同步（含下游用例改挂），各环门照跑 | 收口时扫描本任务产生的回填 → 入队；**攒批**后手动触发（每批 ≤ 10 条） |

- **需求 ID = Trellis task id**（`task.json` 的 `id`，即 task 目录名）；**需求卡 = 该 task 的 `.trellis/tasks/<需求ID>/prd.md`**（`single-source.md` §1）。不另建 inbox。
- **第 4 种形态**（**应然资产自身修订，无需求卡**）**不属本环**：它不挂 Trellis 需求、不经 `apply`，直接按 `prd → e2e` 逐环跑受影响集合。判据与四条粒度纪律见 **§3.2**。
- 四环与 `apply` 是**不同模式**，不合并：四环是「按阶段全量」，apply 是「按需求跨环增量」（D27/F10）。
- **`adopt` 与 `all` 的区别**：两者都不叫「增量」，但 `adopt` **不做全量重述**——既有项目的 UI / 流程 / 数据已经在代码里，全量重写 PRD 与用例既不可能也没价值。`adopt` 只做一件事：**把基线登记下来**（结构事实），并把项目级 PRD 开到「能接第一条需求」的最小形态。**域级同样只开最小集**：止于「概述 + 功能清单 + 规则 + AC」，六件套（状态机 / 字段校验 / 六类文案 / 异常处理）留到该域**真的有需求**时补——开户时写它只能从代码反推产品意图（实测成本见 `rings/prd/reference.md` §4 的「开户最小集」）。
- **形态与门的分工**：`origin`（项目级，一次）定**默认**；三问门（需求级，每条）定**这一条**要拉起哪些环。**形态不剥夺能力**：`origin` 只定默认，不阻止某条需求按三问门把应然 UI 面落细（E1：原型环已移除，应然 UI 的 testid 应然随用例分片产出，见 `rings/e2e/reference.md` §6.2）。

## 3. 参与环与顺序

`apply <需求ID>` 按 **`prd → e2e`** 顺序处理；`structure` **不参与**该增量（它是 apply 的**输入**，不是产出——实然事实在实现后由 `after_finish` hook 与 `trellis-update-spec` 维护）。

**唯一例外（有界）**：若本次 PRD 定稿**改变了域清单**（合并 / 拆分 / 改名），在 `prd` 之后追加一次 structure **re-key**（按 `rings/structure/reference.md` §2.2：按最终域重排 `.trellis/spec/structure/{current,legacy}/<domain>/` 目录并回写 `_meta.json.domains` / `tour.md`，**不重读代码**）。除该情形外，apply 不写结构事实。

**各环是否参与的判据**（`rings/e2e/reference.md` §6.2；D51/E14）——不以需求大小为准，以「是否改变应然 UI」为准：

| 需求性质 | prd | e2e |
|---|---|---|
| 改变应然 UI（新增 / 改元素、交互、文案） | 是 | 是（增量，仅受影响页；testid 应然落分片） |
| 不改 UI、只改业务规则 / 数据 | 是 | 是（复用既有 testid） |
| 纯后端 / 接口、用户不可见 | 视是否改产品定义 | 不产出（不属 E2E） |

### 3.1 门：这条需求要拉起哪些环（三问；**判定与依据必须写进报告**，2026-09-26 补）

1. **这次是否改动既有能力**（而不是纯新增）？——判据见 §4.1。**是** ⇒ 必须有项目级 PRD 基线（`prd` 参与；只写受影响面，见最小必填集）。
2. **这次是否需要人来确认应然 UI / 流程**？**是** ⇒ `prd` 六件套（用户流程 / 状态机 / 字段 / 文案 / 异常）落细 **+ 派生「用户旅程走查」并取得用户确认（`rings/prd/reference.md` §4·八；确认前不得进 `e2e` 环）**；应然 UI 的 testid 应然随用例分片产出（E1：原型环已移除）。
3. **这次是否需要可重复的验收**（超出 lint / test / typecheck 的能力）？**是** ⇒ E2E 环参与。

- **三问全否 ⇒ 只走 `structure` + Trellis**：atlas 三环记 `不适用`，报告里必须留一行 `本需求判定：纯加法 / 不启用三环` + 依据。**这是一条合法路径，不是绕过工作流**——结构事实仍由 `after_finish` hook 保鲜，实现任务照旧拿到路径注入的事实。
- **`prd` 不再恒参与**（原口径：任何需求至少在域级 PRD / 追溯总表留一条）。它在**资产为空的旧项目**上等于「第一个小需求就要写全套项目级 PRD」——成本炸弹，而且与 §2 输入表（要求资产已存在）自相矛盾。改为按上面的门判定；若判定「本需求不改任何应然资产」（纯内部重构且不影响产品定义），apply 报告 `no-op` 并写明依据，**不**强改资产。
- **两条报告口径**并列**，可同段共存**（2026-09-27 补，`3509 §B91`）：① 三问全否 ⇒ 写 `本需求判定：纯加法 / 不启用三环` + 依据；② 本需求不改任何应然资产 ⇒ 写 `no-op` + 依据。一个需求可以**两条同时命中**（如「新增一个与产品无关的通用工具函数」：既三问全否，又不碰任何应然资产）——此种情形**两行都写**，不择一、也无优先序。
- **门是语义判断，机器判不了**（与 `§8 末注` 同源）：所以要求把**判定 + 依据**写进 `atlas-apply.md`，让复核者一眼看出它有没有偷懒。
- **环间人工门（E1 起；2026-09-29 重议 = `3507 AQ`，B124 结论）**：两道人侧门——① **走查单确认门（实现前，硬）**：改变应然 UI 的需求，域级 PRD 的「用户旅程走查」节须用户显式确认（节首 `已确认：<日期>`；`rings/prd/reference.md` §4·八，确认前对照 `product/design.md`（存在时）视觉方向，`3507 BE`），确认前 **`apply` 不得进 `e2e` 环**；② **验收走查门（收口前）**：该域 E2E 在真实应用全 green 后，用户按域级 PRD 功能清单逐条在真实应用上过一遍（可用 + 符合已确认走查单），确认后才算域收口；不符 ⇒ 差异登记且域不收口；真实应用不可用 ⇒ 与 E2E 同为 `blocked` 显式带原因（`rings/e2e/reference.md` §5.4 末）。`e2e` 用例另走独立审查门（`rings/e2e/reference.md` §12）+ 首跑分类协议（同文件 §5.4）。原型增量人工 review 门已随环退役（`3508 §92`）。
- 结构事实的**实现后**回写不属于 apply：由 `after_finish` hook（`refresh_structure.py`，事实区）与 Finish 的 `trellis-update-spec`（语义区）负责（D38）。

`all` 模式的顺序固定为 **`structure → prd → e2e`**（含 structure 全量）。

### 3.2 无需求卡的应然资产修订（第 4 种形态；2026-09-26 补，`3509 §B10` + `§C11④`）

**判据（先问这一句）**：**有没有一条需求要接？**

| 答 | 走哪条路 |
|---|---|
| **有** | Trellis 需求流程 + `apply <需求ID>`（§1）；需求卡是唯一上游 |
| **无**（还在定 / 修应然资产本身，尚未写代码） | **不建需求卡、不建任务**，直接按 `prd → e2e` 逐环跑，逐环**只改受影响集合** |

- **为何要这一条**：原契约把「需求」当作跨环增量的**唯一**上游，而三环只有「全量」入口 ⇒ agent 只能把资产修订塑成需求。实测（2026-09-23）：把「对照截图修订应然资产」当成需求，建了 `1 parent + 6 children` 的任务树，用户当场纠正（原话见 `3508 §33`：还没写代码，在解决生成原型阶段的问题）。
- **与 §1 的关系**：本形态**不经 `apply`**（无需求 ID），但仍适用 §5 的增量边界与 §5 的确认门（整页重建 / 删页 / 全量重生成仍需用户确认）。

**四条粒度纪律**（`3509 §C11④`）：

1. **一条工作单元承载 N 条问题** —— 问题清单是**工作单元内的产物**，不逐条开任务。
2. **不得用子任务树** —— 否则评审被任务生命周期重新串行化（用户 2026-09-23 原话：「所有原型和 E2E 的修改，不应该经过 trellis 吧」）。
3. **清单落 `product/reviews/<日期>-<主题>/`**：`README.md` = 缺口清单 + 决策表 + 验收标准；`plans/` = 分域修订方案。**不落知识库**（会与 `product/` 脱节）、**不落任务目录**。
4. **从「收集」切到「优化」的时机 = 用户显式宣布收齐**（不用自动阈值）。

**门控态（预期红）**：`review` 期间 `validators/validate_testids.py` 的「分片应然 ⇔ 前端实然双向集合」**允许红** —— 分片要等 review 通过后才写，这是门**自身**造成的预期红；**收口前必须绿**。取证：2026-09-23 首轮实跑（见知识库《评审粒度》note）。

**收口留痕**：本形态**不写** `.trellis/tasks/<需求ID>/atlas-apply.md`（无需求 ID）——执行记录写进 `product/reviews/<日期>-<主题>/README.md`（§8 的固定小节照旧填）。

## 4. 影响面识别

**形态**：**agent 语义判断为主 + 结构证据约束**。apply 读需求卡，对照 `routes.md` 与 `product/e2e/e2e-index.md` 页面表推导，产出**结构化影响面清单**：

```
affected_domains:   [<域 slug>, ...]                 # 取自 _meta.json.domains
affected_pages:     [<页 slug>, ...]                 # 取自 e2e-index.md 页面表
page_change_kind:   { <页 slug>: ui | non-ui | backend-only, ... }
affected_acs:       [<既有 AC ID>, ...]              # 若既有 AC 被改动/废除（新增 AC 由 prd 步骤产生）
evidence:           [ "prd.md:<行/要点>", "routes.md:<行>", "e2e-index.md:<页面表行>", ... ]
```

- **证据必须可定位**（`global-rules.md` §6）：每条受影响项都要指回需求卡行 / routes 行 / 页表行。
- **图谱影响面基准（2026-10-05 图谱批 1）**：profile 声明 `graph.backend` 的项目，推导前先跑
  `python3 .atlas/scripts/impact_report.py --root . --task <需求ID> --symbols/--paths/--diff-base …`
  （落 `.trellis/tasks/<ID>/impact.json|md`，用前现刷、确定性可复现；契约见 `shared/stack-profile.md` §3.6）。
  agent **先读报告再做语义判断**——它给的是 name 级静态调用面（偏宽、保守，无边 ≠ 无人用），
  是「结构证据约束」的机器侧输入，**不替代**语义判断与下面的兜底交互。未声明 graph 段 ⇒
  报告器 exit 3 `not_ready`，本步显式跳过（记入执行记录），不阻断 apply。**收口时对账**
  （B191-1，2026-10-07 起）：`.trellis/tasks/<ID>/impact.json` 存在的需求，收口必跑
  `python3 .atlas/scripts/impact_reconcile.py --root . --task <ID> --diff-base <ref>` ——
  预测集 vs 实际 diff 双向差集与基准漂移 ⇒ WARN 指名（漏报/多报双侧留痕 `impact-reconcile.json`）；
  报告缺失 ⇒ SKIP（显式，不是通过）。
- **禁止**用正则或关键词机械匹配需求文本判语义——regex 只判 token，语义交 agent（`rings/e2e/reference.md` §8 注；D53/E16 反例：Autonoma 用 regex 判句意，680 次重试 / $11 / 零用例）。
- **兜底交互**：出现以下任一情形，**一次性汇总问用户（≤3 问）**，不得自行拍板：
  1. 需求映射不到任何既有域 / 页（如全新功能、需新页 / 新域）；
  2. 可在多个域 / 页之间二义；
  3. 变更性质（`ui` / `non-ui` / `backend-only`）判不准。
  问法参照 `rings/prd/reference.md` §5 诊断节奏：一题一问、能查 `structure/` 与既有 PRD 的不问。
- 推导结论写入 §8 的执行记录，作为各环增量与校验的输入。

### 4.1 「改动既有能力」的判据（三问门第 1 问）

> **定义**：这次改动会让某个**已经被记录过**的能力，其行为 / 界面 / 数据 / 契约发生变化（或消失）。

**锚点**（「已经被记录过」在哪里，决定你拿什么当对照）：

| 手上有什么 | 锚点 |
|---|---|
| 项目级资产已存在 | PRD 里已登记的**功能条目**（`FN-*`）/ 规则（`*-R-*`） |
| 资产为空（旧项目首次接入） | `structure/` 反向出来的**能力条目** |

**判据主体 —— 回退测试**：把这次新增的东西**整块撤掉**，既有的东西能否**一一还原、且无残留影响**？

- **能** ⇒ **纯加法**（不需要基线）。
- **不能** ⇒ 动了既有能力。

**四条自问（任一为是即算）**：① 涉及的功能在锚点里**已有名字**；② 会让某个既有能力的**可见行为**变化；③ 会让某个既有能力**消失或改名**；④ 会改某个既有能力的**输入 / 输出契约**。

**边界案例（最容易判错的几条）**：

| 情形 | 算吗 | 为什么 |
|---|---|---|
| 在**既有页面上**加一个独立新功能 | **不算** | 「挂在既有页面上」≠「改了既有能力」；回退测试能还原 |
| 只改既有能力的**一句文案** | **算** | 但基线成本极小（只动那一行） |
| **纯内部重构**（换实现、行为不变） | **不算** | 即 `no-op` |
| 改**非功能需求**（性能 / 安全 / 兼容） | **算** | 全局 PRD §八 是既有应然条目 |
| **域的新增 / 删除 / 改名** | **算**（最重） | 并且连带触发 structure **re-key**（§3 的唯一例外） |

**不得自判**：判定与依据必须写进报告；这是语义项，**不进机器门**（依据 `3508 §75`：连「哪几条可机器修」都得先真的改一条跑一遍才知道）。

## 5. 各环增量边界与覆盖语义

apply 只对**本次受影响集合**落笔，**不整文件覆盖**任何项目资产；各环的增量规程按其契约执行：

| 环 | 增量边界 | 契约出处 |
|---|---|---|
| `prd` | 只改**受影响域**的域级 PRD 章节（功能清单 / 规则 / AC / 变更记录）+ `README.md` 追溯总表对应行 + 全局 `prd.md` 的「范围与处置」「修订记录」（如涉及）；**追加 / 修订，不重写全量** | `rings/prd/reference.md` §9、§10 |
| `e2e` | 只更新受影响页的**分片**与相关**索引行** + 页面表 + 反向视图；ID 删除不复用、每页独立 | `rings/e2e/reference.md` §6.3、§5.3 |
| `structure`（例外） | 仅域清单变更时 re-key；不重读代码、不改语义 | `rings/structure/reference.md` §2.2 |

**覆盖语义与用户确认门**（`global-rules.md` §7）：

- **常规（非破坏性）**：单页 / 单域增量更新、在既有域级 PRD 追加条目、在既有分片追加用例。
- **必须显式确认**：整页重建 / 删除页 / 全量重生成 / 删除或重写既有域级 PRD 或既有用例 / 生成或改写 `product/stack-profile.yaml`。
- apply 自身**从不**整体覆盖文件；遇确认门动作时，先复述待确认内容并等用户回复。

### 5.1 并发写面仲裁（2026-09-26 补，`3509 §B27`）

**问题**：项目级资产里有一批**每个需求都要写**的共享表面（E2E 索引 `product/e2e/e2e-index.md`、`ATLAS-UPSTREAM.md` 的回灌清单…）。本契约原本按「一条需求一次」写，没有并发约定 ⇒ 同板多任务并发时必出「后写覆盖前写」或「主表 ↔ 反向视图不一致」（后者会被 `validate_e2e_index` 抳到，但代价是返工）。

- **单写者表面（硬）**：每个共享文件在任一时刻**只允许一个在办任务**持有写权。
- **声明与分派**：并发前，每个任务必须**声明自己要写哪些项目级文件**；由用户 / 编排者按 `one writer per file` 分派；冲突时**停下报告**，不得抢占（实测第三次才守住，`3508 §55 一`）。
- **降串行度的建议（非硬）**：索引类表面可**按用例 ID 分区**（或拆成每页一份的反向索引）；但反向视图现在是**生成**的（`single-source` §2），所以首选是「一次只让一个任务改主表」。
- **不属本节**：需求级文件（`.trellis/tasks/**`）天然一任务一份，无需仲裁。

### 5.2 回流原语（`backfill`，第 4 种模式；2026-09-28 定，`3509 §99`）

**病根**：管道只建模**前向边**（需求 → 资产 → 实现），反向边（下游发现上游缺口）全靠台账条目 + 跨任务捎带 ⇒ **无通道、无写面、无批量节奏、量不可见**。实证：M1 批 13 条 AC 为挂靠而补（`3508 §91.2`）、E1 收口豁免（PRD 批内改）、`关联AC` 错位转交 prd 环、`§B101` 取证值反灌配置 —— **回填是常态，不是异常**。

**分型（只有第一行走本模式）**：

| 分型 | 通道 |
|---|---|
| **补写 / 修订 / 收口 / 配置**（改**已存在**的上游工件） | **`apply backfill`（本模式）** |
| 需**裁决**（选项 A/B、要用户拍板） | 裁决队列本体（`shared/knowledge.md` §9 + `shared/closeout.md` 步骤 3） |
| **退役 / 迁移**（产物或规则失去宿主） | 生命周期（`shared/global-rules.md` §11） |

**执行四件**：

1. **分组**：按「**上游目标 + 改动类型**」分组；**一次确认门过一组**（不逐条问）。
2. **攒批节奏**：收口时扫描本任务产生的回填 → 登记入队；`backfill` **攒批集中执行**（不即时零散改）。每批 **≤ 10 条**（`3509 §100` 的人工预算上限），超出顺延下批。
3. **独立写面**：`backfill` **自身声明写面**（它可能同时碰 PRD 章节 + E2E 分片 + 索引 + `stack-profile`）⇒ 按 §5.1 的 `one writer per file` 仲裁；跨环同步（含**下游用例改挂**）在同一批内完成。
4. **闭环钩子（硬）**：① 回填完成 ⇒ 触发**受影响下游的重跑 / 重审**（`shared/gates.md` 的验证预算列）；② 台账条目**随批收口挪卷**（不得「改完了但条目还挂着」）；③ **各环门照跑**（`validate_prd` / `validate_testids` / `validate_e2e_index` / `validate_ledger`）——**不得**以「只是回填」为由跳过。

**生命周期五步**：发现（写用例编译失败 / 审查 finding / 运行红 / 实现撞墙）→ 登记（入队）→ 裁决（人拍，P0/P1 分级）→ 执行（本模式）→ **回流验证**（下游门 + 台账挪卷）。

**与「用例先行」的咬合**：用例先行（`rings/e2e/reference.md` §6.2）会在实现前暴露上游缺口 ⇒ **P0 回填的时限执行器 = 域实现准入前必须裁决并执行**；上游缺口阻塞实现属**预算击穿**（`3509 §94`），登记为流水线缺陷（不与产品缺陷混写）。

## 6. `all` 模式

- **顺序**：`structure → prd → e2e`（E1），逐环走**各环自己的全量流程**（`rings/structure/reference.md` §6、`rings/prd/reference.md` §5、`rings/e2e/reference.md` §6）。apply 只做**编排与顺序**，不重实现环内步骤。
- **环间审查门（硬，E1）**：`e2e` 用例产出后、生成脚本前，跑 **E2E 环独立审查**（`rings/e2e/reference.md` §12）——**有 `Critical` ⇒ `gen_e2e_scripts.py --apply` 拒绝写盘**。原「原型产出后停下等用户 review 原型」的门已随原型环退役（`3508 §92`）；应然 UI 的人工确认 = 两道人侧门（**走查单确认门**实现前 + **验收走查门**收口前，见 §3.1 环间人工门；2026-09-29 `3507 AQ` 重议）。
- **幂等**：重跑 `all` 不产生漂移——各环自身的幂等 / 确认门语义照旧（如 `prd` 已存在域级文件默认不覆盖、需 `--force`）。
- **断点续跑**：任一环失败或处门控态 → **停在该环并报告**，**下游环不静默跳过**。用户修好后重跑 `all`，**已完成的环按产物存在与否跳过**（对齐 Trellis 的 `[once]` 语义，`workflow.md` Rules §4）。
- **门控态**：`prd` 待决策非空 ⇒ 只产全局 PRD 与追溯总表；`e2e` 进门控（只落空骨架）。apply 如实报告，**不判失败**。
- **启动顺序自适应**：项目形态（绿地 / 重构 / 存量）决定各环实际工作量，但 `all` 的编排顺序固定；`structure` 环的 A（可选）与 H（条件）仍按其契约过确认门。

**执行记录落点**：`.trellis/tasks/<需求ID>/atlas-apply.md`（需求级执行记录；**非产品文档**、非需求卡，`single-source.md` 的需求卡仍是 `prd.md`）。每次 apply 覆写本文件为最新一次运行结果（幂等）。**无需求卡的应然资产修订（§3.2）本文件 N/A** —— 它的记录落 `product/reviews/<日期>-<主题>/README.md`。

记录内容（固定小节）：

1. **模式与需求 ID**（`apply <需求ID>` / `apply adopt` / `all`；日期）

## 9. patches（Trellis 挂载补丁）

- 落点：`patches/workflow-plan-apply/`（`spec.json` + `apply-patches.py` + 片段）。
- **锚点式版本化**（2026-09-27 改，原「见标记即跳过」见 `3509 §B93`）：只做外科式插入 / **整块替换**，不整体覆盖 `.trellis/workflow.md`。块形态：
  ```
  <!-- atlas:apply:<id>@<片段正文 sha256 前 8 位> -->
  <片段正文>
  <!-- /atlas:apply:<id> -->
  ```
  判据 = **块内正文是否仍等于当前片段**：指纹相同 ⇒ `skipped`；指纹不同（片段更新过）⇒ **整块替换**；旧式块（无指纹 / 无结束标记）⇒ 就地补格式（`upgraded`）或整块替换（`replaced`）。
- **旧式块的安全迁移**：`insert_before*` 的块紧邻锚点 ⇒ 边界 = 重算的锚点位置（精确）；`insert_after*` 且正文不符 ⇒ **报 error 且不改文件**（不猜边界）。
- **可重放**：Trellis 升级、上游模板变更、**或本包片段自身更新**后，重跑 `install.sh`（或 `apply-patches.py --apply`）即对齐；`install.sh` 按真实 `applied / replaced / upgraded / skipped` 回报，**不把「跳过」报成成功**。
- **前置告警（未决 B2）**：全局 `trellis` CLI 版本落后于项目 `.trellis/.version`。在把 CLI 升到项目版本之前，`trellis update` 的模板行为不代表当前版本，**补丁可能被 `trellis update` 冲掉**——因此打补丁前应先升级 CLI（`trellis upgrade`），升级后重跑本补丁。
- 应用本补丁 = 改 `.trellis/workflow.md`，属 `global-rules.md` §7 确认门动作；由 `install.sh` 在用户显式安装时执行（`--no-patch` 可跳过）。
