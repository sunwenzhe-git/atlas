## 1. 结论先行

| 外部机制 | 处置 | 落点 |
|---|---|---|
| WikiBench 任务构造协议（coverage/retrieval 双题型 + 逐题期望事实清单） | **吸收**（经 C1 修法对齐消费位） | runbook §2 后独立小节 + playground `TASKS.md` 任务侧 |
| 双 LLM judge 判分（事实命中 + 锚定核验） | **观察项**（rubric v1 候选仪器，带前置条件与触发形态） | runbook §4 触发行 + 本文件 §8 |

**一句话**：值得搬的只有一件——把 WikiBench 的「题目怎么造、期望事实怎么写、判分者凭什么判」协议，经**消费位对齐**（AC 投影细化 + 盲评证据面输入）收进 ablate 层 3；OpenWiki 本体不引入，其 WikiBench 数据作为消融减法假设的**外部反方证据**登记在案（对称防偏置）。

## 2. 情报取证（一手已核事实 + 未核实项显式登记）

### 2.1 WikiBench 协议（博客一手，2026-11-22 核）

1. **任务构造**：仓库 pin 特定 commit；题目自动生成两类——**coverage 题**（共享模板 × 主题子系统/包面）+ **retrieval 题**（围绕具体行为逐题手写）；每题带 **JSON rubric**：正确答案应命中的事实清单。
2. **reader agent 三条件**：wiki-only / source-only / wiki+source；**wiki-only 最差；wiki+source 最高分且比 source-only 便宜**（wiki 给 reader 起点，免全仓重建）。
3. **双 LLM judge**：① 事实命中（答案覆盖期望事实的比例，题分 = 命中数/期望数）；② **锚定核验**——答案中的事实必须锚在 reader **实际读过的页面**上（治「答案对但不是靠文档对的」）。
4. **指标**：accuracy / cost / runtime 三轴；OpenWiki 0.3.0 > 0.2.5 > bare DeepAgents，版本增益集中在 coverage 题；高成本模型多读 ~3× 文件只多写 1.2–1.5× 页（力气花在理解不在产出）。

### 2.2 未核实项（不引用原则）

- 搜索摘要另称「linked evidence 使准确率 +27% 且单查询成本下降」——**该数字不在博客正文**，仓库 evals/ 页抓取超时未核。按「不造假绿 / 无一手不引用」纪律，本数字**弃用**；留此一行作通道备忘（evals/ 目录可日后补核）。

### 2.3 对 Atlas 的推论（假设，非结论）

1. **竞争假设入账**：WikiBench 给「预消化上下文有正产出面收益」提供了系统实证——这是对 ablate 减法假设的**外部反方**。消融防的不是这个数据本身，是「把减法假设当默认真理」；层 3 A/B 恰是检验仪器，本吸收强化仪器而非预设结论。
2. **对象差异声明（双维度）**：① 形态维——WikiBench 测的是 AI 生成的全仓叙事 wiki；Atlas 装配面是确定性抽取的指针层 + 事实表 + 机制文档（`RFC-20261122-04`）。② **判分维（评审 C1）**——WikiBench 是**问答判分**（judge 判 reader 的答案），Atlas 层 3 是**构建产物判分**（门册 + 人盲评判两臂产物）。协议要素只在「任务怎么造、期望怎么写」层面可移植，「判答案」的仪器形态不可直接迁移——A1 的消费位对齐即为此而设。
3. **wiki-only 最差** ⇄ Atlas 装配形态自证：事实表/机制文档永远指向代码事实源（骨架不内联纪律），不独立成知识库——外部数据与既有定案同向，无需改任何判据。

## 4. 方案

### 4.1 A 批：runbook + playground 任务侧增补（纯 research / 宿主仓文件，零代码零门，无装配面影响）

**A1｜runbook §2 之后新增独立小节「任务构造协议（扩集入口；WikiBench 吸收，RFC-20261122-06）」**：

1. **双题型**：重放任务不可得时（或扩集时）按双题型造题——**coverage 题** = 共享模板 × 装配面覆盖的子系统（对齐结构环 domains 面）；**retrieval 题** = 围绕具体行为逐题写，一题一行为。
2. **前置检查步（s1）**：造题前先 dump 装配面 domains 清单核对 coverage 模板映射——模板子系统与 domains 面对不上即停（证伪条件可执行化，见 §7）。
3. **期望事实清单 = 任务卡 AC 的投影细化（C1 修法）**：`TASKS.md` 每任务 AC 行 ⇒ ≥1 条**单句可判真假陈述**（如 T1「AC：footer 可见且含版本文档」⇒ 「①页脚含版本号字符串 ②页脚含构建日期 ③页脚渲染可见」三条）；清单落 **playground `TASKS.md` 任务侧**（AC 列旁附注或任务节内），**不另立第二真相源**；**消费者 = 人盲评判分者 V1/V2 维的证据面输入**（升版 rubric 时同步改对应维的证据面表述）；措辞锁「单句可判真假、人可复核」。
4. **跨代可比绑定（M2）**：新造题**自第 2 代起才进集**（除非首代重放不可得），首代保持纯重放；每次扩集按 runbook §9 对齐声明义务在账本节头声明对齐策略。
5. **版本语义（M1）**：期望事实清单是**任务侧工件，不动 rubric 版本号**；rubric 版本仍按既有跨代换版、节头单值纪律。
6. 任务卫生四条硬边界原样继承（worktree 重置 / 每臂独立会话 / 臂序随机 / 跑前探针）。

**A2｜runbook §4 追加锚定核验观察触发一行**：

- 触发形态：层 3 **A/B 样本**（非 R1–R5 单臂流程样本，见 §9.2 拆词）中出现「B 不差于 A ∧ 门册零信号 ∧ 人盲评理由含糊」的不可解释样本 ≥2 例。
- **前置条件（M3）**：启用前先确认**会话转录留存面**（runbook §5 现只转录 token、无转录留存要求——不先立留存面，触发后无证据源可锚）。
- 锚面定义（M3）：核验「agent 是否消费过**机制产物文件**」（PRD / E2E 脚本 / 事实表）——**不锚「装配页」**：装配内容为静态注入上下文，读取非代理选择，「锚在装配页」恒真、无判别力。
- **现在不建**，判分面保持二元盲评最小化；若触发启用，rubric v1 **自下一代起生效、不回溯重判**（M1）。

**A3｜runbook §8（拍板流程）追加竞争假设旁注（m2）**：

- 旁注一行：WikiBench 实测「wiki+source 优于 source-only 且更便宜」为减法假设的**外部反方证据**（形态差异见本文件 §2.3.2）——拍板保留/退役时双向防偏置：**保留与退役结论同样只认本仓层 3 实测**，外部数据只作假设输入不进账本。

### 4.2 B 批：QUEUE 观察室 +1 外部情报行（格式对齐既有行 `:56-60`）

- **外部情报·OpenWiki/WikiBench**（2026-11-22 情报吸收；[langchain-ai/openwiki](https://github.com/langchain-ai/openwiki) 18.1k★，MIT，活跃推送中；LangChain 按 Karpathy「LLM Wiki」思路做的代码仓文档生成/维护 CLI，自带 WikiBench 评测）：参考点 = ① 生成 wiki + 代码 reader-agent 实测优于裸代码且更便宜（消融减法假设的外部反方数据，已按 A3 登记进 runbook 拍板前提）；② Grounded Claims 逐条证据版本锚（与 `RFC-20261120-01` §8「任务级结构键快照」同族——触发计数经本 RFC 裁定共用，见 §4.3）；③ OKF v0.2 打包格式（agent 消费文档格式的生态收敛候选）。升室：OKF 被主流 agent 文档生态实际采纳 ≥2 例 ⇒ 按 DR2 起「装配面格式互操作」决策行；出室：OKF 生态判断与 OpenWiki 机制面**自登记日起 6 个月**无新形态 ⇒ 归档（通道无关口径，评审 M4）。

### 4.3 显式不做（含否决理由）

| 不做 | 理由 |
|---|---|
| 引入 OpenWiki 本体 / 采纳仓装生成 wiki | 对立押注 + 快照必漂（Architecture.md 替代映射定案）+ CI 模型烧钱循环违背装配瘦身；且 WikiBench 的 wiki-only 最差恰说明**脱离代码读文档**不是 Atlas 形态 |
| claim 侧车 / 证据版本锚进结构环 | 与 `RFC-20261120-01` §3.3 C 批撤销三理由同构（锚不存在 / 必然恒绿 / 语义被高估）；其 §8 观察项触发条件 = 「结构漂移 added 键真实收口漏处置 ≥3 次**且每次都导致返工**」未满足。**触发计数共用系本 RFC 裁定的类比登记**（20-01 原文对象是任务级结构键快照 + predicted_keys，非 claim 侧车）——翻案需先推翻类比本身 |

## 7. 最强反方与证伪条件（s3 重排）

**最强反方（评审 C1）：「WikiBench 是问答判分，Atlas 层 3 是构建产物判分，根本不同构——题目协议搬过来，判分消费不上，就是无人消费的平行工件，与任务卡 AC 双轨维护必漂移。」**
成立过，v1 恰犯此病（期望事实清单自称「机器可复核」而无任何机器消费它）。修法已折入 A1 第 3 条：清单 = 任务卡 AC 的投影细化（单一来源 = AC，不另立真相源）、消费者明指盲评判分者证据面、措辞降格为「人可复核」。残余风险 = 盲评判分者实际不用清单——处置：升版 rubric 时同步改对应维证据面表述，把清单嵌进判分动作而非并列文件。

**次反方（合并原两条）：「纸面吸收（runbook 多几段字，层 3 一场没跑）+ WikiBench 数字是 OpenWiki 自家评测（二手信仰）。」**
成立过半。处置：本 RFC 自我定位为**仪器设计输入**（对标 `RFC-20261106-01` 判据 4 人工抽检形态），不做机制门、不声称收益；外部数据只作假设输入且双向防偏置（A3 对称措辞），永不进 Atlas 账本。

**证伪条件（可执行）**：
1. 首次扩集实跑时，若「前置检查步」（A1 第 2 条）dump 出的 domains 面与 coverage 模板对不上、或期望事实清单写不出单句可判真假粒度 ⇒ 判本吸收为纸面，构造协议回退为纯重放口径，runbook 增补段删除。
2. 层 3 A/B 首代若出现盲评判分者从未引用期望事实清单（抽样盲评记录核）⇒ 消费位声明失败，清单降格为任务卡 AC 编写纪律，退出判分链。
