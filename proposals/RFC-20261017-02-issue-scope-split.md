# RFC-20261017-02 · 缺陷登记**边界**：只有 atlas 的设计问题进 atlas 库

- 状态：**待独立评审**（评审通过后落盘；本文只是方案，未改任何库文件）
- 起因：维护者 2026-10-17 指出「atlas 无关的也往 atlas 上提 bug？」——要求**项目侧与 atlas 侧分开**，只有 **atlas 的设计问题**才进 atlas 库。

## 1. 病灶（用本轮现场说话）

2026-10-17 一天内在 atlas 库（`duty-review/bugs.md` E2E 段）新增 **#24–#30 共 7 条**，全部由**同一个项目**（百炼/v2前端）的真跑现场驱动。其中确实混进了两类不该进库的东西：

| 混入形态 | 实例 | 为什么不该进（或不该这样进） |
|---|---|---|
| **靶场属性被写成「缺陷」** | #26：靶场用「图形验证码 + cookie 会话」 | 这是**项目的靶场事实**，不是 atlas 坏了。atlas 侧唯一成立的是「契约三态装不下这类形态」= **契约缺口**，且已按 `D103` 处置（描述路径） |
| **项目侧处置缺失（只记了 atlas 半）** | #30：零步基线挂到 30s | atlas 半（探针应快判 `null`）成立；但**触发面是项目自己把带参页面写进页面表**（页级路由不可渲染），这一半被漏写，读起来像纯 atlas 缺陷 |
| **已处置却仍挂在「开放」区** | #27（已按 `D104` 修）、#26（已按 `D103` 落） | 库是**工作面**不是台账（`duty-review/README.md` §4：出库 = 完全确认修复后当场删除），已处置的应出库并指向决策行 |

反例（这些**没有**混进 atlas 库，是本轮做对的）：v2 的 `app_base_url` 要带 tenant、页面表路由改 `/console/#/...` 形态、仓库没装 `@playwright/test`、dev server 只有 13.8MB dev build、会话短命需人工登录 —— 全部记在 v2 任务件（`testid-landing.md` §9/§10/§11）。

## 2. 判据（本 RFC 主张的登记边界）

一条问题要进 atlas 库，必须能回答「**atlas 的哪一份代码 / 契约 / 校验器是错的**」。按此分三档：

| 档 | 判据 | 落点 |
|---|---|---|
| **A. atlas 设计问题** | 缺陷本体在 atlas 的 `scripts/` / `validators/` / `_support/` / `rings/*/reference.md` / `shared/*.md`：判据错位、默认值不足、口径分裂、生成物能力缺口 | `duty-review/bugs.md`（atlas 库）。**须写明 atlas 侧的错误面（`file:line`）** |
| **B. 项目侧** | 资产选择 / 环境 / 数据 / 靶场属性：路由形态、base query、依赖安装、构建产物、会话时长 | **只进项目任务件**（如 `.trellis/tasks/<id>/`）。**不入 atlas 库** |
| **C. atlas 契约缺口（可归因但非缺陷）** | 契约的**形态集合**装不下真实世界的一类（例：登录形态三态 vs 验证码+cookie），且**已有决策行处置** | **不入库**（或入库一行即出库），正式记录在 `DESIGN.md` 决策行 + `CHANGELOG`；库内**最多**留「已出库：<编号> ⇒ <D 行>」的锚 |

**两条硬约束**：
1. **一条问题涉及两档时必须拆开写**（A 半进库、B 半进项目件），并在库内那半写明「项目侧半见 `<项目件路径>`」——防「读起来像纯 atlas 缺陷」。
2. **已处置的 A 档问题按出库规则处理**（完全确认修复后当场删除，库内不留「已修但挂着」的僵尸行）。

## 5. 决策点（请评审者表态，别客气）

1. **已修的 A 档问题（#24/#25/#28/#29）出不出库？** README §4 说出库 = 完全确认修复后**当场删除**，库是工作面不是台账。我的倾向：**出库**（正式记录已在 `DESIGN.md` D 行 + CHANGELOG），但那样本轮 7 条里只有 #30 一行留在库 ⇒ 库会显得「空」。**这属于口径取舍，由维护者/巡检决定，本 RFC 默认「保留到下一轮巡检真跑复验后出库」**。
2. **C 档（#26）「入库一行即出库」还是彻底不入库？** 我倾向彻底不入库（D103 + CHANGELOG 已是正式记录），库内只在同根归纳留锚。
3. **载体**：本仓「issue」= `duty-review/bugs.md`（`gh` CLI 在本机不可用，GitHub issue 面暂时只能手工开）。是否要求在 GitHub 上同步开 issue？
4. **#30 的 v2 半**该给什么结论（用 `守卫:` 承载实例 id？还是把带参页面从页面表里摘出去、改用例自带 `goto`）——这决定 §12 怎么写。

## 6. 残留与诚实边界

- 本 RFC **只改登记面**，不改任何代码/契约；#30 的 atlas 半仍是**开放**（本 RFC 不含修法实现）。
- 「已出库」不等于「没发生」：正式记录在 `DESIGN.md` 决策行 + `CHANGELOG`；出库只是把工作面清干净（README §4 原文）。
- 本 RFC 不能防止下次再混入——它只是把判据写下来来；是否给巡检器加一条机器判据（如「条目必须含 `file:line` 且标注 A/B/C 档」）**不在本 RFC 范围**，如需另起。
