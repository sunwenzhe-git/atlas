## 1. 现象与取证 (The Problem & Evidence)

### 1.1 触发形态（抽象）

* **规则 / 环节**：提案起案流程（`proposals/TEMPLATE.md` 填写）。模板从「§1 现象与取证」直接开始——**模糊点的澄清没有结构位**：需要人拍板的分叉靠会话里临时追问，追问的质量与覆盖随会话状态漂移；「待确认问题」零散地嵌在各节正文，评审者无法一眼区分「已拍板的定案」与「仍在等拍板的悬案」。
* **触发时机**：每次起案。
* **具体行为**：两条在案缺口——①访谈式追问纪律（复述理解 → 顺着回答挖 → 极模糊时发散收敛）与「先问人再问代码」的既有判据（`shared/stack-profile.md:204`）已拍板却无模板承载；②外部转述的经验（需求评审 AI 用访谈式逐层深挖而非检查清单，且「必须明确 / 建议明确」分档放行）在 Atlas 侧无对位物。

### 1.2 客观证据 (Evidence)

- **外部转述（会话经验级，原文未留档、无仓内锚）**：需求模糊是 AI 端到端最大失败模式，「怎么提需求」的权重被端到端化放大；复述理解是最高效纠偏点；「必须明确（**做什么 / 为谁做 / 关键业务规则 / 验收标准**）不明确不放行，建议明确（优先级 / 异常场景）不强制」的分档与提案场景同构。**引用纪律**：该经验若要写进对外文档或正式依据，须先补「标题 + URL + 访问日期」；在此之前只能按「会话经验」引用，不得自称「外部实证」。
- Atlas 侧已拍板件与可核定位：`shared/stack-profile.md:204`「判定顺序（2026-10-15 补，用户实测驱动）——先问人，再问代码」；追问纪律的同类默认在 `skills/atlas-grill/SKILL.md`（「事实属于模型，决策属于用户」「不要向用户询问任何你能查到的事实」、单轮严控 1~2 问）。**本提案不采用「深度 4 问」**：该框架的对象是「专家」（学习外部技能场景），与提案起案场景错配；收尾自检改用起案场景两问（见 §2.1）。
- 模板现状实读：`proposals/TEMPLATE.md` §1 现象与取证 → §2 决策与权衡 → §3 改动面 → §4 验证 / §4.5 留出验证（全文 89 行）——无澄清节；§1 的「拒绝主观推测」纪律是判据面，不承担起案前的需求澄清。

## 2. 决策与权衡 (The Decision & Trade-offs)

### 2.1 核心定案 (The Decision)

* **方案总结**：`proposals/TEMPLATE.md` 在标题元信息之后、§1 之前增补 **「§0 起案前澄清（访谈式，落笔前完成）」**，三步一段：
  1. **复述理解**：一句话回述需求核心意图（供需求方确认有无理解偏——最高效纠偏点）；
  2. **访谈式追问**：顺着回答挖新暴露的模糊点，不走预设清单；极模糊需求列 2~3 种合理解释供选择（发散收敛），不直接驳回。**边界**：模型可自证的事实（代码现状、依赖版本、契约文本）自行查证、不提问，只问**意图与取舍**（同 `skills/atlas-grill/SKILL.md` 的「事实属于模型，决策属于用户」；与 `shared/stack-profile.md:204` 同向，不构成相反默认）；
  3. **必须 / 建议分档 + 收尾两问**：必须明确 = 做什么 / 为谁做 / 关键约束（对位外部经验的「关键业务规则」）/ 验收口径（**不明确不起案**）；建议明确 = 优先级 / 异常场景 / 历史包袱（可带显式默认值起案，默认值写入正文不得静默）。收尾自检两问（起案场景的两问，不搬外部技能学习框架）：**① 这是设计问题还是用法问题？② 有没有更小改动面？**——答不上的项在 §0 内显式记「待澄清」，并在 §2.1 方案总结末尾带一行「待确认：…」（**§2 无独立小节，不新增节号**）。
  * 澄清产物**不强制落盘**：过程留在会话即可，**不设复核义务**——评审只按模板既有节判，不追查 §0 是否走过。落盘时（可选）以「§0」节随提案提交，供作者自查留痕。
* **为何这是正解**：两条缺口同源（澄清纪律已有共识、无承载结构），模板增补是最轻落位——零门零字段零代码；且与既有结构无冲突（§0 产出喂 §1 现象与 §2 决策），§0 的「待澄清」有明确收纳行（§2.1 末尾一行），不新增节号、不改既有节引用。

### 2.2 考虑过的备选方案及否定理由 (Considered Alternatives)

* **备选 A**：澄清做成机器门（起案 PR 缺 §0 段 ⇒ 拒）
  * *否定理由*：违反零新门纪律；澄清的质量无法机器判（填了不等于问了），机器门只会教会「复制模板字面」。
* **备选 B**：澄清内容并入 §1（现象与取证前置一段）
  * *否定理由*：§1 的纪律是「只报设计问题、零业务上下文」——澄清过程天然带业务语境，混入会污染 §1 的取证纪律；分离 = §0 可含语境、§1 保持纯净。
* **备选 C**：不做模板增补，靠「记住这些纪律」
  * *否定理由*：纪律无结构位就靠不住（本仓已有「记账未落」先例）；且起案者是不同会话 / 不同 Agent，记忆不跨会话承载。

### 2.3 必须警惕的刺痛代价与兼容性影响 (Trade-offs)

* **起案变重**：多一步澄清（预计 +5~10 分钟/案）——但消除的是「拍板错方向后整案返工」的高频大税；分档保证轻案只有 §0 ≤3 行（复述 + 分档判定 + 两问），不被仪式拖累。
* **模板变长**：`TEMPLATE.md` **+≥40 行（89 → ~130 行，约 45% 增量）**——这是本次的明确代价。锚面实查：`docs/map` 与行数锚对 `proposals/TEMPLATE.md` **零命中**；但 `proposals/PLAN-20261108-01-closeout.md:40,46,61,217` 以 `TEMPLATE.md:88` 直接引用「三态结论」行，加节后该行号失效——**按当时快照理解，本次不回补**（PLAN 本身明令不追改）。
* **零业务上下文纪律的边界**：§0 允许业务语境（澄清需要），但 §1 起仍严格执行零业务上下文——§0 明示「本节内容不入契约正文、不进装配面」。**执行点**：`.github/pull_request_template.md` 引用的是 `proposals/` 路径而非正文，粘贴 §0 片段进 PR 描述即可能把业务语境带上 PR 面 ⇒ 模板 §0 内写明「PR 描述只引提案路径，不粘贴澄清正文」。
* **存量在途提案**：不溯及（在途提案按旧模板完成；新起案适用 §0）。
