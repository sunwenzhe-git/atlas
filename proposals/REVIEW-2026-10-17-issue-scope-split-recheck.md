### MUST-2 的两反例（判据仍非唯一）

§2.1 只给 A1/A2 两格；§2.2 又引入「接口面」这一**第三类**，却只说「归属仍是 A」——没落 A1 还是 A2。于是：

**反例①（接口面无子档）**：一条缺陷**只在 atlas 与项目的交接面成立**（任一侧单独看都不错，`RFC…-02.md:55` 定义）。v2 说它「归属仍是 A」，但 §2.1 档位表里没有「接口面」这一格，执行者/校验器仍要在 A1 / A2 之间二选一，而 RFC 没给规则 ⇒ **同一新问题两种落档**。（#27 即此类，v2 自己把它判 A2，但 §2.2 只说它是「接口面」，两处口径未打通。）

**反例②（A1 ∧ A2 共现，以 #26 自身为模板）**：`#26` 的两面同时成立——契约三态装不下验证码+cookie（**A2 装不下**）；而 `validate_stack_profile` 的 WARN「请声明」与「给出路」的意图不符（**A1 判错**）。D103 的实际修法恰是 A1 型：把 WARN 由「请声明」改为「给出路」+ 变异 M93（`DESIGN.md:572` ②、`duty-review/QUEUE.md:10` 生效面），而形态集合则**不动**（「三态之外不设第四态」）。即 #26 = A1+A2 双面，v2 §3（`:73` 邻近行 `:76`）却只标 **A2**。⇒ 同一案既可判 A1 也可判 A2，判别子不唯一。

结论：A1/A2 判别子比 v1 的「看有没有决策行」前进了一步（是先验的、且补上了「未处置缺口」），但**未闭合**——接口面缺子档、A1/A2 可共现。建议在 §2.1 里明确「接口面 ⇒ A1 还是 A2」的判法，并给「判错与装不下同时成立」时取哪个为主。

## 二、新判据的副作用

1. **「项目侧事实永不入库」会不会让真正的接口面缺陷无处登记？——方向对，但没兜住。**
   §2.2（`RFC…-02.md:52-57`）的「双向指名 + 接口面」是**必要的**：库内行写「项目侧事实见 `<项目件>`」、项目件回指「atlas 侧 = `<编号 / D 行>`」，能把事实与缺陷解耦又保持可追。但它**没有回答接口面缺陷落 A1 还是 A2**（= 上文反例①），所以「无处登记」的风险从「没有类别」变成「有类别但无子档」——登记者照样卡在二选一。且 §2.1 要求条目必带 `file:line`，接口面缺陷的 `file:line` 落在 atlas 侧哪一行，也未指引。
   ⇒ 判：**不够**，需补「接口面子档 + file:line 来源」。

2. **出库两类与 `duty-review/README.md` §4 是否逐字对齐？——基本对齐，漏四字，无第三类。**
   README §4 原文：机器面（文本 / 解析 / 门）= 全量测试绿 + 变异即红还原一致即算确认；运行面 = 「下一轮真跑**或等价实测**复验通过才算确认」。
   v2 §2.3（`RFC…-02.md:59-62`）把这两类拆得与 README 一致，且 `#24/#25 ⇒ 机器面当场出库`、`#28/#29 ⇒ 运行面保留至复验`（`:68-71`）与我上一轮 SHOULD #1 的建议一致 ⇒ 方向**已采纳**。
   **唯一偏差**：v2 写「运行面 … 下一轮真跑复验通过」，**漏了 README 的「或等价实测」** ⇒ 把运行面出库**收窄**了。属 SHOULD 级口径漂移。
   **第三类**：README §4 只分机器面 / 运行面两类，v2 与之对齐，**没有漏第三类**（#26/#27 均能归入机器面并用 M93/MB1–MB3 确认）。
