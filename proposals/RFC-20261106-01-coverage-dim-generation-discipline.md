# E2E 覆盖维度生成纪律三件套：§6.1 逐维自检提示 + apply 第 4 列默认声明 + 数据构造检查单（只写设计，不含代码）

> 提案编号：RFC-20261106-01  
> 提案作者：agent_learning（Atlas 维护者会话，2026-11-06）  
> 关联状态：已定案 (Accepted)——2026-11-06 用户拍板实施；v2 采评审必修项（评审记录见同目录 `REVIEW-20261106-01-coverage-dim-generation-discipline.md`）；同批落地，实施记录见 §8  
> 影响范围：环契约 (rings/e2e) | 编排契约 (apply) | 设计决策 (DESIGN.md D184) | 测试防线 (tests)

**一句话**：生成端只按 AC 样例类型展开、对账门默认哑火 ⇒ 用例长期偏科正常流。本批在**既有闭集与既有门**之间补一条「生成纪律」通道——全部提示级 / 流程级，零新门、零新字段、零校验器改动；先实测缺口数，再议是否棘轮。

---

## 1. 现象与取证 (The Problem & Evidence)

### 1.1 触发形态（抽象）

* **规则 / 环节**：apply → e2e 环落用例（`rings/e2e/reference.md` §6.1「从 AC 到用例」）；对账面 = §8.2「AC × 覆盖维度」门（`validate_e2e_index`）。
* **触发时机**：每次需求增量落用例时；每次 `atlas check` 时。
* **具体行为**：生成指令只按 AC 样例类型（正向→`acceptance`、反向/异常→`exception`、边界→按性质、权限→`permission`）展开，**展开的广度完全继承 PRD 侧 AC 的样例形态**——AC 大多为正向 GWT 时，用例同步偏科正常流，无任何一层有广度下限。

### 1.2 契约行证据（仓内实况，非推测）

成因是**三层叠加**，每层单独看都合理，合起来把「异常/边界类用例必须有」变成无人承载：

1. **生成端无广度要求**（`rings/e2e/reference.md:453`）：「用例设计法（等价类 / 边界值 / 决策表 / 状态转移 / 错误推测）作为**生成提示**，不落字段」——设计法被合法化为提示，但提示里**没有**逐维检查的硬性动作，实践中退化为「想到才写」。
2. **PRD 侧义务已降级**（`rings/prd/reference.md:203`，`3509 §B74`）：「本环不再逐 AC 标注，也不再要求『每个关键功能至少覆盖四类』（该义务属**语义项**，人工维度 = §8 审查维度 4）」——机器化的尝试有过教训（§7 原参数 5 Waste Test 是恒 PASS 空门，「一道永远绿的门比没有门更坏」），降级本身有依据，**本 RFC 不翻案**；但降级后语义项在独立审查里从未被稳定执行过（无留痕、无统计）。
3. **对账门默认哑火**（`rings/e2e/reference.md:336`、`:615`）：`覆盖维度` 字段与「AC × 覆盖维度」门（D130/D153 闭集 `C01`–`C14`）形态完备，但第 4 列「适用覆盖维度」**可选声明**——缺列 ⇒ 按 N/A 兜底「不报假缺口」；命中缺口也先 WARN。存量项目不声明，机器面整条不咬合。

外部实证：存量试跑项目（外部仓库，2026-10-17 收口 11/11 全绿基线，共 11 条用例）以正常流为主，异常/边界/权限类用例缺失是维护者确认的现状（2026-11-06 维护者原话口径：「冒烟是有的，其它类型的用例生成肯定不全」）。

### 1.3 外部触发源与本 RFC 的关系

一篇外部测试技能体系文章（2026-11-06 评估，18 个测试 Skill 全景）在生成端立了「广度纪律」：五大维度全覆盖、风险场景数量下限、按 P0–P2 标优先级。**本 RFC 只吸收其「生成端广度纪律」的思想，不引入其实现形态**（角色文件规则库 / 自动修复补丁 / 自然语言执行面与 Atlas 契约 + 确定性生成物哲学冲突，评估结论留档会话，不在本 RFC 展开）。

### 1.4 本 RFC 明确不翻案的

* 不恢复「每个关键功能至少覆盖四类」硬口径（降级依据 `3509 §B74` + 恒 PASS 空门教训仍然有效）；
* 不动「AC × 覆盖维度」门的判定与级别（含 `RFC-20261103-08` 表头校验 M174、`RFC-20261105-01` 未采信表诊断）；
* WARN→FAIL 棘轮与义务回归**留待实测后另案**（见 §4 实测判据的升级出口）。

## 2. 决策与权衡 (The Decision & Trade-offs)

### 2.1 核心定案（三件一批，全部提示级 / 流程级）

**改动点 ①：§6.1 新增「逐维自检」生成提示块**

插入位置：`rings/e2e/reference.md` §6.1，紧接「用例设计法…生成提示，不落字段」行（当前 `:453`）之后。**落地时逐字实现**：

```markdown
- **逐维自检（生成提示，2026-11-06 补，`DESIGN.md` D184；`RFC-20261106-01`）**：每条 AC 展开用例前，按 §5.2 `覆盖维度` 闭集（`C01`–`C14`，定义以 §5.2 为准，本表只给生成期自答问题）**逐维过一遍下表**；命中的维度必须落用例（可并入既有用例的 `覆盖维度:` 列），其余维度无须逐条留痕，但**不得未经逐维过表就直接只产 `acceptance`**。**「界面不可表达 ⇒ 记缺口，不硬造」的结论有唯一落点 = 域级 PRD §六 Assumptions & Defaults 一行**（纯人读、零机器面；**不得**挂「不可验 AC 清单」——那会改 AC 反向覆盖门的豁免面）。本条是生成纪律（提示），不是门；对账仍由 §8.2「AC × 覆盖维度」门承担（声明侧默认动作见 `apply/reference.md` §5）。

  | 维度 | 展开时自答（命中即落用例） |
  |---|---|
  | `C01` 正常流 | 该 AC 的主成功路径是否已有用例？ |
  | `C02` 异常流 | `Then` 的失败分支（服务拒绝 / 校验失败 / 请求报错）是否落了 `exception`？ |
  | `C03` 边界值 | 是否存在数值 / 长度 / 容量 / 数量上下限？上下界各一条 |
  | `C04` 权限约束 | 无权限 / 低角色访问同一入口是否有 `permission` 用例？ |
  | `C05` 并发竞争 | 双端同时改同一对象是否可从界面表达？（不可表达 ⇒ 记缺口，不硬造） |
  | `C06` 失败重试 | 失败后重试路径是否可从界面到达？ |
  | `C07` 审计埋点 | 该操作声称的留痕在界面是否可观测？ |
  | `C08` 会话恢复 | 刷新 / 重进后状态是否保持？（§5.5 `会话:` / `参数:` 通道适用性一并自答） |
  | `C09` 数据一致性 | 列表 ↔ 详情 / 双视图是否同源一致？ |
  | `C10` 依赖容错 | 依赖接口失败时的降级表现是否可测（§5.8 `mock:` 适用性一并自答）？ |
  | `C11` 操作幂等 | 重复提交 / 二次点击是否有防御或幂等语义？ |
  | `C12` 输入校验 | 非法类型 / 空值 / 超长 / 非法字符是否有 `exception` 用例承接？ |
  | `C13` 状态转换 | 对象全生命周期态是否都有用例触达（状态转移法）？ |
  | `C14` 安全防护 | 注入 / 越权值在输入面的防御是否可见？ |
```

**改动点 ②：§6.1 新增「数据构造」生成提示（同块续接）**

```markdown
- **数据构造（生成提示，同批 `RFC-20261106-01`）**：`C03` / `C12` 类用例必须在生成期给出**具体值**，不得留待运行时现想：边界类至少含「最小合法 / 最大合法 / 越界各一」；异常类至少含「空缺 / 非法类型 / 超长 / 非法字符」中适用于该输入面的子集；具体值写在 `step` 的输入动作里，**不新增字段**。**料不足 ⇒ 先回 prd 环补六件套（`rings/prd/reference.md` §4），不得自造预期文案。**
```

**改动点 ③：apply §5 新增「第 4 列默认声明」流程义务**

插入位置：`apply/reference.md` §5「覆盖语义与用户确认门」清单（当前 `:185` 起）之后、§5.1 之前。**落地时逐字实现**：

```markdown
**PRD AC 表第 4 列默认声明（apply 默认动作，2026-11-06 补，`DESIGN.md` D184；`RFC-20261106-01`）**：凡 apply 落笔**新增或修订**域级 PRD 验收标准表的 AC 行（表形态见 `rings/prd/reference.md` §4），逐行声明第 4 列——表头**逐字**为「适用覆盖维度」（`RFC-20261103-08` 判据），值域 = E2E 通道闭集 `C01`–`C14`（`rings/e2e/reference.md` §5.2）。声明口径 = 该 AC **适用**的维度（逐行过 §6.1 逐维自检表），不是「已覆盖」维度；无异常面的 AC 允许单值 `C01`。**落笔目标表的表头若不符逐字判据（或前三列非 canonical），须同批校正表头**（属本次受影响面内动作）——校正后方可行级声明，否则整表按未采信 N/A（`RFC-20261105-01`），逐行声明对账无效且静默。**通道分流：界面不可表达的服务端维度（典型：`C09`/`C10`/`C11` 的服务端形态）走后端列「后端适用覆盖维度」（D153），第 4 列只声明界面可表达子集**——挤入第 4 列会制造 E2E 永久填不上的结构性 WARN。**adopt 开户轮豁免**：基线 AC 行是当前实然登记断言（非验收承诺），不逐行义务；该域首次需求增量补六件套时一并按验收承诺口径补声明。**只及本次受影响行：不溯及存量行、不整表回填**（回填走 §5.2 `backfill` 裁决通道）。第 5 列「覆盖就绪」（D173）语义不动。该声明是 §8.2「AC × 覆盖维度」门的输入；未声明第 4 列的项目仍按 N/A 兜底，零误报口径不变。
```

### 2.2 考虑过的备选方案及否定理由

* **备选 A：恢复「每个关键功能至少覆盖四类」为机器门**
  * *否定理由*：「关键功能」无机器判据；语义项机器化有恒 PASS 空门前科（PRD §7 原参数 5，2026-09-26 撤）。广度义务的正确机器承载 = 已存在的 `C01`–`C14` 闭集 + 对账门，缺的只是让它们**默认咬合**的流程通道——这正是本批改动点 ③。
* **备选 B：本批同时把对账门 WARN→FAIL**
  * *否定理由*：「先 WARN 后 FAIL」是 D130 既定棘轮，升档前提是实测缺口数与形态（存量表交互 / 覆盖就绪页判定）已知；无实测先升档会产生假阻断，违背该门「不产生假阻断」的设计承诺。升级出口见 §4。
* **备选 C：给「本 AC 无此维度」的判定留痕（新字段或 apply 报告新行）**
  * *否定理由*：新字段触 D99 字段集冻结；「无此维度」无机器判据，强制留痕会诱发未经核实的假明——比不留痕更坏。
* **备选 D：整包引入外部文章的技能形态（testcase-generator 等角色文件规则库）**
  * *否定理由*：其广度思想已被 ①②③ 以契约内方式吸收；其实现形态（自由文本规则库、失败自动修复补丁）与「生成物 = 确定性派生物」「fail-loud 不静默重试」的既有裁决冲突。

### 2.3 必须警惕的刺痛代价与兼容性影响

* **存量项目零破坏**：第 4 列仍可选；存量 AC 行不溯及；`scripts/gen_e2e_scripts.py` 不动 ⇒ 「生成物逐字节零变化」承诺不受扰动（既有钉 `tests/test_gen_e2e_scripts.py` 全绿即证）；无需 `atlas init` / 刷新事实。
* **试跑项目咬合点**：新契约进存量试跑仓库须经 `install.sh --update` 重装配（既有口径：契约改动不溯及已装配副本，咬合点 = 下次 update），实测计划（§4）已把此前置列入。
* **无脚本改动** ⇒ 无执行耗时变化；纯契约文本 + 测试。
* **apply 落笔量略增**：每条新增/修订 AC 行多写第 4 列值（几个词），换取对账门从 N/A 变为可判——本批的核心交换。

## 4. 实测判据（本批的「真验收」，非变异面）

前置：试跑仓库 `install.sh --update` 拉新装配；挑一个有真实 AC 存量的域做一次 `apply` 需求增量。**实测域须含覆盖就绪页**（否则就地标 `覆盖就绪: 是`，D173 口径）——维度门只对覆盖就绪页上的挂靠 AC 生效，全 `实现中` 域会让判据 3 恒 N/A、实测静默空转；无法就绪时台账显式记「门未咬合原因」。

四判据（全部走**既有字段 / 既有门输出 / 人工抽检**，零新增机器面；数字快照按 D154 台账口径留档 `product/reviews/`）：

1. **声明率（含漏写对账）**：本次 apply 触及的 AC 行第 4 列声明率 = 100%——贴「受影响 AC 行数 vs 第 4 列非空行数」grep 对账进台账（混合表漏写行无机器信号，`validate_e2e_index` 对未声明行静默跳过，只能靠此对账兜住）；表头逐字合规，不产生**新增的**「未采信表」诊断（`RFC-20261105-01` detail 通道可复核）；
2. **类型分布**：`e2e-index.md` 索引 `类型` 列（`smoke | acceptance | exception | permission`，§5.2 闭集）前后对照——`exception` / `permission` 从 ≈0 上升为非零；
3. **对账亮灯**：`atlas check` 的「AC × 覆盖维度」行从 `N/A` 变为 `PASS` / `WARN`，WARN 缺口逐条点名（`RFC-20261105-01` 诊断通道输出留档）；
4. **声明广度直方图 + 人工抽检（防声明面与生成面同源自指）**：第 4 列声明值按域统计分布直方图（读既有表，零新字段）留档；**每域人工抽检 ≥3 条**「异常处理 / 字段校验有料」的 AC，核对声明与 §6.1 自检表答案的吻合度——**失配 ≥1 条视同缺口数不降**，参与升级出口判读。理由：判据 3 的 WARN 缺口面被声明面锚定，而声明出自执行生成的同一 agent（偏科生成 ⇒ 偏科声明 ⇒ 缺口面恒窄），无此判据则「填得上」可能被判在零真实广度改善的基线上。

**升级出口（不在本 RFC 内执行）**：若实测后缺口在后续真跑轮次中**填不上**（连续两轮 WARN 缺口数不降，或判据 4 抽检失配），升级议题另开 RFC，候选形态 = 四类义务回归（PRD 侧）或 WARN→FAIL 棘轮（对账门侧）；若缺口**填得上且稳定**，棘轮议题同样另案。本 RFC 不预设结论。
