## 1. 现象与取证 (The Problem & Evidence)

### 1.1 触发形态（抽象）

* **规则 / 环节**：需求起手阶段的会话协作方式——任何需求讨论，含但不限于提案起案（澄清节只管落笔起案前，会话全程无协议承载）。
* **触发时机**：需求刚开始聊（信息最缺、方案未定）。
* **具体行为**：确认与评审循环由用户逐轮承担，用户成为唯一协调中枢，三种症状——①起手问答呈问卷式逐条确认，而不是收敛后的拍板点；②草稿评审逐版串行，每版等一次用户意见；③「需用户拍的事」与「Agent 可自证的事」不做区分，混在同一轮里来回打断。

### 1.2 客观证据 (Evidence)

* **会话陈述（2026-11-14，主观，如实标注）**：用户报告「刚开始聊需求就反复确认反复评审」。
* **评审轮次税（文件实读）**：`RFC-20261026-02`（backend-coverage-dimensions）一天内走 v1→v2→v3→v4→v4.1 **四轮串行单评审**（REVIEW-20261026-02/03/04/05 同主题四份，头部实读确认，全部单人 tech-proposal-reviewer）——每轮都是「评审意见 → 全量重修 → 重派」的人工接力，结构性问题一评审员一轮才浮出。
* **外部产品证据（今日实读，出处见头部）**：Meldwork 的产品定位即是对同一痛点的回应——README 卖点「减少你在 Agent 之间转述、催办和整合结果的工作」；其 Auto Discussion 协议 = 首轮并行独立提案 → 互评收敛、全员同意同一份计划才开工 → 只有缺信息 / 缺权限 / 真取舍三类事升级为人工门（Human Gate）；其并发回复模式 = 同一冻结任务快照、独立作答、按稳定顺序合流。同时其 README 自认边界：「Agent 相互检查不能保证结果正确，重要交付物仍需按实际用途验收」——验收面不在本提案范围，Atlas 契约门不变。
* **仓内对位物审计（实读 2026-11-14）**：`RFC-20261114-05` 已建「§0 起案前澄清」（复述理解 / 访谈式追问 / 必须-建议分档），覆盖**落笔起案前**；但三面无承载——①起手候选面（澄清之后、落笔之前的并行候选与 Agent 侧互评收敛）；②全程打断面（什么才有资格中断用户，执行与评审中同样适用）；③评审派工面（提案评审为单人串行派工，无并行双评与意见合流规则）。

## 2. 决策与权衡 (The Decision & Trade-offs)

### 2.1 核心定案 (The Decision)

* **方案总结**：新增 `proposals/KICKOFF-requirement-protocol.md` 一页协议 + `proposals/README.md` 末尾增两行指针（起手协议 / 评审派工法），把 Meldwork 三机制移植为本仓工作方法文档。**不装 Meldwork、不引入任何新工具、零门零字段零代码。**

**机制一：首轮并行候选 + 一次对齐门（起手面）**

**触发面（零口令）**：本协议是 Agent 的默认起手行为，用户正常说需求即入场，不存在触发口令；Agent 自判启用——需要产出候选方案 / 改动的需求讨论才走（单点事实问答、一句话小改不套仪式）；启用与否经档位声明可见，用户说「直接做 / 别问」即跳过轻档仪式直接干。

1. 原始需求入场后，Agent 第一回复固定三件套：**结构化回读**（目标 / 范围 / 非目标）+ **假设清单**（本该问但按合理默认推进的点，逐条带依据与证伪方式）+ **档位声明**（轻档 / 全档，判据见下）；
2. 候选方案按档位给 1~3 个**不同取舍方向**的独立候选（非同案微调）；全档时 Agent 侧先互评一轮（各挑对方最大风险）再收敛为「推荐 + 备选」；有子 agent 环境时由并行子 agent 独立生成，无则单会话分视角生成并显式声明；
3. **一次对齐门**：用户只答三类事（见机制二），单轮 ≤2 问（沿用 `skills/atlas-grill/SKILL.md` 单轮 1~2 问纪律），按影响排序，其余转假设清单留痕；答完即开工，不再逐条确认。

与 `RFC-20261114-05` 的缝合规则（三条，防两套门打架）：
* **门问题集覆盖 §0 四必须**：对齐门问题除三类判据产出外，必须覆盖 §0 必须类（做什么 / 为谁做 / 关键约束 / 验收口径），缺项按「缺信息」进门——四必须齐备 = 对齐门通过态；
* **起案时刻以 §0 为放行判据**：机制二的「假设推进留痕」不得覆盖 §0 必须类——§0 是无条件起案门槛，机制二三值判据只管非起案的会话全程；
* **不重问**：对齐门的回读与假设清单即 §0 复述理解的输入；落笔时需求未变，§0 直接引用门结论，不二次确认。

**机制二：三类才问人（全程打断面）**

升级判据封闭三值，三类之外一律 Agent 侧按假设推进并留痕（写进假设清单），不打断用户：

* **缺信息**：答案改变方案形态，且 grep / 读码 / 查料不可自证；
* **缺权限**：涉及用户资产、外发、不可逆操作（发版、仓外/生产面/不可逆写盘、删改他人产物；git 可逆的仓内写盘不在此列，见下方关系声明）；
* **真取舍**：≥2 个候选各有实质代价，无人能替用户选。

与既有必问义务的关系（只做增量过滤，不收窄任何已定裁决）：`shared/global-rules.md` §7 四条（覆盖/删除已有产物、改写 `product/stack-profile.yaml`、workflow.md 补丁、跨项目契约变更）**恒为必问，不因三类判据豁免**。既有提问纪律照旧：`skills/atlas-grill/SKILL.md`「事实属于模型，决策属于用户」与 `shared/stack-profile.md:204`「先问人，再问代码」（D 类接口探测的判定顺序，2026-10-15 拍板）。本判据管的是既有义务之外的**全程中断权**，并把「权限」显式立为一类——同向，不构成相反默认。

**机制三：并行双评审派工（评审面）**

* **全档提案**：同一冻结输入（同一提案文件 + 逐字相同的评审指令）派两个互不可见的独立评审（独立性既有锚 = `shared/independent-review.md` §2「先独立得出，再比对」），两份意见按四条规则合流，输出一份合流意见单——消灭「评审员 A 说改 X、评审员 B 说改 Y、用户来回传话」：
  1. **刻度复用**：严重度沿用 `shared/independent-review.md` 既有闭集，不另造；同一问题两评定级不一致时**取高**；
  2. **重合**：同一问题双命中标注「双评命中」；升可信度的前提是两评给出**独立定位 / 独立理由**（同基座模型两次采样盲区相关，仅措辞重合不升档）；
  3. **分歧**：真冲突不做假合流——提案方逐条回应并留痕；回应后仍分歧且影响验收口径（属真取舍）的升级用户裁决，其余**默认从严**（按更严一侧处理）。升级用户仅此一类，不重开传话通道；
  4. **落盘**：两份原始意见按既有 `REVIEW-YYYYMMDD-NN` 编号规则落盘（两列号各自独立递增），合流单引用两份编号；显式选择不落盘时，合流单内必须附双评结论对照表。
* **降级路径**：无并行子 agent 环境时降级单人单评并**显式标注「未双评」**，不伪装双评。
* **轻档维持单人单评**；评审者 / 合流者发现轻档误报（命中全档判据）可当场升档。
* 正交性：`RFC-20261103-05` atlas review 是 CLI 实现审查的**命令编排**入口（单评审流程的一键化；`shared/independent-review.md` §1 实例⑤明文「不扇出，单审查者」），不解决提案层的多评审员并行派工与意见合流；两者叠加使用。

**机制四：意见处置（评审面全程，方案细节 review 与代码 review 通用）**

评审意见回来后的「意见 → 修 → 再评审」接力是同一痛点的下半场——用户被拉去逐条传话、逐条裁决。意见进来按四分法处置，不逐条请示：

1. **自证面直接修**：grep / 读码 / 跑测试可核实的事实问题 → 修完留证（diff / 测试输出），不请示不逐条汇报（对齐 duty-review「缺漏当场修，不请示」与「事实属于模型，决策属于用户」）；
2. **判断面回应留痕**：判断 / 取舍类意见 → 提案方逐一回应（采纳 / 不改＋理由），留痕在意见单 / REVIEW 档，不外溢到会话让用户传话；
3. **真取舍升级一次**：回应后仍分歧且影响验收口径 → 收敛成一个决策点（选项＋代价＋推荐）升级用户，一次问完（≤2 问纪律）；`global-rules.md` §7 四条所在项不受本分拣影响，一律人工；
4. **回评审按派工规则**：批量修复方案先按 1~3 收拢再动工；re-review 按机制三派工（全档双评 / 轻档单评）。

适用面声明：`shared/independent-review.md` 骨架管「意见怎么产生」，本机制管「意见进来之后怎么处置」——叠加不替代，骨架既有判据零改动。意见处置四分法全档通用（它不管派工重量，分档判据只管派工与起手仪式）。

**分档判据（成本闸；客观代理判据，候选成形前即可判）**：**全档 = 任一命中，存疑从严**——①跨 ≥2 个契约面 / 环（跨域）②不可逆（发版、外发、删改他人产物）③触及机器门 / 校验器 / 契约判据；其余为轻档。起手声明初档；候选成形后按实际改动面**可升档**（评审者 / 合流者亦有权升档），降档需用户点头。轻档 = 单候选 + 自评 + 单评审；全档 = 完整协议（多候选 + 互评 + 对齐门）+ 并行双评审。

* **为何这是正解**：三个面同源（用户是确认 / 评审循环的唯一中枢），Meldwork 已把同一组机制产品化验证（README：六 Agent 真跑 9 轮、各参与者交付哈希一致）；移植为方法文档是最轻落位，且不与任何在途件冲突。

### 2.2 考虑过的备选方案及否定理由 (Considered Alternatives)

* **备选 A：装 Meldwork 产品本体**
  * *否定理由*：Electron 桌面编排产品与仓内装配式方法形态不同；其 README 自列「Agent installation does not guarantee a working model connection」（装了 CLI ≠ 能跑，多款认证失败）、「Writable conversations that share a folder are not coordinated」（共享目录跨会话并行写不协调）、安装器「do not verify a pinned digest or signature」；多 Agent 长讨论 token 成倍放大。机制移植即可收益，产品不装。（引文原文摘录如上，防转述腐化。）
* **备选 B：三机制并入 `RFC-20261114-05` 的 §0 节**
  * *否定理由*：§0 是模板节、只管落笔起案前；本协议是会话级全程方法（起手并行候选、全程打断判据、评审派工），承载面不同。且 RFC-05 评审在途待重派，往在途件混入新面会拖重派。
* **备选 C：对齐门并入「深度 4 问」自检**
  * *否定理由*：`RFC-20261114-05` §1.2 已裁决深度 4 问与起案场景错配（其对象是外部技能学习），已定案不重议。
* **备选 D：协议做成机器门（缺协议档 ⇒ 起案拒）**
  * *否定理由*：违反零新门纪律；会话协议质量不可机判（写了协议档 ≠ 走了协议），同 RFC-05 备选 A 理由。

### 2.3 必须警惕的刺痛代价与兼容性影响 (Trade-offs)

* **token 成本**：全档提案面约 2~3×（多候选 / 互评）、评审面 2×（双评）；轻档 ≈ 现状。分档判据本身即成本闸，全档应为少数案。
* **纪律漂移**：无机器门，协议靠起手时显式声明执行；对冲 = 双评审互查协议三件套是否走全 + §4 内容级验收首三案观察，空转回炉。
* **计数棘轮风险**：`proposals/README.md`（现 60 行）与新协议档若被行数锚引用会咬红——落刀时按计数棘轮链核查（docs/map index+html 措辞 / apply.md 行数锚 / gates.md），红了同步回填。实查：docs/map 与 docs/apply.md 对 `proposals/README` 零命中（2026-11-14 grep）。
* **存量在途提案不溯及**；新起案适用。

### 4.1 双评审实跑记录（2026-11-14，机制三首跑）
