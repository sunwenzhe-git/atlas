# REVIEW-2026-10-17 · 路由值形态判据（判接受）独立评审

审查对象：`proposals/RFC-20261017-03-route-value-form.md`（作者推荐：判接受 / 不做）。
结论速览：**「判接受」这个终态我同意，但方案给的核心理由（「真跑 404 ⇒ 元素守卫必红」）不成立，必须替换；B′ 的规范化规则按现文不够，升判时不可直接照抄；升判条件按现文几乎不可触发 = 事实永久关闭，须改措辞。** 这是「结论对、论证错」的一案 —— 若只搬结论、把错误论证写进登记面，会种下一个会被后来者依赖的假安全网。

## 一、判接受的成立性（含反例）

### 1.1 方案的核心论证不成立

方案 §3 案 C 理由② 断言：

> 「该假 PASS **不是假绿**：它只让『写错的路径』通过**文本期**，真跑时 `page.goto` 404 ⇒ 元素守卫 `toHaveCount(1)` 必红」

这条论证把一个**未取证的路由器性质**（「未匹配的尾段 ⇒ 404 ⇒ 目标元素缺席」）当成了**保证**。取证到的事实恰恰相反方向：

- 守卫发射面 `gen_e2e_scripts.py:633-634`：`page.goto(guard_url)` 后 `for (id of ids) expect(getByTestId(id)).toHaveCount(1)`。它红的前提是 **404 后 `testid:` 清单里的 id 全部缺席**。
- 但 `testid:` 清单 = **该页应然清单**（`gen_e2e_scripts.py:419-423`，D95 明写回归 `case.get("testid")`），而 `reference.md:80`（§3.2 实现状态判据）明写「**壳层 testid** 会让一个尚未实现的页被严判」—— 即：**壳层 / 布局层 testid 是页面应然清单的一部分**。404 / NotFound 若落在同一壳布局内渲染，清单里的壳层 id **仍在** ⇒ `toHaveCount(1)` 绿。
- 该应用的路由**已知存在 catch-all 段**：`routes.md` 事实区 `/app/:tab`、`/market/:type`、`/rag/:kbId/:tab?`（可选段）。`routes.tsx:97` 用自定义 `routesMap` 做匹配（`src/entry/main/routes.tsx:94-97`），**其严格性（是否 splat / 是否忽略多余尾段）本轮不可取证**（需读各模块 `index.tsx` 的嵌套声明并真跑，超出本轮只读面）。

⇒ 于是存在两类**真正的假绿**（文本期 PASS + 真跑也 PASS）：

1. **壳层 testid 兜底型**：页面应然清单含壳 / 布局层 id；垃圾尾落到 NotFound，但 NotFound 在壳内渲染 ⇒ 守卫全绿。此型**不依赖路由器是否严格**，只依赖「该页清单里有壳层 id」—— 而 §3.2 已承认壳层 id 存在。
2. **宽匹配路由型**：若应用的详情路由对多余尾段宽匹配（或尾段被当作 `:tab` / `:type` 这类 catch-all 消费），`/console/#/app/<anything>` 之类照常渲染页面，断言目标在场 ⇒ 绿。

**结论**：方案「真跑必红」是**常识补全**，不是取证。判接受本身可以站住（见 §1.3），但**不能**把「真跑兜住」当兜底理由 —— 这正是本机制要抓的缺陷类型。

### 1.2 真跑兜底还有第二重漏洞

即便假定「垃圾尾 ⇒ 404 ⇒ 必红」，兜底也不可靠：

- `reference.md:437` / `shared/gates.md:65`：地址为空**或靶场不可达** ⇒ 真跑门判 **SKIP**（不是红）。
- `reference.md:613`：**`blocked` / `skipped` 用例执行按钮禁用**（服务端同样诚实拒绝）。
- `DESIGN.md` D103 / `reference.md:461-463`：有门但无形态的靶场走「人工会话取出」，**不可复现、CI 上不可用**。
- 本仓近期真跑现场（#28/#29/#30）红因全是**超时 / cwd / 未登录**，不指向「路径多一段」。

⇒ 「真跑会兜住」在**靶场长期不可达 / 用例长期 blocked** 时等价于**不兜**；而真跑红一旦发生，根因排查的第一顺位也不会是「路径形态」（见 §四 Q4）。

### 1.3 但「判接受」这个终态我同意 —— 理由应换成这三条

1. **无现场实例**（全仓仅本行自陈的理论例，`CHANGELOG.md:183`、`:166`）；
2. **前缀命中是契约有意设计**（`reference.md:511` §8.2 原文 + `validate_e2e_index.py:317-318` docstring），收紧前须先动契约；
3. **收紧的代价落在「会误伤合法带参路径」上**，且唯一可行收紧（B′）要引入跨环事实源（§二），成本/风险高于当前收益。

这三条成立 ⇒ 判接受 OK。**必须删掉「真跑 404 必红」这条假理由。**

## 二、B′ 的可行性

### 2.1 模式能否与页面表业务段对上：能，但规范化不能照现文写

- 页面表 `路由` 列实值：`/console/#/app/agent/detail`、`/console/#/market/app/agent`（`product/e2e/e2e-index.md:36-39`）—— **壳前缀 + `#` + 已去参的业务段**；`reference.md:78` 明写「可含 hash 段，壳前缀与 `#` 都属路径形态」。
- structure 事实：`/app/agent/detail/:id`、`/market/app/agent/:id`（`routes.md` 事实区）—— **纯业务段模式**。
- 规范化后 `/app/agent/detail/211.../FUZZY` 对模式 `/app/agent/detail/:id` 无匹配 ⇒ 红；`/app/agent/detail/211...` 命中 ⇒ 绿。**机制上可行。**

### 2.2 但方案的规范化规则不够（三处）

- **壳前缀来源错**：方案说「取 `e2e.app_base_url` 的 path（如 `/console/`）」。该值**带 query**（`stack-profile.yaml:54`：`http://localhost:2000/console/?switchAgent=7202`），且 `ATLAS_BASE_URL` **只覆盖 host、不覆盖 base 的 query**（`_support/url_merge.py:18`、`reference.md:468`）—— 从它取 path 要多剥一层 query，脆。**更稳的来源是页面表 `路由` 自己**：在 `#` 处切分即得壳前缀（`/console/`）+ 业务段，零外部依赖。方案舍近求远。
- **`#` 与 `.atlas-case` 注释语义**：`/console/#/app/...` 里 `#` 必须紧邻 `/` 才不被当注释（`reference.md:78`）—— 规范化必须**先剥注释再切 `#`**，方案未写清顺序。
- **多应用 / 未实现行**：structure 事实按「应用 + 页面/路由」组织，含 `实现状态`（`/upload-demo` = 未实现、`/component` = 部分）；`/spark-flow` 无独立路由。哪些行该参与匹配、`:param?` 可选段与 `*` splat 怎么算，方案未定。

### 2.3 更根本的问题：B′ 引入第二个路由真相源，与既有单源原则相抵

`reference.md:470` 明写「**页面 URL = 页面表，唯一来源，不从文件系统派生**（E1）」，而 `DESIGN.md` D90（`:559`）记录过「一个字段被两种相反语义消费」的教训、D86/D99 记录「第二真相源」的教训。B′ 让 e2e 环路由门去读 structure 环事实，是把 `路由` 列的权威**分给两个环** —— 这正是方案自己列的风险③「事实漂移 ⇒ 假红」。**所以升判时，B′ 的事实源与规范化必须先收敛成「页面表路由自派生 + structure 仅作 `:param` 段数佐证」的形态，才谈得上落地。**

**B′ 可行性结论**：方向可作升判首选，但**现文的规范化规则不足以直接照抄**，且需先解掉「跨环第二真相源」这一原则冲突。

## 三、第四案 / 我的建议

### 3.1 第四案 D′：同环实例段数上界（可比 C 贵一点、比 B′ 便宜）

- **判据**：对每条页面表路由 `R`，在**同仓 e2e 环**（页面表 + 各分片的 `goto:` / `守卫:` 值）里收集规范化后以 `R` 为前缀的**已存在实例**，取其**最大段数** Nₘₐₓ 作为该路由的实例上界；新出现的 `goto:` / `守卫:` 路径规范化后段数 > Nₘₐₓ ⇒ **WARN（不 FAIL）**。
  - 现场即：`守卫: /console/#/market/app/agent/211...`（`product/e2e/cases/market-app-agent.md:24`）业务段数 = 3；`/console/#/market/app/agent/211.../FUZZY` = 4 > 3 ⇒ 命中。
- **优点**：事实源 = **同环已存实例**（零跨环、零契约增量、零字符白名单）；`WARN` 级不动既有判定。
- **误伤场景**：① 某路由**只有一条**实例且它就是最长合法形态时，新用例引入合法的新参数量（如从 `/x/:id` 扩到 `/x/:id/:tab`）⇒ 假 WARN；② 仓内该路由**无任何实例**（新页首写）⇒ 判据空转。
- **我的表态**：**不建议做**。收益只覆盖「已有更长实例的页面」，且 WARN 级不足以在文本期挡住真垃圾尾；它的存在价值仅在「比 C 多做一点、不引入 B′ 的风险」。若维护者要「比 C 多做一点」，D′ 是唯一低风险选项，但**我不为它背书**。

### 3.2 我的建议（与作者终态一致，理由不同）

1. **判接受**（同意作者），但把理由换成 §1.3 三条，删掉「真跑必红」。
2. **B′ 记为升判首选方向可以，但注明「不可照现文规则落地」**：须先解两件事 ——（a）壳前缀从**页面表路由自派生**而非 `app_base_url`；（b）「跨环第二真相源」与 `reference.md:470` 单源原则的对账方案。
3. **升判条件改写为「维护者口径」**（见 §四 Q4）。
4. **不做案 A**（同意方案 §3）。

## 四、逐条回答方案 §5

**Q1「真跑可发现」是否足以判接受？**
**不足以**。真跑可发现性是**弱兜底**（SKIP / blocked / 人工会话不可复现，§1.2），且「真跑 404 必红」本身有反例（§1.1）。**判接受仍然成立，但依据是 §1.3 三条，不是这一条。** 这一条若留在登记面会被下次巡检当作「已兜住」而不加处置。

**Q2 B′ 规范化够不够？壳前缀取 `app_base_url` 的 path 可靠吗？**
**不够。不可靠。** 该值带 query 且 `ATLAS_BASE_URL` 只覆盖 host（`url_merge.py:18`、`reference.md:468`）⇒ 从它取 path 需多剥一层。**应改从页面表路由在 `#` 处自派生**（`e2e-index.md:36-39` 的 `/console/#/...`）。另需补：剥注释先于切 `#`、多应用与未实现行取舍、`:param?` / `*` 语义。

**Q3 有没有第四案？**
有，**D′（同环实例段数上界，§3.1）**，判据与误伤如上。**但我建议不做**：误伤面虽可控（WARN 级），收益面太窄（仅覆盖已有更长实例的页），不足以抵一条新门的维护成本。

**Q4 升判条件的可操作性 —— 能不能真的触发？**
**按现文几乎不能触发**，等于「判接受」被包装成了「等实例自动升判」，实质是**永久关闭**。三个阻断点（均为取证过的机制，非臆测）：
- 真跑门在地址空 / 靶场不可达时 **SKIP**（`reference.md:437`），不产生任何「实例」；
- `blocked` / `skipped` 用例**执行按钮禁用**（`reference.md:613`）；
- 系统**不回写「根因」字段**，「文本期 PASS ∧ 真跑红 ∧ 根因=垃圾尾」这一对事实**没有任何落盘位置**；而真跑红的根因排查第一顺位是 testid / 超时 / 未登录（本仓 #28/#29/#30 全是），不会指向「路径多一段」。

⇒ 应把「等 ≥1 条现场实例 ⇒ 转 DR4」改成**维护者口径**（见 Q5 措辞）：**默认不收紧；仅当维护者另行拍板才立项**。把「自动升判」的假象去掉。

**Q5 登记面措辞（可直接抄）**

> **§D94 ③（追记 · 判接受，非待办）**：前缀命中的「合法前缀 + 垃圾尾」假 PASS 通道，经独立评审**判接受**——① 无现场实例（全仓仅本行自陈的理论例）；② 前缀命中是 `rings/e2e/reference.md` §8.2 **契约有意设计**（带参页面友好），单独收紧会误伤合法带参路径；③ 唯一可行的收紧（structure 事实派生值形态）会引入**跨环第二真相源**并需重写规范化规则，成本/风险高于收益。**本项登记为「已知边界（明示接受）」，不是未修缺陷 —— 下次巡检不得重报。** 不做案 A（字符白名单）。**升判口径（维护者，非自动）**：仅当维护者拍板，按「页面表路由自派生壳前缀 + structure 事实仅作 `:param` 段数佐证」的形态立项；**不设**「出现实例即自动升判」。
