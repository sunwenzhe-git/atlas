# REVIEW-2026-10-17 · 缺陷登记边界方案（RFC-20261017-02）独立评审

## 一、判据：能不能给一条新问题唯一裁定 —— **不能**

A/B/C 三档在「缺陷本体在 atlas 的哪份文件」这一维上是自洽的，但一旦碰到下面两种情形就分裂：

**反例①（同构异判，A 与 B 的边界未定义）—— `#28` vs `#30`**
两案的触发面都是**项目属性**：
- `#28`：触发面 = 项目首屏 14,184ms（dev bundle 13.8MB，`bugs.md:15`）—— 按 B 档定义「构建产物 / 环境」正落在 B；方案判它**纯 A**（RFC:39），纳入「默认值不足」族。
- `#30`：触发面 = 项目页面表列了页级路由（RFC:14）—— 方案判 **A+B**（RFC:43）。

同一结构位置（触发面=项目属性），一次判纯 A、一次拆 A+B，判据没有给「触发面算不算 B 档」的定义 ⇒ 对一条新问题**不唯一**。这不是措辞瑕疵：它直接决定该条要不要在项目件里开一行。

**反例②（三档都不沾）—— 未处置的契约形态缺口**
- A 档 locus 明确包含 `rings/*/reference.md / shared/*.md`（RFC:29），而 C 档的载体「契约的形态集合」也在 `rings/shared`（RFC:30）⇒ **一条契约形态缺口按文件位置既满足 A 也满足 C**，区分它们只靠 C 的附加条件「**且已有决策行处置**」——这是**事后属性**，不是问题自身的属性。
- 于是当一条契约形态缺口**尚未处置**时：#26 的原始态正是「开放·缺口上报」（`bugs.md:19`）——A（不是缺陷本体）、B（不是项目侧）、C（还没有决策行）**三档都不沾**。

**缺口**：A 与 C 需要一条**先验**判别子（「本体是**判错**还是**装不下**」——判错=缺陷，装不下=能力/形态边界），而不是用「有没有决策行」来分。否则「缺口待处置」这一整个状态在库里没有落点，而这恰好是最需要登记的状态。

## 四、我不同意但你有权不理

1. **决策点①（已修 A 档出不出库）：同意方向，不同意默认值**。README §4 分两类：**机器面**（文本/解析/门）=「全量测试绿 + 变异即红」即算确认 ⇒ **当场出库**；**运行面** =「下一轮真跑复验」才确认。据此：`#24`（判据，M88–M90、全量绿）、`#25`（解析，M92、全量绿）**已满足当场出库**，方案默认「保留到下一轮」对这两条**与 README §4 相抵**；`#28`/`#29`（真跑现场驱动）归运行面，保留到复验才成立。建议按机器面/运行面**分开判**，而不是四案一刀。
2. **决策点④（#30 的 v2 半）与第二节复核同源**：一旦 `#30` 判**纯 A**，所谓「v2 半」就不是**缺陷半**，而是「项目是否给该页基线声明 `守卫:`/豁免」的**资产选择题**——它是项目件该写、但不是缺陷。方案把它当缺陷半会继续误归因。
3. **决策点②（#26 彻底不入库 vs 入库一行即出库）**：两者**终态几乎相同**（都只剩一行锚）。但语义上应说「**曾入库、已出库**」而非「本不入库」——后者会侵蚀 C 档与「已处置出库」的区别（见第二节 #26 行）。
4. **决策点③（GitHub issue 同步）**：`gh` 本机不可用、本仓 issue=库文件，我视为**超出本 RFC 范围**，不表态。
