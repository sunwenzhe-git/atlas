## 0. 一句话

PRD 从「用例清单的上游」退回「产品应然的声明面」：只写**正向行为**与**必须由产品拍板的分叉点**；E2E 从「AC 的翻译器」改为「正向条目的派生器」，用**覆盖矩阵 + 派生来源标注**证明展开了哪些面。机械 UI 默认既不进 PRD，也不进 AC。

## 1. 问题

### 1.1 现场（用户提供，非本文取证）

跨网同步记录页的 PRD 一度写成 0.1.7：**21 条规则 / 39 条 AC**。其中大量条目是 UI 操作手册，而不是产品承诺：

- 每页条数只给 `10 / 20 / 50 / 100`；
- 页码输入越界夹取；
- 条件变化回第一页但保留条数。

由这种 PRD 生成的 E2E，颗粒度退化为「点一下类型下拉看一眼」；用户随后指出「测一个系统，考虑的不应该完善点吗」。PRD 补细后，用例数量上去了，但补的是控件行为，不是业务面。

> 现状 0.2.0 已收敛为 5 条规则 / 6 条验收断言（`AC-SYNC-001`–`006`），这说明项目侧能靠人纠偏；但**契约仍然允许并事实上鼓励** 0.1.7 的写法，下一次换人或换项目会复发。

### 1.2 两个退化，根因是同一处断链

| 退化 | 表现 | 直接诱因 |
|---|---|---|
| PRD 膨胀成操作手册 | 为了让测试「有依据」，把每个控件默认值、边界处理、交互惯例都写成规则 + AC | 「每条规则必须有 AC」「每个功能必须有 AC」是硬门；**加覆盖的唯一合法动作 = 加 AC** |
| E2E 把实现当需求 | 结论不唯一时，去读代码 / 跑一遍现网，把观察到的行为写成断言 | 「预期只能来自 AC」「每条用例必须回指 AC」是硬禁令；**没有 AC 时，测试没有合法预期来源** |

### 1.3 契约证据（现状）

- `rings/prd/reference.md` §6「双向追溯（硬约束）」：每条规则**必须**至少有一条 AC；每个功能**必须**至少有一条 AC（经「功能 → 规则 → AC」传递）。机器落点 = `validate_prd.py` 参数 4。
- `templates/prd/domain.md` §四 / §五：规则表与 AC 表是唯一登记面，注释再次强调「每条规则 ≥1 条 AC；每个功能 ≥1 条 AC」。
- `rings/e2e/reference.md` §2 禁令 1 / 3：预期只能来自 AC；每条用例必须回指一个 AC。
- `rings/e2e/reference.md` §6.1：`关联AC` 必须能从该 AC 的 `Then` 读出；读不出就「先补 PRD 的 AC」。
- `rings/e2e/reference.md` §8.2 / §12.2 D7：AC 反向覆盖、`Then` 可读性，均以 AC 为唯一锚。

**结论**：现行契约没有位置表达「一句正向描述 + 由测试自行展开的覆盖」。当结论唯一时，PRD 被迫把展开结果写死；当结论不唯一时，测试被迫去实现里找答案。两者都不是人的失误，是契约缺了一层。

## 2. 职责划分（核心主张）

| 关注点 | PRD（prd 环） | E2E（e2e 环） |
|---|---|---|
| 产品要什么 | 正向行为陈述 + 业务值域 + 产品承诺文案 | 只消费，不定义 |
| 两种实现都合理时选哪种 | **分叉点登记 + 选定结论 + AC** | 只消费选定结论，不替产品选 |
| 一句正向描述能推出哪些用例 | 不写 | **派生覆盖矩阵**（枚举 / 组合 / 边界 / 空态 / 异常 / 状态 / 持久化 / 权限 / 幂等） |
| 控件默认值、分页夹取、loading、toast 时长 | 不写（除产品明确承诺） | 不作为断言；确需验证时只断言结构不变量（存在 / 变化 / 清空），不断言具体取值 |
| 预期从哪里来 | — | 正向条目（`R-*`）或分叉 AC（`AC-*`）；**不得来自 structure/current/legacy、运行观察或源码** |
| 推导不出来怎么办 | 接收回填，补正向条目或登记分叉点 | **停手并回填**，不得猜、不得读实现 |

一句话：**PRD 负责「说什么」，E2E 负责「推什么」；两者之间用「可派生边界」切开。**

## 3. 新契约条文

### 3.1 正向条目（`R-*` 的新语义）

**定义**：一条正向条目是一句**全称可观察行为陈述**——「在什么条件下，用户/系统必然看到什么」，且对值域内所有取值只有一种结论。

**写什么**

- 用户目标与可观察结果（谁、在什么入口、完成什么、看到什么）。
- 业务值域（类型、状态、角色、业务约束）——仅当它是**产品事实**，不是控件实现。
- 业务状态与流转（不是 loading / hover 这类 UI 状态）。
- 产品明确承诺的文案、默认值、上限（品牌 / 合规 / 性能约束）。
- 非功能承诺（审计、权限模型、性能口径）。

**不写什么（机械条目清单，按「删除」处理）**

- 控件选项集与默认值：每页条数 `10/20/50/100`、下拉默认项、排序默认字段；
- 平台交互惯例：页码越界夹取、切换筛选回第一页、loading / 骨架屏、toast 时长、防抖、重试次数、二次确认样式；
- 可由正向条目演绎出的用例清单（「每种类型都要试」不是规则）；
- 实现细节：字段名、接口、表结构、组件、列宽 / 列序 / 图标；
- 无业务含义的任意数值边界（除非它来自业务约束或外部系统契约）。

> 判定口径：机械条目的特征是「**换一个同形态系统也这么写**」。它描述的是平台惯例，不是本产品的选择。若本产品**确实要偏离惯例**，那不是机械条目，而是一个分叉点（见 3.2）。

**颗粒度**

- 一句 = 一个可观察行为；不要把一句话拆成「每个控件一行」；
- 不要把互不相关的行为合并成一句；
- 值域只声明**产品事实**，不声明测试展开结果。

**值域登记（可选列，opt-in）**

规则表末列追加 `值域（可选）`，形态：

```text
类型={租户,项目,需求,任务,缺陷}；结果={成功,失败,部分失败,进行中}
```

- 只有需要机器核对「每个取值是否都被测到」时才写；
- 未声明 ⇒ 该条目的取值覆盖不可机判，按 WARN 记录，不报假缺口；
- 值域不是 AC，不产生「每个取值一条 AC」的义务。

**正反例**

| 条目 | 判定 | 落点 / 理由 |
|---|---|---|
| 可按类型筛选（类型 = 租户 / 项目 / 需求 / 任务 / 缺陷） | 正向 | 类型集合是产品事实；「每种类型都要试」由 E2E 派生 |
| 筛「失败」是否包含「部分失败」 | 分叉点 | 两种实现都符合正向描述，用户看到不同结果 |
| 清空全部筛选条件是否回到第一页 | 分叉点 | 「重置」语义不唯一；与「切换筛选回第一页」不是同一问题 |
| 切换类型筛选后回第一页 | 机械 | 列表通用惯例，不写 |
| 每页条数只给 10 / 20 / 50 / 100 | 机械 | 控件默认值；若产品承诺「默认 20、上限 100」，改写为约束句 |
| 页码输入越界夹取到最后一页 | 机械 | 平台惯例，不写 |
| 进行中批次是否自动刷新 | 分叉点 | 影响用户是否能及时看到终态 |
| 展开的明细翻页后是否保持展开 | 分叉点 | 持久化语义不唯一 |
| 无权限时隐藏入口还是提示无权限 | 分叉点 | 两种都合理，验收结论相反 |
| 列表列宽 / 列序 / 图标 | 机械 / 实现细节 | 不写 |
| 空列表文案 | 产品承诺（若指定）；否则归 §三 文案规范统一 | 不逐条 AC |

### 3.2 分叉点（`DP-*`）

**定义**（三条同时成立才是分叉点）：

1. 同一句正向描述下，存在 ≥2 种实现，**都满足 PRD 且互不违反**；
2. 不同选择产生**用户可观察**的不同结果，且会改变验收判定（测 A 绿、测 B 红）；
3. 无法从已有正向条目、已登记分叉点或跨域统一决策**演绎出唯一答案**。

任一条不成立 ⇒ 不是分叉点：可演绎的是派生义务，平台惯例的是机械条目，审美/实现细节的是不写。

**登记位置**：域级 PRD 末尾追加固定节 `## 九、分叉点登记`（不重排既有章节号）。

**表格形态（机器可判）**

| 分叉点 ID | 议题（问句） | 候选结论（≥2，互斥、可观测） | 选定结论 | 依据 | 影响面 | 状态 | 决定人 / 日期 | 关联 AC |
|---|---|---|---|---|---|---|---|---|
| `DP-<CODE>-001` | 「失败」筛选是否包含「部分失败」？ | A 包含；B 不包含 | A | 用户口径：部分失败仍需处理 | `R-<CODE>-002` / 记录页 | 已决 | 用户 / 2026-11-11 | `AC-<CODE>-003` |

- **状态闭集**：`已决` / `待决` / `已废止`。
- `已决` ⇒ `关联 AC` 必填，且该 AC 必须存在、可判定、`Then` 能读出选定结论。
- `待决` ⇒ 必须同时出现在全局 PRD 的「待决策登记表」；**受影响面的 E2E 用例不得落笔**（阻塞，不是猜）。
- `已废止` ⇒ 必须写替代落点（另一 DP / 正向条目 / 无），不得静默删除。

**颗粒度**

- 一个分叉点 = 一个**语义选择**，不是一次控件操作。
- 候选结论必须写「用户看到什么」，不写「代码怎么做」；候选之间必须互斥且可观测。
- 同一议题跨页面 / 跨域复用 ⇒ 提为跨域统一决策，域内只写「遵循 X」，**不重复登记、不重复 AC**。
- 一个分叉点影响多个观测面时，允许拆多条 AC，但必须逐面给断言；**不得**用一条 AC 概括多个不同观测面。
- 默认一条分叉点对应一条 AC；多于一条时必须在 `依据` 里说明为什么不能合并。

**正反例**

| 议题 | 是否分叉点 | 理由 |
|---|---|---|
| 「失败」是否包含「部分失败」 | 是 | 两种实现都合理，验收相反 |
| 进行中批次是否自动刷新 | 是 | 用户可观察，且无唯一解 |
| 明细展开状态是否跨页保持 | 是 | 持久化语义不唯一 |
| 无权限：隐藏入口 / 提示无权限 | 是 | 验收结论相反 |
| 清空全部条件是否回第一页 | 是 | 「重置」是产品语义，不是通用惯例 |
| 切换筛选回第一页 | 否 | 列表通用惯例（机械） |
| 每页条数选项是 10/20/50/100 | 否 | 控件默认值（机械）；若产品承诺上限，改成约束句 |
| 列表用表格还是卡片 | 否 | 设计/实现选择，不是验收分叉 |

### 3.3 AC 的重新定位

- **AC 的主语义 = 分叉点的可判定断言**，不是用例清单，也不是控件检查表。
- 正向条目**不要求** AC；它通过 E2E 的派生矩阵被覆盖。
- `Then` 仍必须是可判定的确定断言，且不断言实现（现行规则不变）。
- 后端 / 全栈场景的 AC 仍是 `validate_ac_alignment` 的法定输入；分叉点落在后端时，AC 照旧表达状态码 / 字段 / 落盘变化。
- 结构类 AC、不可验 AC 两个清单保留，语义不变。

**AC 分四类（`类别` 列，新写必填）**

| 类别 | 含义 | 关联要求 | E2E 覆盖义务 |
|---|---|---|---|
| `分叉断言` | 分叉点选定结论的可判定断言 | 必须挂 `DP-*` | 有（可进不可验清单） |
| `结构断言` | 页面初始态才能观测的骨架 / 默认面板 | 必须进「结构类 AC 清单」 | 零证据用例挂靠 |
| `后端断言` | 纯后端 / 全栈服务端验收，无界面观测面 | 必须回指 `R-*`，并在「不可验 AC 清单」说明界面不可表达 | 无（`validate_ac_alignment` 管） |
| `派生断言` | **仅迁移期**：本质可派生或机械、但引用尚未清理 | 不得被新用例引用 | 过渡态，见 §7 |

- 每个 `已决` 分叉点必须有 ≥1 条 `分叉断言` AC；每条 `分叉断言` AC 必须挂 ≥1 个分叉点。
- 非 `分叉断言` 的 AC 不要求挂分叉点，但必须有上表的关联要求，杜绝「无主 AC」。
- 迁移期外，新写 AC 不得使用 `派生断言`。

**AC 表列（末列追加，不改前三列次序）**

```text
| AC ID | 场景（Given / When / Then） | 回指规则 | 适用覆盖维度 | 后端适用覆盖维度 | 分叉点 | 类别 |
```

- `回指规则` 保留：仍是「功能 → 规则 → AC」链的前一环，不因新增分叉点而断。
- `分叉点`：`DP-*`；`类别=分叉断言` 时必填，其余类别留 `—`。
- `类别`：`分叉断言` / `结构断言` / `后端断言` / `派生断言`；新写必填。

### 3.4 可派生 / 不可派生边界（硬）

E2E 只能从正向条目派生**结构与状态**，不能派生**产品承诺的具体值**：

| 可派生（允许写进 `expected`） | 不可派生（必须 PRD 明写或登记分叉点） |
|---|---|
| 元素存在 / 不存在、可见 / 不可见 | 具体文案（品牌 / 合规 / 产品指定） |
| 集合成员资格（结果只含匹配项） | 具体数值阈值、默认值、选项集 |
| 计数、分页结构、排序结构 | 两个候选结论之间的选择 |
| 业务状态标志与流转终态 | 错误码、跨模块副作用 |
| 空集 / 无匹配的结构表现 | 时间格式 / 时区 / 精度口径（未在 PRD 声明时） |
| 权限可见性（角色矩阵已由 PRD 给出时） | 任何只能从源码或运行观察得到的行为 |

> 判据：**「如果实现换一种同样合理的做法，这条断言还应不应该成立？」** 答案依赖实现 ⇒ 不可派生，必须回 PRD。

## 4. E2E 侧派生义务

### 4.1 覆盖矩阵（每个断言源一张）

对每个 `R-*`（正向条目）与每个 `分叉断言` AC，在该页分片内维护一张覆盖矩阵。`结构断言` / `后端断言` 不建矩阵：前者由「零证据用例挂结构类 AC」门承接，后者由 `validate_ac_alignment` 承接。

| 覆盖维度 | 是否适用 | 理由（不适用时必填） | 用例 ID |
|---|---|---|---|
| `C01` 正常流 | 是 | — | `E2E-...-001` |
| `C02` 异常流 | 是 | — | `E2E-...-004` |
| `C03` 边界值 | 否 | 该条目无数值 / 容量约束 | — |
| `C15` 枚举展开 | 是 | 值域 5 个类型 | `E2E-...-002` … |
| `C16` 条件组合 | 是 | 类型 × 结果为非正交条件 | `E2E-...-006` |
| `C17` 空态 | 是 | 无匹配 / 无数据 | `E2E-...-003` |
| …（C04–C14 同表） | | | |

- 维度词表沿用 `rings/e2e/reference.md` §5.2 的闭集，**只追加 `C15 枚举展开` / `C16 条件组合` / `C17 空态`**，不重编号、不改 C01–C14 语义。
- 「是否适用」是**人的承诺**：机器只能核对「声明为适用的维度是否有用例」，判不了「这个维度是否真的不适用」。后者归独立审查（见 §5.4）。
- 不适用的维度必须写理由；空白与「评估过为不适用」不得同形（沿用 `global-rules.md` §5 的显式原则）。

### 4.2 派生来源标注

**分片用例块新增必填字段**：

```text
派生: R-<CODE>-002 / C15 / 类型=租户
派生: AC-<CODE>-003 / C01 / 失败包含部分失败
```

- 源 ID ∈ {`R-*`, `AC-*`}；分叉点通过 AC 间接指向（`AC` 行的 `分叉点` 列），不另写 `DP-*`。
- 维度 ∈ `C01`–`C17`；取值 / 场景尽量点名（枚举值、边界值、状态名），便于机器核对。
- 一条用例原则上只有一个主动断言源；确需多源时逐行写，**首个为主源**。
- 索引主表的 `关联AC` 列语义扩为「关联条目」，值域 = `R-*` / `AC-*`。**建议同批更名为 `关联条目`**（列名继续叫 AC 会撒谎），迁移期校验器双读旧表头；若评审认为改名成本过高，退路是保留列名、扩展取值语法并在契约里注明历史包袱。

### 4.3 「没漏面」的证明边界

机器能证明的：

1. 每条用例都有派生来源，且源可达；
2. 每个「声明为适用」的维度至少有一条对应用例；
3. `R-*` 声明的值域里，每个取值至少出现在一条 `派生` 行；
4. 每个用例的维度都在闭集内；
5. `已决` 分叉点有 AC，`待决` 分叉点影响面没有落笔用例。

机器**不能**证明的：矩阵里「不适用」的判断是否正确、维度是否漏列、断言是否真的异源。这三项归独立审查，不得假装是门。

### 4.4 禁止「实现当需求」（强化现行禁令）

- 预期来源只有两类：正向条目 + 分叉 AC。`structure/current|legacy` 只能提供路由、元素存在性、testid 锚点，**不得提供预期值、状态流转或错误文案**。
- 派生不出来时，唯一合法动作是**停手 + 回填 PRD**（`apply backfill`），不得：
  - 跑一遍现网把观察结果写成断言；
  - 读源码 / 接口返回倒推「应该是这样」；
  - 用「实现如此」作为 `intent` 的理由。
- 新增审查维度（§12.2）：
  - **D11 派生合法性**：把 `派生` 行遮住，只看正向条目 / 分叉 AC，能否独立读出该 `expected`；若必须看源码或现网才能得出，判违反。
  - **D12 反事实**：对分叉 AC 问「若实现选了另一个候选结论，这条用例会不会红？」不会红 ⇒ 断言没有咬住分叉点。

## 5. 校验器怎么变

> 原则：只加「结构可判 + 来源可达 + 声明对账」三类；**语义判断不硬造规则**。新增检查先 WARN，跑一轮实测再决定是否升 FAIL（`global-rules.md` §12）。

### 5.1 `validate_prd.py`

| 变更 | 内容 | 级别 | 备注 |
|---|---|---|---|
| **改**（参数 4） | 取消「每条规则必须有 AC 回指」；保留「每条 AC 必须回指规则」「功能 → 规则」链路 | — | 正向条目允许零 AC |
| **增**（独立 check） | 分叉点登记表形态：固定节存在；表头含 9 列；状态 ∈ 闭集；候选结论 ≥2；`已决` ⇒ 关联 AC 非空且可达；`待决` ⇒ 全局待决策登记表有对应行；`已废止` ⇒ 有替代落点 | FAIL（形态）/ WARN（待决缺登记） | 只判形态与可达，不判结论好坏 |
| **增**（独立 check） | `类别` ∈ 四类闭集；`分叉断言` ⇒ `分叉点` 非空且 `DP-*` 可达；`结构断言` ⇒ 在结构类 AC 清单；`后端断言` ⇒ 在不可验 AC 清单且回指 `R-*`；`派生断言` ⇒ 仅迁移期允许且不得被新用例引用 | FAIL（新写 / 修订）；WARN（存量缺列，按 `派生断言` 过渡） | 这是防 AC 膨胀的主门 |
| **增**（独立 check） | `已废止 AC 清单` 自洽：不得与在用 AC 重号；每条有原因与替代落点；被 E2E / 测试引用的废止 AC 必须能在清单中解析 | FAIL | 配合 §7 |
| **增**（WARN） | 规则表声明了 `值域` 时，值域形态可解析（字段=集合，集合非空） | WARN | opt-in |
| **不做** | 「机械条目识别」 | — | **机器判不了**：同样是「每页 20 条」，在 A 产品是惯例、在 B 产品是合规承诺；按词表判会把正常条目打成机械，逼作者改词而不是改内容。不造这条规则 |

### 5.2 `validate_e2e_index.py`

| 变更 | 内容 | 级别 | 备注 |
|---|---|---|---|
| **增** | 每个用例块必须有 `派生:`；源 ID 可达（`R-*` / `AC-*`）；维度 ∈ C01–C17 | FAIL | 与现有 `关联AC` 可达检查同层 |
| **增** | 覆盖矩阵形态：每个 `R-*` 与每个 `分叉断言` AC 至少一张矩阵；每行维度合法；「适用」⇒ 有用例 ID；「不适用」⇒ 理由非空 | FAIL（形态）/ WARN（首轮） | 矩阵由分片内固定块承载；`结构断言` / `后端断言` 不要求矩阵 |
| **增** | 值域覆盖：`R-*` 声明值域的，每个取值至少被一条 `派生` 行点名 | WARN → FAIL | 仅对声明值域的条目生效 |
| **改**（追溯门） | 「AC 反向覆盖」保留，但对象改为 E2E 可观测 AC；新增「正向条目覆盖」：每个 `R-*` 至少有 1 条派生用例、或有任意类别 AC 承接、或矩阵声明该条目无 E2E 观测面（并给理由） | WARN | 防「写了规则没人测」与「规则写了却没人消费」 |
| **增** | `已决` 分叉点的 AC 若无任何用例（且不在不可验清单）⇒ 缺口清单 | WARN | 与 AC 反向覆盖同源 |
| **增** | `待决` 分叉点影响面出现新用例 ⇒ FAIL | FAIL | 阻断式回填，不许猜 |
| **不做** | 判断断言是否「真的从正向条目推出」 | — | 语义项；用 `expected` 与 `Then` 关键词共现做近似已被 §6.1 明确否决（误报高），不重开 |

### 5.3 `validate_ac_alignment.py`

| 变更 | 内容 | 级别 |
|---|---|---|
| **增** | 测试挂载的 AC 若出现在「已废止 AC 清单」⇒ 按「可解析但已废止」处理：不报 dangling，报 WARN 并提示替代落点；一个迁移周期后升 FAIL | WARN → FAIL |

> 目的：AC 收敛不能把后端测试一夜打红；但也不能让废止 AC 永久合法。

### 5.4 明确判不了的（不造规则）

- 一条规则是正向还是机械；
- 一个分叉点该不该登记（是否「真的不唯一」）；
- 覆盖矩阵的「不适用」是否诚实；
- 一条断言是否真的异源 / 是否反事实有效。

这四项全部落到 §8 独立审查与 §12.2 新维度 D11 / D12，不进校验器。**「一道永远绿的门比没有门更坏」（`rings/prd/reference.md` §7 的既有结论）在这里同样适用。**

## 6. 防两种退化的机制

### 6.1 防 PRD 膨胀

| 机制 | 类型 | 作用 |
|---|---|---|
| **`分叉断言` 必须挂分叉点**（§5.1） | 机器门 | 没有分叉点就写不出新的分叉 AC；想加「验收条目」必须先证明存在产品选择 |
| **每条规则必须有消费者**（§5.2 正向条目覆盖） | 机器 WARN | 没有 AC、也没有用例派生、也没有「无 E2E 观测面」理由的规则 = 死条目，暴露出来 |
| **值域 vs 机械条目的写法约束**（§3.1） | 契约 + 审查 | 值域是产品事实；控件默认值不是 |
| **「为什么不能派生」一问** | 审查 | 新增每条规则时回答：它能否由已有条目演绎？能 ⇒ 不写 |
| **体量预算** | 既有 | 沿用 9500 字符拆分线（`rings/prd/reference.md` §9 / `global-rules.md` §12），不新增任意阈值 |

### 6.2 防 E2E 把实现当需求

| 机制 | 类型 | 作用 |
|---|---|---|
| **预期来源二元化**（§3.4） | 契约 | 只有正向条目与分叉 AC 两个合法来源；实现行为被明确排除 |
| **派生来源必填 + 可达**（§5.2） | 机器门 | 每条断言必须能指回一个 PRD 源；指不回就不能交付 |
| **派生矩阵**（§4.1） | 机器 + 审查 | 把「想到才写」变成「逐维表态」；不适用也要留理由 |
| **D11 / D12**（§4.4） | 审查 | 遮住派生行能否读出预期；反事实换一个候选结论用例是否会红 |
| **待决分叉阻断落笔**（§5.2） | 机器门 | 结论未定时不许写用例，从源头消灭「去实现里找答案」 |
| **输入最小化** | 既有强化 | 生成 / 审查只拿 PRD 条目 + 分片 + testid 清单，不拿整份源码（沿用 §12.4） |

## 7. 迁移：0.1.7 这类 PRD 怎么收敛

### 7.1 先分类，再动刀

对每条规则与每条 AC 做一次三分类：

| 类别 | 判据 | 处置 |
|---|---|---|
| **正向** | 全称行为陈述，结论唯一 | 保留 / 合并进 `R-*`；补值域（如有产品事实枚举） |
| **分叉** | 满足 §3.2 三条件 | 新建 `DP-*`；保留或新写 1 条 AC；选定结论写入登记表 |
| **机械** | 平台惯例 / 控件默认值 / 实现细节 | 删除；若产品确实要偏离惯例，改判为分叉 |

AC 侧按 §3.3 四类归位：**分叉断言**保留并补 `DP-*`；**结构断言** / **后端断言**按既有清单归位；剩下「可派生 / 机械」的，先判为**废止**，若仍被引用则暂记 **派生断言** 过渡。

### 7.2 AC 编号处置（建议）

**不重排、不复用、不静默删除。** 三态：

| 态 | 适用 | 做法 |
|---|---|---|
| **保留** | 断言的是分叉点的选定结论 | 编号不变，补 `分叉点` 列；语义不变 |
| **降级** | 已被 E2E / 后端测试引用，但本质是机械或可派生断言，短期无法重挂 | 保留编号与文本，`类别=派生断言`；**不得再被新用例引用**；不计入「分叉 AC」覆盖；下一个需求触碰该域时删除或改挂 |
| **废止** | 无人引用，或纯机械断言 | 从 §五 主表移入 `### 已废止 AC 清单`；编号作废、永不复用；写原因与替代落点（`R-*` / `DP-*` / 无） |

> 推荐默认「废止 + 墓碑」，而不是「保留但降级」。降级只作为**引用未清理完**的过渡态，避免用一个合法状态长期容纳机械条目。

### 7.3 收敛步骤（人执行，按 `apply backfill` 攒批）

1. **抽分叉**：把 AC / 规则里「两种实现都合理」的句子抽出来，逐条登记 `DP-*`；把 0.1.7 已隐含选择的结论写成 `选定结论`，由用户确认（这是用户确认门，不是 agent 代签）。
2. **并正向**：把同一功能的碎规则合并成一句全称陈述；把值域抽成 `值域` 列。
3. **删机械**：按 §3.1 清单删除；删除前检查是否被用例引用。
4. **用例重挂**：把 E2E 的 `关联AC` 逐条改到 `R-*` 或保留的 `AC-*`；给每条用例补 `派生:`；删掉只验证控件默认值的用例。
5. **建矩阵**：为每个 `R-*` 与每个 `分叉断言` AC 建覆盖矩阵，逐维标适用性；不适用的写理由。
6. **跑门**：`validate_prd` / `validate_e2e_index` / `validate_ac_alignment`；先接受 WARN，清零后再谈升 FAIL。

### 7.4 兼容与窗口

- **止损优先**：先禁止新增「无分叉点的分叉断言 AC」与「无派生来源的用例」，存量按「触碰即收敛」处理，不做一次性全量重写。
- **双读窗口**：校验器对旧表头 / 无分叉点节 / 无 `派生` 字段的存量资产按 WARN；新写或修订的条目按 FAIL。
- **schema 位**：若 `RFC-20261111-03` 的 `prd_schema` 落地，本文语义作为下一档 schema；否则沿用域级 PRD `version` 递增并在变更记录里注明「正向 + 分叉」形态。
- **退役登记**：废止 AC 进墓碑表；`validate_ac_alignment` 在窗口期内可解析、只报 WARN。

### 7.5 对 0.1.7 典型条目的处置示例

| 0.1.7 条目 | 新判定 | 处置 |
|---|---|---|
| 每页条数 10/20/50/100 | 机械 | 删除；若产品承诺「默认 20 / 上限 100」，改写为一句约束 |
| 页码输入越界夹取 | 机械 | 删除 |
| 条件变化回第一页但保留条数 | 机械 | 删除（切换回第一页是列表惯例；保留条数是控件行为） |
| 清空全部条件回不回第一页 | 分叉 | 新建 `DP-*` + 1 条 AC |
| 「失败」是否含「部分失败」 | 分叉 | 新建 `DP-*` + 1 条 AC |
| 进行中是否自动刷新 | 分叉 | 新建 `DP-*` + 1 条 AC |
| 明细展开翻页后是否保持 | 分叉 | 新建 `DP-*` + 1 条 AC |
| 无权限隐藏 / 提示 | 分叉 | 新建 `DP-*` + 1 条 AC |
| 可按类型筛选 | 正向 | 合并为一句 + `值域`；由 E2E 派生 5 个类型 × 结果 × 空态 |

> 形态上，21 规则 / 39 AC 预计收敛为个位数的正向条目 + 个位数的分叉点 / AC；其余不是「被删掉的需求」，而是从 PRD 移到 E2E 覆盖矩阵。具体条数以逐条裁决为准，本文不预判。

## 9. 风险与代价

### 9.1 这套分工在什么情况下会失效

| 失效形态 | 机制 | 后果 |
|---|---|---|
| **正向写得太粗** | 一句「可筛选」不带值域、不带约束 | E2E 无法派生，只能回填或猜；回填频繁 ⇒ 预算击穿 |
| **分叉点成垃圾桶** | 把所有不确定都登记为分叉，换取「可以写 AC」 | PRD 重新膨胀，只是换了表 |
| **矩阵表演** | 维度都标「适用」，用例只做冒烟 | 机器全绿，覆盖仍偏科 |
| **声明即覆盖的假信心** | 机器只证明「声明面」，人把绿灯当全覆盖 | 漏掉的维度永远不被发现 |
| **语义审查跟不上** | D11 / D12 需要读 PRD + 用例，审查成本上升 | 审查抽样化，退化回「看格式」 |
| **后端 AC 断裂** | 收敛 AC 时测试挂载悬空 | `validate_ac_alignment` 红，团队为变绿而放宽 |
| **跨仓 / 多仓** | PRD 在父仓，用例在成员仓 | 分叉点登记与矩阵分居两地，追溯链断 |

### 9.2 兜底

- **正向太粗**：E2E 派生失败必须落「阻塞 + 待派生」清单，按 P0 回填；连续回填超预算 ⇒ 登记为流水线缺陷（`global-rules.md` §12），不是测试自行补脑。
- **分叉点膨胀**：给每个域设「分叉点 / 正向条目」比例观测（只报告、不设硬阈值）；比例异常 ⇒ 触发一次 PRD 评审，而不是加门。
- **矩阵表演**：D11 / D12 必须逐条抽样；抽样发现「矩阵适用但用例没咬住」⇒ 整页重审，不只看单条。
- **假信心**：在契约里明写「机器只证明声明面」；审查报告必须列出未机判项，禁止用「门全绿」代替覆盖结论。
- **后端断裂**：墓碑表 + 双读窗口；窗口结束仍悬空 ⇒ FAIL，但在此之前提供替代落点映射。
- **跨仓**：分叉点登记跟随 PRD 所在仓；矩阵跟用例所在仓；两边用同一 `R-*` / `AC-*` 全局唯一编号对齐，不复制正文。

### 9.3 代价与实测前置（`global-rules.md` §12）

- **新增产出**：每个断言源一张矩阵、每条用例一行 `派生`、每个域一张分叉点表。相对 0.1.7 的 39 AC，总量应下降；相对 0.2.0 的 6 AC，E2E 侧产出会上升。
- **新增审查**：D11 / D12 逐条判断，审查宽度上升。
- **前置实测**：先在 1 个域试跑，量三件事——① 正向条目数 / 分叉点数 / 用例数；② 回填次数与阻塞时长；③ 审查每页耗时。任一指标击穿预算 ⇒ 先调矩阵粒度（页级 → 条目级）再谈升 FAIL。
- **不承诺**：本文不预计收益数字；没有实测就不宣称「更省」。

## 10. 待评审的开放问题

1. **AC 降级的幅度**：允许正向条目零 AC 是否过度？替代方案是「每个功能保留 1 条正向 AC」，但会重新引入枚举压力。
2. **索引列改名**：`关联AC` → `关联条目` 的收益是否值得控制台 / 文档 / 测试的联动成本？退路是保留列名、扩展取值。
3. **矩阵粒度**：条目级矩阵更准但更重；页级矩阵更轻但容易表演。是否允许按域选择？
4. **`C15–C17` 是否新增**：也可以把枚举 / 组合 / 空态映射到既有 C01 / C03，但会失去「每选项是否测到」的机器可核对性。
5. **分叉点与走查单的关系**：分叉点是否必须在 §八 用户旅程走查里再确认一次，还是走查单只确认正向流程？
6. **跨域统一决策的落点**：跨页面复用的分叉（如「无权限隐藏还是提示」）登记在全局 PRD 还是某个域的 §九？需要单一真相源。
