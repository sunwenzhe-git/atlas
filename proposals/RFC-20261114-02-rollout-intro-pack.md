## 1. 现象与取证 (The Problem & Evidence)

### 1.1 触发形态（抽象）

* **规则 / 环节**：组织推广场景下 Atlas 的**第一眼呈现物**。仓内已有对外文字，但读者定位都是「已决定自用的人」：`README.md`（安装 + 契约细节）、`docs/guide/how-it-works.md`（对外叙事「破局 Vibe Coding」）、`docs/guide/legacy-adoption.md` §5「依赖与边界（诚实清单）」。**缺的是「5 分钟说服非本团队角色 + 可照做的 30 分钟演示」这一形态**——不是没有对外版本。
* **触发时机**：向组织内其他团队（DevOps 协作流 / 测试工作流角色）介绍 Atlas 时。
* **具体行为**：第一眼看到的是机械面——契约体量（`shared/` **九份共 1477 行**，`wc -l shared/*.md` 实测）+ 专用词汇（棘轮 / 升档 / 装配 / 回灌 / 收口）⇒ 被读成「官僚系统」而不碰；而这与产品真实价值（提测准入门禁 + 冒烟自动化楔子）毫无关系。

### 1.2 客观证据 (Evidence)

- 压头追问（2026-11-13）：用户确认「推广负担」是过重焦虑的两头之一——「别人一看这么重就不碰」。
- 词汇壁垒实证：契约词汇表（棘轮 / 升档 / 装配 / 回灌）在对外语境零解释位；词汇解释文档面向的是已经决定使用的人。
- 组织推广语境（**口头在案，仓内无锚**）：领导推广走「13 节点流程 MVP」的说法来自会话口述，仓内检索不到该口径 ⇒ 提案正文**不把它当可复算数字引用**，只在 §2.1 楔子中作为「领导层按交付物质量与效率考核」的背景一句带过；切入建议 = 提测准入门禁冒烟自动化，不碰流程串联、不碰执行平台。
- 外部数据垫场（**外部引用**，字段化见 §2.1 第 4 件）：2026-11-13 评估的腾讯 OK 平台公开文章——约 85% 团队仍停留在个人编码加速层；测试环节（设计测试策略、判断边界覆盖）被端到端平台列为「人还在做」——正是 Atlas 的空位叙事。

## 2. 决策与权衡 (The Decision & Trade-offs)

### 2.1 核心定案 (The Decision)

* **方案总结**：新增 `docs/guide/rollout-intro.md` 一份对外开场包，四件套结构——
  1. **楔子一页纸**：提测准入门禁 + 冒烟自动化打头（继承既定切入边界：不碰流程串联、不碰执行平台）；Atlas 是什么 / 不是什么各三行；
  2. **30 分钟真实仓演示脚本**：顺序化动作清单（装 → 装配 → 建一条用例 → 跑门 → 拦下一个真实问题），每步标注预期输出与讲解话术。
     * **第 0 步前置清单（逐项勾选，缺失即降级）**：① 靶场可达且**关键 API 实响应**（根路径 200 ≠ 就绪，先 curl 一条真实业务 API）；② 测试环境 profile（`app_base_url` 临时指向测试环境、不提交）；③ 登录态 `state.json` 就绪（从用户 checkout **只读复制**，不覆盖不删除）；④ **stack-profile 的 adapters 至少声明一项**——`adapters` 全 `null` 的仓里 `atlas check` 对 adapter 面出的是 `N/A`/`WARN`，「拦下一个真实问题」这一步演示不出来（预期输出须与「直接做」域逐条对账）。任一项缺 ⇒ 该步改成「只讲预期输出、不实操」，话术随前置清单勾选结果切换，不临场硬演。
     * **隔离口径**：演示在**专用一次性演示仓**或靶场仓的 **detached worktree** 里跑（`git worktree add --detach`，对齐 `docs/guide/real-run-day.md` §0 形态）；**明文排除「演示者正在用的 checkout」**（D148：维护者 checkout 不碰，分支可能被占用）。演示产物留在 worktree，用完即弃。
     * **拦截用例定性**：演示里故意注红的用例，按 `real-run-day.md` §4 注红条款当场声明——「它的 red 是取证动作，不计缺陷判据、不进 `bugs.md`、跑完即删」；讲解话术里必须有这一句，防听众把演示红当成产品缺陷证据。
  3. **支持 / 不支持清单**：四象限形态（直接做 / 风险侧人机协同 / 复杂度侧人机协同 / 暂不支持），按 adopt 域的真实覆盖现状填写；**校准绑发版动作**（每次 beta 发版收口时顺带核对一遍四象限，不设日历提醒、不做「按月回顾」这类无承载物的承诺）。
  4. **数据引用清单**：外部来源数据逐条**字段化**——`来源名 + 日期 + 原句 + 公开可访问性`（例：`腾讯 OK 平台公开文章 / 2026-11-13 / 「约 85% 团队仍停留在个人编码加速层」/ 待补公开链接`），逐条标注「外部引用」性质；自家数字只写可复算的（装配面文件数、门数、判收口径，给出复算命令）。
* **为何这是正解**：对外第一眼的单位是「这东西帮我解决提测准入吗」，不是「它的治理架构多完整」。契约全文降为附录链接，正文不出现棘轮 / 升档 / 回灌等内部词汇（首次出现必须带人话解释）。**单版本拍板约束下，开场包不引入「哪一版」话术——只有一个 Atlas。**
* **与既有三份文档的分工（互链，不合并、不复写）**：
  * `how-it-works.md` = **为什么**（价值叙事，已是公开站的对外正文），`rollout-intro.md` = **怎么开始讲**（楔子 / 演示 / 四象限）——读者与生命周期不同，不合并；`rollout-intro.md` 头部链出 how-it-works，how-it-works 顶部加一行反向入口「要拿去讲？见 rollout-intro」。
  * `legacy-adoption.md` §5「依赖与边界的诚实清单」= 接入后的边界真相源；开场包的四象限**链向它**，不复制表格（复制 = 两份漂移）。
  * 安装 / 跑门命令**链向 `quick-start.md`**，不复制命令块。

### 2.2 考虑过的备选方案及否定理由 (Considered Alternatives)

* **备选 A**：把 README 改写成对外版（一材两用）
  * *否定理由*：README 的读者是已决定自用的开发者（装配 / 契约细节必须保留）；混排会让两类读者都不满意。分离 = 各自最短路径。
* **备选 B**：开场包做成 PPT / 视频等富媒体
  * *否定理由*：维护成本高、随产品演进漂移快；markdown 一页纸可随发版收口顺手校准。富媒体等楔子被验证有效后再投入。
* **备选 C**：演示脚本虚拟化（用 playground / 假仓库）
  * *否定理由*：playground 环境漂移有在案记录（`research/2026-11-04-ablation-full-logo.md:218`：嵌套 playground 段整跑在 18% 卡住不返回）；真实仓演示才有说服力，脚本按「以当期最新发行版在任一存量试跑仓执行」写，不绑死仓库。

### 2.3 必须警惕的刺痛代价与兼容性影响 (Trade-offs)

* **公网发布边界（拍板：选脱敏）**：`docs/guide/` 全目录进公开站（`docs/.vitepress/config.mts` 的 `srcExclude` 只排 `map/**`），所以开场包一旦落盘即公网可见。**定案 = (a) 脱敏**：外部引用改为「某头部团队公开分享，2026-11」或给出可公开访问的出处；组织内部口径（领导层考核方式、13 节点 MVP 说法）不进正文，只保留「领导层按交付物质量与效率考核」这类不含内部细节的表述。**否决 (b) 用 `srcExclude` 做私域分发**：开场包的价值就在可公开分享，私域分发会把推广对象锁死在组织内，且新增一条需要长期维护的排除规则。
* **漂移**：开场包与产品演进会漂移（演示脚本依赖门输出形态）⇒ 每次 beta 发版收口时人工校准一次；不设机器保活门（对外文档不进装配集，加保活门 = 加自举重量，违背本批方向）。
* **数据纪律**：外部数据（OK 文）只可作叙事引用、必须按 §2.1 四字段标注，不得写成自家实测——防「引用变实证」的措辞漂移。
* **边界纪律**：开场包不得承诺「流程串联」「执行平台」能力（既定不碰）；不得出现分档 / 多版本话术（单版本拍板）。
* **零代码**：本提案纯文档（docs/guide/ 不进装配集、不进摘要、不咬 golden / 计数棘轮），对采纳仓零影响。
