# Atlas 流水线改进提案机制 (Pipeline RFCs)

> **“凡改流水线，必留取证、必记决策、必带测试。”**

当你在真实业务项目中遇到 Atlas 自身的设计问题、契约漏洞、校验器误报或新特性需求时，请遵循本机制进行协同。

---

## 为什么要“三位一体（问题 + 决策 + 改动）”？

在常规开源协作中，常见的坏习惯是：
1. **只提代码，不记原因**：发一个 PR 改了两行正则，过两个月谁也想不起为什么改，后来人一重构又改回去了；
2. **只发抱怨，不带取证**：提个 Issue 说“你们的校验器报错了”，没有环境、没有日志、无法复现；
3. **缺少决策权衡**：改动只图自己省事，却暗中破坏了其他项目的兼容性。

Atlas 要求所有对流水线本体的改动，**必须将“问题记录 + 决策记录 + 代码/测试改动”作为一个 PR 一并提交**。

---

## 协同四步法

```
  1. 发现流水线缺陷
          │
          ▼
  2. 拷贝模板并记录取证与决策
     cp proposals/TEMPLATE.md proposals/RFC-YYYYMMDD-01-你的简短主题.md
          │
          ▼
  3. 修改代码并追加测试钉子 (tests/)
          │
          ▼
  4. 提 PR 并在描述中勾选验证结果 ──► 维护者一键审批合并！
```

### 1. 提案命名规范
文件统一放在本目录下，命名格式为：
```text
proposals/RFC-YYYYMMDD-序号-<短横线英文主题>.md
```
示例：`proposals/RFC-20261008-01-nested-router-extraction.md`

### 2. 强测试约束（变异证明）
* 若本次 PR 修复了一个门禁漏洞或新增了一条规则，**必须在 `tests/` 下同步新增测试用例或 M 系列变异钉子**；
* 证明修复生效，且未来的改动绝不会退化该规则。
* **系统性修复的留出验证（2026-10-26，D156；`RFC-20261026-03` Phase 1）**：改门 / 校验器 / 契约判据、且 RFC §1 引子族锚（`bugs.md` 同根归纳）或 ≥3 条独立审查重复 finding、或 diff 落在 DR4 段级锚路径族的，**§4.5 必写留出集 + pre-fix 红证**；三态 `闭族` / `未闭族` / `单案修复（无留出集，须 QUEUE 观察行 owner + 期限）`。**留出独立性三条**（缺一按「同夹具变体」驳回，独立评审当场重放）：①判据输出翻转（verdict / 案数 / 最近日期 / 精确病案数至少一项；仅 WARN 文本 / 日志 / 通道变化不算）；②变异增量杀伤（既有钉全绿而留出案红）；③结构不可达（夹具不可由既有钉夹具只改日期串 / 通道 / 增删行得到）。「只换日期串 / 只换调用通道」不合格。流程门登记 = `shared/gates.md` §2.5。

### 3. 一键审批体验
当维护者打开你的 PR 时，通过查看 `proposals/` 中的提案记录，可以一秒看懂：
* **前因后果**：你在什么场景下报了什么错；
* **为什么这么解**：否定了哪些不合理的方案；
* **代码与测试**：改动是否克制，全套测试是否全绿。
* **留出验证面（系统性修复触发时，D156）**：留出集是否真独立（三条判据、评审当场重放）、pre-fix 是否真红、post-fix 是否真绿、三态与证据是否一致、触发是否被逃（(b) 路径交叉检查 = `git diff --name-only` + `scripts/closeout_derive.py` 路径族表手工对照）；不得无留出而宣称闭族。
审批通过后一键合入主干，所有人即刻受惠！
