## 1. 现象与取证 (The Problem & Evidence)

### 1.1 触发形态（抽象）

五个独立信号，同一根因——「需求类信息」与「长期应然登记」共用一套词与一条落点链，且需求确认阶段无落点：

1. **术语歧义引发连续误读**：一次真实协作会话中，「PRD 跨多个域怎么办」「任务卡是不是 spec」「基线环归哪个 skill」三问接连出现。前两问根因 = PRD 一词覆盖两类信息（需求增量 vs 应然存量）；第三问根因 = 「基线」一词已有三义（`rings/structure` 契约标题即「结构基线」、installer 装配基线、ablate 消融基线），而 prd 环 AC 的「基线登记断言」措辞使归属更混。
2. **契约自身矛盾**：`rings/prd/reference.md` §0 自称「项目级产品**需求文档**」，同句定义「它是**应然**——只写产品应该是什么样，**不写实现进度、不挂状态**」。「需求文档」的本质（待办、带状态、会过期）与该定义（应然、不挂状态）冲突——名字叫 PRD，干的活是事实登记。
3. **需求确认材料散落契约外**：执行层 `plan` 开卡即拆，「聊清楚、确认范围、出确认稿」阶段无落点。实证 = 某采纳仓一张任务卡 `prd.md` 的「上游材料」节出现自注：「技术方案：`<日期目录>/<slug>/outputs/…`（**当前工作区实际落点**：`<另一契约外目录>/<slug>/outputs/`）」——确认材料住在契约外日期目录，卡只能拿指针去够；无登记、无状态、无对账。
4. **契约立场被现实挤爆**：`shared/single-source.md` §1 需求卡行明文「**不另建 inbox 或需求文档**」（2026-09 立场：防第二正文源漂移）。2026-11-21 机制批（#71–#74）把需求原文真相源落在**卡目录**（`work/需求PDF-全文.md`），一条需求拆多卡时同一转换稿被多卡重复持有；且「确认稿」类产物无处可落——实践中只能散落契约外（见 3）。
5. **采纳仓手写区已自成漂移**：某采纳仓 AGENTS.md 手写区「需求入库与条目覆盖」节，条目表落点写 `<日期目录>/outputs/需求条目表.md`（契约真相源 = 卡目录 `requirement-items.md`），且同节第 4 条「覆盖矩阵留空格**阻断** verify」与第 5 条「四条判据均为 **WARN** 不拦停」自相矛盾——手写区不入装配分发、`atlas update` 推不到，正是「采纳侧无法自治」的直接实证。

## 2. 决策与权衡 (The Decision & Trade-offs)

### 2.1 核心定案 (The Decision)

**两块改动、五个决策点（D1–D5 带推荐，待拍板）：**

**A. 术语正名（契约正文面）**

- **A1（D5 缩幅方案，推荐起步）** `rings/prd/reference.md` §0 改写为「产品应然事实登记」并加别名括注（域级/全局产品事实，现称域级/项目 PRD）；词汇表补全局层；标注「`-prd.md` 文件名 = 历史遗留」过渡注记。**全量改措辞（约 20 个仓内文件的「域级/项目 PRD」字样 + 环标题 + skill 名）列第三批另案**（D5 扩面方案）——单改 §0 而满仓旧称并存会制造第三套叫法，故过渡期契约内显式声明「现称即别名」。
- **A2** 「基线」词表封口：现有三义不再扩义；prd 契约「基线登记断言」措辞保留（说的是断言性质，不是环身份）。**该封口对 1.1-1 第三问是缓解非解决**（困惑源自词多义，消歧需消费面措辞清理，属 D5 扩面）。

**B. 需求层落点（执行层 + 契约面）**

- **B1** 新增落点 `<assets_root>/requirements/<需求slug>/`（推荐 `product/requirements/`，D1；路径按 `layout.assets_root` 解析，不写死根），目录内四件：
  - `requirement.md`：确认稿 = 需求 PRD；
  - `items.md`：**落点条目表**（唯一住址），表头 `| ID | 页码 | 章节 | 原文（逐字） |`，沿用 #71 口径（逐字不改写、限定语保留、表行数 = 声明总数）；
  - `work/需求PDF-全文.md`：转换稿唯一住址（自 #71 卡目录迁移）；
  - 状态行：值域闭集 `{候选, 已确认, 已拆, 已收口}`；收口后目录移 `requirements/archive/<YYYY-MM>/`。
  - 登记 = 独立 `requirements/_index.md`（需求 slug / 状态 / 关联卡），**不进** `product/prd/README.md` 追溯总表——追溯总表行形态受 validate_prd 参数 4⑥ 行形态硬约束（已覆盖/未覆盖二值），需求登记行两态都不像，落进去会被判 FAIL；且 `prd/` 下除 `reviews/` 外不允许子目录（`ALLOWED_PRD_SUBDIRS`），故落点必须在 `prd/` 外（这也是 D1 备选的否定理由）。
- **B2** 确认动作 = **契约纪律段**（plan 前置），手法复用 atlas-prd 确认门（证据优先、只问意图/范围/风险/验收行为、查证后仍模糊才问人）；不新建 skill（D3 备选：atlas-prd 加「需求确认档」，第三批另案）。机器面一行软校验：`plan` 落点模式下状态行缺失或仍为「候选」⇒ WARN「未确认先拆」。
- **B3** `plan --requirement` 支持指向落点（目录或 `requirement.md`），**双模式并存、存量行为不变**：
  - **直填模式（旧路径，保留）**：指向普通文本文件，条目表/矩阵骨架照旧卡级生成（D204 代码生成面），表头沿用 `| ID | 页码 | 章节 | 原文 |`，原文逐字住卡内——存量卡与单卡小需求不受影响。
  - **落点模式（新增）**：卡条目表 = **领取引用表**，表头 `| ID | 来源 |`，`ID` = 落点条目 ID，`来源` 格式定死为 `<落点路径>#<落点ID>`（纯引用、无正文复制）；卡 `prd.md` §1 的需求正文（details）渲染为**指针**（落点路径 + 领取条目 ID 集），不逐字复制确认稿——plan 渲染通道本身就是「同一正文两处」的生成器，必须与条目表同步改造；plan 骨架文案「落本卡 work/」分支为落点模式提示。
  - **#71 真相源迁移走 single-source §3 迁移仪式**（登记表更新 + 完备性对账 + 存量豁免条款，见 §2.3）。
- **B4** `verify` 对账扩展（落点模式卡）：判据 = **ID 覆盖性集合运算，放弃计数相等**——①每条落点条目 ID 至少被一张关联卡领取（防漏领）②卡侧引用 ID 无幽灵（防多领/错领）③落点表非空而 Σ卡领取 ID 并集为空 ⇒ 对账失效自检。**条目↔卡语义显式声明为 at-least-once 共担合法**（一条条目跨两卡实现是常态，按覆盖性不按计数——计数相等防不住「漏 A 多 B」的对冲，且与 #72「本卡承接」子集语义冲突）。对账运行窗口 = 落点状态「已拆」时，扫描其全部关联卡（含已 archive）。升格口径沿用 #73/#74 既有（第一个被放行的实际漏单后另案）。
- **B5** 收口双回写（纪律面，不设新门）：`finish` 提醒 ① 按域沉淀回域级产品事实（FN/R/AC/文案规范表 + 变更记录）② 落点状态 → 已收口。收口判据锚定卡 archive（归档才是收口）。
- **权威源排序五层写死**（single-source §4 改写）：**需求原文（转换稿）> 需求 PRD（确认稿）> 任务 PRD > 设计文档 > 代码惯例**；确认稿是原文的协商派生承接，与原文冲突时**原文优先**，登记冲突并上报。

**为何这是正解**：把「需求类信息」的唯一真相源从卡级上移到需求级——一条需求 N 张卡时，转换稿/确认稿/条目正文只存一份，卡侧全部指针化；应然面按「事实（存量）vs 需求（增量）」切开。单源保障：落点持正文，卡持引用（ID + 路径语法化，机器可验）；这不是造第二正文源，是 #71 从卡级到需求级的**搬家**，走既有迁移仪式。

### 2.2 最强反方与证伪条件 (Strongest Counterargument & Falsification)

* **最强反方论证**：「需求落点 = 2026-09『不另建 inbox』要防的第二正文源，需求层是多余抽象——条目住在卡里（卡级条目表）已经够用，需求级与卡级条目会成为新的漂移对（同一需求改口径要改两处）；确认材料散落是采纳仓自治问题，不该由 Atlas 契约收编。」此反方否决了：①「仅卡级打补丁」——确认阶段材料仍无落点，1.1-3 无解；②「需求级持有条目正文副本」——那才是真双源。
* **回应**：反方对「条目两处正文」的担忧由设计消解——卡条目表 = 引用行（`来源 = 路径#ID` 语法化，正则可验），正文唯一住址在落点；口径冲突走「登记冲突并上报，不许就地二选一」。对「采纳仓自治」：#71–#74 已是装配副本机器面（真跑出声），契约外散落与手写区自漂移（1.1-5）正是采纳侧无法自治的实证。
* **证伪条件**（`discriminating_check`）：
  * command: 落地后任取一落点模式需求，`grep -E '^\| R-[0-9]+ \| .*#R-[0-9]+' <各关联卡>/requirement-items.md` 提取引用行，与落点 `items.md` 的 ID 集做双向差集；并对卡 `prd.md` §1 与落点 `requirement.md` 正文做重复行比对。
  * expected_if_false: 任一卡条目表出现条目**正文复制**（非 `路径#ID` 引用语法）⇒ 单源设计证伪；落点 `items.md` 非空而 Σ卡领取 ID 并集为空 ⇒ 对账判据失效。
* **其他备选**：D1/D3 备选及否定理由见 §2.1 与 §5；另否决「需求落点放 `.atlas/tasks/inbox/`」——需求层是应然面输入，与执行层运行目录混居会复活「运行态 / 资产态」边界问题（`.atlas/runs/` 不入库是既有定案 D140）。

### 2.3 必须警惕的刺痛代价与兼容性影响 (Trade-offs)

* **兼容性**：直填模式（旧路径）保留为合法路径且**行为逐字节不变**（verify needle 双词表 `("原文", "来源")` 兼容存量卡旧表头）；落点模式增量开启，失败即停用，无不可逆变更。
* **迁移并存期（存量豁免条款，随第一批入 single-source §3）**：#71 真相源迁移按**需求增量切换**——存量卡级源（`work/需求PDF-全文.md` + 旧格式条目表）随卡 archive 自然清退，清退完成前**该卡条目以卡内源为权威**；verify 双词表显式识别旧格式卡并按旧判据处理。把并存期写成有边界的例外，规避 §3「旧源不得同时被消费」判漂移。
* **耗时**：verify 多一次落点解析与集合运算（毫秒级文本处理）；无新增重型门。
* **存量项目**：拉取后 `atlas update` 咬合即得（**装配面**），无需 re-init、无需刷新事实。**采纳仓手写区 update 推不到**——升级指引须附「手写区人工同步清单」三行（权威源排序行补确认稿位、转换稿落点行、条目表格式行），并列为发布说明项。
* **分期中间态**：第一批（正名 + 登记 + 纪律段）**不含条目表 schema 改判**——schema/needle/plan/verify/迁移仪式在第二批一次咬合，避免「契约已宣布新格式而机器仍按旧 needle 判」的误报窗口。
* **长期维护成本**：需求落点生命周期到「收口归档」为止，不新增长期机器门；新增抽象仅「一个目录约定 + 两条 WARN 判据」，三年维护面 = 执行层既有 owner。
