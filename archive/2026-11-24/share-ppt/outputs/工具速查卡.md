## ✅ 已处理：OpenSpec 这句已改（2026-11-24 已写入口播稿 P4、附录 B 与 comparison.md §三.3）

口播稿 P4 原话：「**不验证**这条验收标准在代码里有没有对应真实的测试——这是**它自己声明的非目标**」。

今天实查，OpenSpec 2.0 的**扩展工作流**（非默认档）里有 `openspec-verify-change` 技能：由 AI 用**关键词搜索、合理推断**检查需求是否实现、**场景有没有测试覆盖**。但技能正文写明这是 **advisory（建议性）**，缺测试覆盖只记 **WARNING**，不阻断归档。

所以原句台下一查就能被挑：「它明明有 verify」。建议改成：

> 「OpenSpec 有个可选的 verify 技能，会让 AI 搜一搜场景有没有对应测试——但它自己写明这是**建议性**的，缺测试只给个 warning，归档照走。也就是说，**判没判对，还是 AI 自己说了算**。」

这样改反而更有力：和后面「BMad 方法本身的评审/测试以 agent 判断加流程纪律为主，未见机器给结论的核对」是同一个论点。comparison.md §三.3 的写法（「不提供代码级静态分析工具去自动验证」）仍然成立，可以补半句提到这个 advisory 技能，显得更公允。

| | |
|---|---|

出处：口播稿 P4、附录 B（11-19 实测 release 记录：v6.2 → v6.4 → v7.0.1）

> **新雷点（11-24 发现）**：v7.0.2 的 brainstorming 改成**问得更少、先问为什么、有选择时给选项和推荐**——和我们 P10 讲的 onegate「不会一上来抛五个选择题」很像。被问「Superpowers 也这么做了」时：
> 「对，会话内的提问纪律大家在收敛到同一个答案，这是好事。区别在于问完之后：我们的起手结论会被编译进 PRD 和验收账本、后面机器对账；它的结论进入计划、规格与执行账本，但没有全局业务资产账本和机器给结论的核对。」

## 3. OpenSpec（L3 规范层）

| | |
|---|---|
| 是什么 | 规范驱动开发：`specs/` 放存量、`changes/` 放增量提案，管「施工的图纸」 |
| 刻意不做 | 不做 AC ↔ 真实测试的**机器**对账（verify 技能是 advisory，见上方 ⚠️）；改动不走提案流程，spec 就开始漂 |
| 我们的结论 | 设计优雅，我们自己用过、文档真漂了；已有 OpenSpec 的团队不用扔：评审流留它，定稿条目落 Atlas 资产根，接上 Atlas 的核对 |
| 状态 | `Fission-AI/OpenSpec`，MIT，**活跃（11-23 还在推送）**，已到 2.0 |
| 被追问 | 「并存是给存量团队的过渡桥，不是推荐稳态——两棵需求树会抢『条目正文唯一住址』。」 |

> 顺带：OpenSpec 自己的 README 评价 **Spec-kit** 是「详尽但重，阶段门僵硬」。若被问 Spec-kit：它的门是**流程阶段门**（先写完 spec 才能进下一步），不是**核对门**（实现对不对由机器核对）。

出处：comparison.md §三.3；口播稿 P4、P7、附录 A Q2
