## 0. 一页结论

**推荐：方案乙（单源快照 + 派生块字节门 + 受管区无自由数字 + 批次 preflight）。先落步 1–2，删正则与重锚推迟到一个干净批次。**

**为什么是乙**

1. 问题不是「数字抄错了几处」，而是**同一条事实在 4–6 个正文里有副本，而门只锁了其中一处**。本次在干净树上实测到三条：7 个 map 章节版本串停在 `v0.2.0-beta.7`、`docs/map/gates.md:4` 写「77 个测试文件」（实况 80）、同文件 `:66`/`:90` 的 M 编号上限自相矛盾（实为 `M176b`），而 `python3 tests/test_map_anchors.py` 全绿。
2. 乙是唯一同时满足「可回滚」「不碰判据语义」「把失效模式从不可判定变成可判定」的取向：门从「手抄数字 == 实况」改成「派生产物 == 生成器输出」，再加一条「受管区不准出现自由数字」的 lint，堵住「删掉那句话就删掉了门」。
3. 乙的最小切片（步 1–2）只新增一个生成器与一个测试文件，零改判据、零改正文语义，可单独 revert；删 canonical 白名单正则这一步单独成批，风险可隔离。

**不推荐甲（点状补漏）**：它把「已发现的三种漏检」补成正则，但判据仍然是句式白名单。仓内已有两次同形态教训（`tests/test_canonical_consistency.py:420-433` 自认「漏形态就静默放过」；2026-09-28 计数事故）。补漏追不上写法演化，且本次三条漂移里没有一条是「写错了数」，全是「另一个副本没人读」。

**不推荐丙（账本重构：结构化 + 全量生成）**：它会把 `gates.md` 最有价值的资产——「不查什么」列、取证等级、缺口清单——压进 schema，而这些恰恰是无法结构化的人写判断。落成后成本最低，但一次投入的 review 面不可抽样，且不解决 F2（批次门），在当前单人节奏下必然半途。

**「现在不该动」部分成立**：详见 §6。结论是「现在动步 1–2，不动删正则与正文重写」。

## 4. 门禁应该落在哪一层

### 4.1 两种取向的差别

| | 取向 A：锁「手抄数字 == 实况」 | 取向 B：锁「派生层产物 == 源」 |
|---|---|---|
| 判据形态 | 正则匹配固定句式，取出数字与实况比 | 生成器输出与仓内受管块**逐字节相等**；受管区外禁止出现该键 |
| 覆盖对象 | 门作者想到的句式 | 被纳入快照的**键**（与句式无关） |
| 新增一种写法 | 静默放过（必须回来扩正则） | 只要键已纳管，自动覆盖；未纳管则被 lint 拦下 |
| 数字副本 | 副本越多，漏锁概率越高 | 副本被消到 1 个（受管块） |
| 修红方式 | 改数字（最省力）→ 红灯变噪声 | 跑生成器（改不了数字，只能同步源） |

### 4.2 失效模式对照（这是本题的核心）

**取向 A 的失效模式（不可判定）**

- **白名单腐烂**：`test_canonical_consistency.py:420-433` 自认「判不了换了写法的计数陈述」。本次三条实测漂移全部落在白名单外。
- **删句即删门**：门只校验「出现过的句子」。把 `gates.md` 的「80 个测试文件」删掉，门不会红（它只管匹配到的），但事实也失去了唯一登记处。
- **多副本互相掩护**：同一事实在两处，只有一处被锁时，另一处永久自由漂（77 vs 80）。
- **改数字成本低于改行为**：人会选便宜的修法，门逐渐变成噪声源——审计里「红灯训练成噪声」的正是这一层。

**取向 B 的失效模式（可判定，且可被自身的反面包抓住）**

- **生成器与门同源 ⇒ 双端同错恒绿**（`test_shared_kernel.py:222-226` 记的 B197-1 家族）。必须配：golden vector 冻结（`requirements_digest` 已有先例）+ 喂坏源必红 + 「空值即红」（glob 路径失效时不允许静默输出 0）。
- **覆盖率不足**：只覆盖被纳入的键；受管区外仍可自由写数字。必须配 lint：受管键不允许出现在受管块之外的自由文本里，否则红。
- **生成物刷新制造 diff 噪声**：每次源变化都改受管块。但这部分 diff 是**可验证的**（跑一次生成器即可复现），与「人抄错一个字」性质不同。
- **生成器本身失效**：`_derive_snapshot` 里每条都是 `if is_dir()`，目录改名会静默少键 ⇒ 必须「键集合固定，缺键即红」。

**判定**：取向 A 的失效是「判据腐烂」，只能靠人不断扩白名单；取向 B 的失效是「工程缺陷」，每条都有对应的反面包。**应采用 B，但保留 A 的一小块：对无法派生的判断性内容（§2 的盲区列、取证等级）继续只做形态门，不假装能算。**

### 4.3 门应该落在哪一层（层级结论）

```
源（代码 / 文件系统 / package.json / git）
        │  生成器（唯一写入者）
        ▼
受管块（index 数字快照 / gates.md 计数引用 / map 行数 / 版本）   ← 字节门：块 == regenerate()
        │  人读
        ▼
叙述层（门册的判据与盲区 / DESIGN 理由 / changelog 措辞）        ← 形态门：只判结构，不判数字
```

- **批次门**（F2）：`--preflight` 只跑「受管块字节对账 + map 锚 + canonical 形态」三件事，目标 p95 ≤ 60s，挂 `shared/closeout.md` 步骤 1。理由：账本漂移的发现点现在在发版日（`scripts/release.py:307-321`），而漂移是**每次改动都可能产生**的，验证频率必须 ≥ 改动频率。
- **发版门**：保留全量 pytest，不再承担「发现账本漂移」的职责。

## 5. 候选方案

三个方案共用一条基线判断：**不新增判据语义，只改数字的落点与门的比较对象**。

### 方案甲：点状补漏（继续锁手抄数字，扩白名单）

| 项 | 内容 |
|---|---|
| 改动面 | `tests/test_map_anchors.py`（版本串扩到 8 个 md；散文计数纳入值域）；`tests/test_canonical_consistency.py`（扩 2–3 条正则）；修 3 处已实测漂移（7 个版本串、77、M162/M164）。共 2 个测试文件 + 6 个正文文件 |
| 分几步 | ① 版本串扩面 + 修 7 处；② map 散文计数纳入 + 修 2 处；③ M 编号上限加门 + 修 2 处 |
| 每步可独立回滚 | 是（纯测试与正文改动，逐步 revert 无耦合） |
| 对 80 个测试文件 | 不增不减；改 2 个 |
| 对计数锚 | 不动（锚数不变） |
| 迁移期双写 | 不涉及 |
| 日常成本 | 把已知漏检补上，预计 ~9 → ~7 次/活跃日；每出现一种新写法再回来扩一次 |
| 最强反对 | 「补漏」这个动作本身已被这个仓证明追不上：`test_canonical_consistency.py:420-433` 自认白名单会漏，本次三条漂移全部在白名单外。更关键的是它治不了「同一事实多副本」——补到 77 那一句后，下一次改数字仍要记得改两处。 |
| 能被证伪的检查 | ① 修完后连续 10 个活跃日的账本类 fix 提交是否 ≤2/天（若仍 ≥5/天 ⇒ 病根不是漏检）；② 注入一条白名单外的合法新写法（如「共 12 器」「12 件校验器」）⇒ 门应绿 ⇒ 证明「补漏」永远落后于写法演化；③ 在 `docs/map/gates.md` 再复制一份「80 个测试文件」并改成 79 ⇒ 门应绿（副本不受锁）⇒ 证明多副本问题未被触及。 |

**结论：不推荐。** 它会让本次三条漂移变绿，但三个月后同一形态会以另一种写法回来。

**结论：推荐。** 理由：把「谁写」收敛成一个人，把「对不对」从「像不像」换成「等不等」，并且每一步都能单独撤。

## 6. 「这题不该现在动」是否存在

**存在，但是部分的。**

### 6.1 应当推迟的部分（现在不动）

- **删 canonical 四条计数正则 + 重锚 M20/M22/M23/M24**：这四枚钉是「门册计数会被抓」的现存证明。删正则那天若同时有新判据在飞，会把「门失效」和「判据变更」混在一个批次里，事后无法归因。建议等一个**只有账本改动**的干净批次。
- **两份 changelog 合一或声明权威**：涉及对外站点与发版脚本（`release.py:277-301`），且 HEAD 上两份都没有 `[Unreleased]`，改之前要先决定「批次是否当日写账」（`closeout.md:34` 的 26/30 实证说明现在不是）。
- **`gates.md` 正文改写（丙）**：不在此列。

### 6.2 应当现在就动的部分

因为「门全绿但账本自相矛盾」已经发生且可复现（§1 三条）。这不是理论风险：
- 版本串 7 个副本过期，任何人按章节开工都会读到错误版本；
- 同文件内 M 编号上限两处矛盾，且都错（真值 `M176b`）；
- 计数 77 vs 80 会让「新加测试有没有被登记」这一判断失真。

**推迟的触发条件（出现任一 ⇒ 本设计案整体挂起）**
1. 有 ≥2 个并行会话正在改 `shared/gates.md` / `docs/map`（仓内 `QUEUE.md` 有「在途批未提交」先例）；
2. 正处于发版窗口（`release.py` 跑过、tag 未推完）；
3. 存在必须保持旧格式的外部消费者（采纳仓需要 `gates.md` 的既有 §2.1 行号引用）。

**提前的触发条件（出现任一 ⇒ 立即执行乙的步 ①–②）**
1. 下一次 beta 发版再出现「发版门清障」提交（当前 3 天 3 次，若变成连续两次发版各一次）；
2. 出现「账本自相矛盾但门全绿」的第四例；
3. `--preflight` 之外，账本类 fix 提交连续 3 个活跃日 ≥5 次。
