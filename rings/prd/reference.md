# atlas prd — 项目级 PRD

> 本环为 atlas 独立 skill `atlas-prd` 的执行契约，位于 `.atlas/rings/prd/reference.md`。
> 执行前先读共享契约：`.atlas/shared/global-rules.md`、`stack-profile.md`、`single-source.md`、`layout.md`、`knowledge.md`。

## 0. 一句话

产出**项目级产品需求文档**：全局一份 + 每个产品功能域一份。它是**应然**——只写产品应该是什么样，**不写实现进度、不挂状态**。

本环**不产出**：E2E 用例、代码、结构事实（那是 `atlas structure`）。

## 1. 输入

| 输入 | 必需 | 说明 |
|---|---|---|
| `.trellis/spec/structure/` | 是 | 域清单（`_meta.json.domains`）、页面结构、字段技术事实、处置所需的旧/新实现事实 |
| `product/stack-profile.yaml` | 是 | 产品名与 apps |
| 用户对话 | 是 | 诊断与确认门的信息来源 |
| 既有 `product/prd/` | 否 | 刷新/增量时读 |

**证据优先**：凡是 `structure/` 或代码能回答的事实，**不得问用户**。只问产品意图、偏好、范围、风险容忍度、验收行为，以及查证后仍模糊的决策。

**接入形态（`stack-profile.yaml` 的 `origin: adopt`）**：结构事实是**第一次接入必须全量落一次**的基线来源——没有它，「哪些能力是既有的、哪些被静默丢掉了」无从判断，§六 的处置表也就没有可比对的对象（`rings/structure/reference.md`）。

**与 structure 环的关系**：本环以 `.trellis/spec/structure/` 为输入，但**相互独立**——structure 环不自动触发本环，本环也不触发 structure；PRD 独立运行、按需更新。诊断阶段读 `_meta.json.domains` 的**候选域**并**定稿**，回写 `status`。

## 2. 产物布局

```
product/prd/
├── README.md                 追溯总表 + 索引（域 ↔ structure 模块 ↔ 页面 ↔ Rule Set ↔ AC）
├── prd.md                    全局（唯一）
└── <domain>-prd.md           域级（每域一份）
```

**域 slug**：ASCII kebab-case（如 `dubbing-config`、`prompt-management`）；文档内保留中文显示名。

**模板**：`.atlas/templates/prd/global.md`、`.atlas/templates/prd/domain.md`（含 frontmatter 契约与逐节必填标注）。

**编号体系**（全产品唯一，不复用）：

| 对象 | 格式 | 例 |
|---|---|---|
| 功能 | `FN-<DOMAIN>-NNN` | `FN-PROMPT-001` |
| 业务规则（Rule Set） | `<DOMAIN>-R-NNN` | `PROMPT-R-003` |
| 验收标准 | `AC-<DOMAIN>-NNN` | `AC-PROMPT-007` |

`<DOMAIN>` 取域 slug 的大写中段（`prompt-management` → `PROMPT`）；若冲突，用 `README.md` 的域表固定映射。

## 3. 全局 `prd.md` 章节规格

> 文档信息（版本 / 日期 / 作者 / 状态）+ **范围形态声明**（见下）+ 目录，然后：

**范围形态声明（必填，逐行一条，键名固定）**——本 PRD 相对「对照基线」的写法（2026-09-26 补，依据 `3509 §B6` + 本轮双形态设计）：

| 形态 | 必填行 | §六 写什么 |
|---|---|---|
| **首建** | `范围形态：首建` | **功能范围表** |
| **变更** | `范围形态：变更` + `覆盖度：全量 \| 增量起步` + `基线：<路径或版本>` | **处置表** |

- **基线的两个来源等价**：接手别人的系统（`structure/legacy/`）与本产品的上一版（上一版 PRD / 现行 `structure/`）**同属「有基线」**。新项目做着做着必然进入维护态——那时把声明从 `首建` 改成 `变更` 并写明基线即可：**形态会演进是正常生命周期，不是特例**。
- `增量起步` = 只覆盖本次受影响集合，其余显式记 `未覆盖（沿用实然）`；`全量` = 对基线逐条表态、无未覆盖。
- **`首建` 不得声明 `增量起步`**——没有基线就没有「沿用实然」可言。
- 这一行是**机器门的第一输入**（§7 参数 4）：不写、值非法、或与 §六 表形态不一致 ⇒ **FAIL**。

| # | 章节 | 最小必填 |
|---|---|---|
| 一 | 产品定位 | 是什么 / 为什么做 / 一句话价值 |
| 二 | 目标用户与角色 | 角色清单，每角色：身份、目标、使用场景、使用频次 |
| 三 | 核心场景 | 3–5 个端到端场景，每个含 Mermaid 流程图（正常 + 异常分支） |
| 四 | 产品形态与入口 | 平台形态、入口、导航骨架 |
| 五 | 功能架构 | **域清单**（域 slug + 中文名 + 一句话职责 + 对应域级文件）+ 域间关系图 |
| 六 | 范围与处置 / 功能范围 | 见下（**形态二选一**） |
| 七 | 页面结构全景 | 导航层级表 / 页面职责表 / **页面 ↔ 域映射表** |
| 八 | 非功能需求 | 性能 / 安全 / 兼容性 / 可维护性 |
| 九 | 术语表 | 术语 + 定义（跨域共享的才写这里） |
| 十 | 风险与依赖 | 风险（描述/影响/应对）+ 外部依赖 |
| 十一 | 修订记录 | 版本 / 日期 / 修订人 / 变更说明。**不设修订记录的产品**写一行 `不适用（理由：<一句>）` 即合法（与 §4「状态机」的「不适用」同源）；把整节**静默删除**不合法（§10 幂等）。 |

**最小必填集（`增量起步` 时）**：只强制 **五 功能架构 / 六 范围与处置 / 七 页面结构全景** 三节。判据是「**有没有下游消费者**」：五 → 域级文件组织；六 → 防静默丢功能；七 → e2e 环页面表的**页清单来源**（`product/e2e/e2e-index.md` 页面表，`rings/e2e/reference.md` §3.1；E1 迁入）。其余章节在 `增量起步` 下可缺省，**但一旦存在就必须满足本节规格**。

**缺省 ≠ 占位符**：`增量起步` 下未覆盖的部分在**追溯总表**里显式记 `未覆盖（沿用实然）`——这是**有意的未覆盖**，与 §6 禁止的占位符（`TODO` / `待补充`）不是一类。

### 六、范围与处置 / 功能范围（防静默丢功能，必写）

**形态由 §3 的范围形态声明决定，二选一**（2026-09-26 补）：

| 声明 | §六 写什么 |
|---|---|
| `首建` | **功能范围表**：`功能 / 能力 \| 所属域 \| 一句话说明`——逐条列出本产品规划的全部功能 |
| `变更` | **处置表**：`功能 / 能力 \| 所属域 \| 处置 \| 理由` |

- `变更` 形态的 `处置` 枚举：`保留` / `改造` / `废弃` / `新增`。
- **`变更` 形态须覆盖基线里的每一个能力**；不得有基线能力未出现在本表（**`首建` 形态无此要求**——没有基线就没有可覆盖的对象）。基线是外部旧系统还是本产品上一版，**不影响本条**。
- `变更（增量起步）` 下，本轮未触及的基线能力在表里显式记 `未覆盖（沿用实然）`（**合法值，不是占位符**）。
- **本表只管「功能能力级的得失」**：模块级 / 字段级 / 交互级的变化归各域 PRD 的「变更记录」与 `apply` 环，**不写进本节**（否则本节会膨胀成第二个 PRD）。
- 另设 **不做清单**（本产品明确不做的事）与 **迁移性需求**（见 §6）。

## 4. 域级 `<domain>-prd.md` 章节规格

> 文档信息 + In Scope / Out of Scope / 依赖域，然后：

**frontmatter `depends_on`（域间依赖的机器真相源，2026-10-04 补，`3509 §B186-1`）**：

- **取值**：已定稿域 slug 的列表（可空 `[]`）；不得指向域清单外的名字（悬空引用 ⇒ FAIL）。
- **语义**：本域应然的**实现前置依赖**（没有上游域就无法实现 / 验收本域）。**只对应全局 `prd.md` §五 mermaid 的实线（`-->`）**；**虚线（`-.->`）不入本字段**——虚线 = 增强链路或数据回流（如成片状态回写项目），不构成实现前置，且入字段必成环。
- **与另两处表达的关系**（`shared/single-source.md`）：§五 mermaid 实线边集与域级正文「依赖域 / 上游 / 下游」均为**派生视图**；三处不一致 ⇒ `validate_prd.py` 参数 4 ⑧ FAIL（以本字段为准修派生视图；若派生视图才是对的，先改本字段并留变更记录）。
- **正文与本字段矛盾时的仲裁**：按**产品语义证据**逐域判，不一律以某一方为准（先例：`role-casting` 正文「上游」漏 `project-management`，而证据——角色库项目内隔离、角色名项目内唯一——支持 mermaid 的实线 ⇒ 补正文而非删边）。

| # | 章节 | 最小必填 |
|---|---|---|
| 一 | 域概述 | 定位、边界、上下游依赖 |
| 二 | 功能清单 | 功能编号 / 名称 / 说明 / 优先级（P0–P2）/ **需求类别** |
| 三 | 功能详细说明 | 每个功能一节，六件套见下 |
| 四 | 业务规则（Rule Set） | 规则 ID / 内容 / **所属功能** / 触发条件 / 优先级 / 影响范围 |
| 五 | 验收标准 | GWT **三列**（`AC ID` ｜ 场景 ｜ 回指规则），每条回指规则 ID；末附**结构类 AC 清单**（见下） |
| 六 | Assumptions & Defaults | 未证实但按此推进的假设，逐条带默认值 |
| 七 | 变更记录 | 版本 / 日期 / 变更说明 |

### 开户最小集（`origin: adopt` 的**首轮开户**；2026-09-27 补，依据 `3509 §B85`）

`apply adopt` 开户时为域清单里**每个域**开一份**最小域级 PRD**，**只含四节**：

| 节 | 内容 | 为什么它在开户时可得 |
|---|---|---|
| 一 域概述 | 定位 / 边界 / 上游 / 下游 | 由 `structure/` 的域 globs、`global/routes.md` 与域级 `apis.md` 的调用方向导出 |
| 二 功能清单 | `FN-<CODE>-NNN`：编号 / 名称 / 说明 / 优先级 / 需求类别 | 由「域内可枚举的能力组」导出（一个能力一条） |
| 四 业务规则 | `<CODE>-R-NNN`：规则 ID / 内容 / **所属功能** / 触发条件 / 优先级 / 影响范围 | 由代码里**可观察且可判定**的行为导出 |
| 五 验收标准 | `AC-<CODE>-NNN`（GWT + 回指规则）+ **结构类 AC 清单** | 同上；每条断言必须能指回代码事实 |

- **三 功能详细说明（六件套）与 六 Assumptions & Defaults 在开户最小集里缺省**，留到该域**真的有需求**时补——那时才有依据写状态机 / 字段校验 / 六类文案 / 异常处理。测试：该域首次由 `apply <需求ID>` 增量时，把这两节一次补齐。
- **缺省 ≠ 占位符**：被缺省的两节**整节不出现**，**不得**写 `TODO`、空表或「待补充」；其余各节的实质内容也不得留空。**章节号不重排**（仍用 一/二/四/五/七），以便日后补齐时编号稳定。
- **§五 的 AC 在开户轮是「基线登记断言」**：它断言的是该能力**当前可观察的行为**（即下一条需求要 diff 的对照基线），不是本轮新作出的验收承诺——与 §六 的 `未覆盖（沿用实然）` 同口径。
- **「四类样例」不在本环承载（2026-09-28 移交，`3509 §B74`）**：原「开户轮按域计四类样例（正向/反向/边界/异常）」的义务由 **E2E 环的用例 `类型` 字段**承担（`rings/e2e/reference.md` §5.2）；本环不再逐 AC 标样例类型，也不再要求「每个关键功能覆盖四类」。
- **为何要这一集**（`3509 §B85` 的「先量再动手」实测）：开户时若按全量写，7 域 / 24 能力 ≈ **2,006 行**，其中六件套占 **74%**，而这些内容在开户时**只能从代码反推产品意图**（属推断而非事实）；开户最小集 ≈ **518 行**（**−74%**），且每一行都能指回结构事实。
- **开户最小集仍受全部机器门约束**：`validate_prd.py` 参数 1–4 与「域清单 ↔ 域级文件一一对应」照旧——最小集只是**少两节**，不是少门。
- **跨文档引用统一用项目根相对路径**（2026-09-27 补，`3509 §B86`）：域级 / 全局 PRD 里指向同产品其它文档的反引号引用（如追溯总表、结构事实）**一律写成项目根相对**（`product/prd/README.md`、`.trellis/spec/structure/...`），**不用** `./` / `../` 相对当前文件。理由：`validate_prd.py` 参数 3 对 `./`、`../` 开头的 token 取**文档所在目录**为基点，而从 `product/prd/<domain>-prd.md` 出发的 `../README.md` 会解析到**不存在**的 `product/README.md`；项目根相对在两种基点下都不会歧义。

### 三、功能六件套（每个功能必写）

1. **功能描述**：用户在何处完成什么、解决什么问题。
2. **用户流程**：正常路径 + **全部异常路径**（分支树或 Mermaid）。
3. **状态机**：状态名 / 进入条件 / 退出条件 / 用户可见表现。**无状态流转时写「不适用」并给一句理由。**
4. **字段规范**（业务语义）：字段名 / 类型 / 是否必填 / 长度限制 / 校验规则 / 错误提示文案。
   技术表结构（列、约束、关系、枚举取值）**一律引用 `structure/*/data-models.md`，不在此重复**。
5. **文案规范**：六类场景齐全——空状态 / 加载中 / 操作成功 / 操作失败 / 权限不足 / 网络异常。
6. **异常处理**：异常场景 / 触发条件 / 处理方式 / 用户反馈。

### 四、Rule Set

`<DOMAIN>-R-NNN` ｜ 规则内容 ｜ **所属功能** ｜ 触发条件 ｜ 优先级 ｜ 影响范围。
**禁止模糊表达**（"适当处理"、"合理展示"、"尽快"）。

**`所属功能`（2026-09-28 补，依据 `3509 §B109`）**：本规则**服务于哪些功能** —— 填 §二 功能清单里的 `FN-*` 编号，跨多个功能用 `、` 分隔。

- **必填**：每条规则至少服务一个功能；每个功能至少被一条规则服务。**这是「每个功能必须至少有一条 AC」的前一环**：缺了它，该义务无从机器判定（功能表用 `FN-*`，而 Rule Set 与 AC 都不引用功能 ID ⇒ 链路断开；实测有功能进了 In Scope 却零 Rule、零 AC 而无人发现）。
- 机器判据 = §7 参数 4；三个消费者是同一份数据：`功能清单`（§二）、`规则 → 所属功能`（本列）、`AC → 回指规则`（§五）。
- **横切规则**（一条规则同时服务多个功能，例如「删除须二次确认」）写多个功能号，**不要拆成两条**（拆 = 同一句话两处维护 = 漂移面）。
- 编号与列名以本节为准；**宽容匹配**：实现里 `FN-*` 行带不带反引号都可（实测产物两种写法共存）。

### 五、验收标准

每条 AC 用 **Given / When / Then** 表达，**三列形态**（2026-09-28 定，`3509 §B74`）：

| AC ID | 场景（Given / When / Then） | 回指规则 |
|---|---|---|

- **列头是机器判据**（`validate_prd.py` 参数 4）：§五 必须有一张表**同表含** `AC ID` 与 `回指规则` 列，且**不得**含 `样例类型` 列 —— 表列是契约承诺，无判据时文本与产物会长期不一致（实测：契约曾要求 6 列、7 份产物全 3 列，无人发现）。
- **样例类型已移交**（`3509 §B74`）：四类样例（`正向` / `反向` / `边界` / `异常`）的载体 = E2E 环用例的 `类型` 字段（`rings/e2e/reference.md` §5.2），本环不再逐 AC 标注，也不再要求「每个关键功能至少覆盖四类」（该义务属**语义项**，人工维度 = §8 审查维度 4）。
- `Then` 必须是可判定的确定断言；含实现描述的断言不合格（AC 断言行为，不断言实现）。

#### 结构类 AC 清单（必填，可为空表）

域级 §五 末尾必须有**结构类 AC 清单**（小节标题固定为 `#### 结构类 AC 清单`，2026-09-25 补）：

| AC ID | 为什么只能在初始态观测 |
|---|---|

- **语义**：清单里的 AC，其被测属性**只能在页面初始态观测**（页面骨架 / 默认面板 / 按数据渲染构成），因此在 E2E 环由 `initial:` 通道承担（`rings/e2e/reference.md` §5.6 R9），**不计入「有证据」**。
- **用途（硬）**：E2E 环的门「零证据用例须挂结构类 AC」直接读本清单 —— 一条 `expected` 全为 `initial:` 的用例，只有挂了本清单里的 AC 才算合法；否则 FAIL（依据 `3509 §B36` + `§B50`）。
- **不得滥用**：把「可用真实界面动作派生」的 AC 放进清单 = 给零证据用例开后门。判据：该 AC 的 `Then` 是否**存在真实界面动作**能改变它 —— 有，就不属结构类。
- **覆盖要求**：每个页面 / 面板都应在清单里有一条对应 AC（页面骨架 + 按数据渲染）；**挂不上骨架 AC 的骨架类用例只能错挂到业务 AC 上**（`3509 §B50` 的成因）。
- **自洽**：清单里的每个 AC ID 必须在同一文档的 §五 AC 表里存在（`validate_prd.py` 的参数 4 检 FAIL —— 清单是 E2E 那道门的唯一输入，它漂了门就静默失效）。

### 八、用户旅程走查（2026-09-29 补，`3507 AQ` = B124 结论；产物节位 = 域级 PRD 末节「## 八、用户旅程走查」，六 Assumptions / 七 变更记录见模板）

- **是什么**：从功能六件套**派生**的一节——每个用户目标一条旅程：**入口（页 / 路由）→ 编号步骤（动作 ⇒ 用户可见状态 / 文案）→ 终态（状态机落位）**。派生时不得新增六件套之外的行为。
- **覆盖判据**：§二 功能清单中**功能性** FN 每条 ≥ 1 条旅程；非功能 / 迁移 / 约束类 FN 无旅程形态，**豁免并注明理由**（对照：六件套状态机的「不适用（理由）」先例）；**跨页状态变化必须显式写出**（该类变化在字段表 / 状态机表里不可见，恰是本节的存在理由——例：「删音色 ⇒ 角色绑定解除」）。
- **确认门（硬）**：**用户显式确认前不得进 `e2e` 环**（`rings/e2e/reference.md` §6.2 前置门读它）。确认状态写在节首行 `> 已确认：<日期>`，无该行 = 未确认；**重派生本节时必须删除该行**（确认随内容失效——确认的是那次派生的内容，不是这个节名），待用户重确认后重写。用户提出修改 ⇒ **先改六件套、再重派生本节**（本节是投影，六件套是唯一源——防第二真相源，`§B103` 同族纪律）。确认前对照 `product/design.md`（视觉设计档案，存在时）：走查内容涉及的界面方向不得与 design read / 旋钮冲突——冲突 ⇒ 先改六件套或更新档案再请确认（`3507 BE`）。
- **存量回填（2026-09-29 补，全局审查 G7）**：存量域 PRD（无本节的）在该文档**下一次被任何需求触碰六件套时**补节并走确认门——不限于「改变应然 UI」的需求（改业务规则也会触碰六件套）。
- **触发范围**：仅「改变应然 UI」的需求（判据与 `rings/e2e/reference.md` §6.2 同口径）；三问全否的纯加法需求不触发。
- **为什么有这节（E1 缺口）**：原型环退役后「实现前看见流程」的人侧确认空缺——流程性错误在六件套文字里难发现，第一次「看见」被推迟到实现后，返工成本升级。可点原型已被 P4/E1 否（第二实现），本节以一页派生文字补位。

## 5. 流程（四段式）

**形态预判（先问这一句，再进阶段 1；2026-09-26 补）**：**有没有一条需求要接？**

- **有** ⇒ 输入含需求卡（`.trellis/tasks/<需求ID>/prd.md`），四段式只覆盖**受影响面**（入口 = `apply <需求ID>`）。
- **无**（应然资产自身修订，尚未写代码）⇒ **不建需求卡、不建任务**；仍按本节四段式跑，但只跑受影响的部分。四条粒度纪律与清单落点见 `apply/reference.md` §3.2（判据出处 `3509 §B10`）。

### 阶段 1 — 诊断

四个视角收集事实：**用户 / 业务 / 技术 / 页面结构**。

- **每轮最多 3 个问题**，然后停下等回答；用户已答过的不重复问。
- 用户不知道页面结构时，基于功能架构给一份最小草案让他确认。
- **查得到的不问**（structure、代码、已有 PRD）。

### 阶段 2 — 项目级定位对齐（概念版）

输出**固定 8 行**、尽量 ≤200 字，**不加其它章节**：

```
## 概念版 PRD
核心用户：[一句话]
要解决的一件事：[一个具体问题]
产品形态：[平台]
页面结构：[主干页面，不含细节]
功能域清单：[域 slug + 中文名，逐行]
本版不做：[明确排除]
定位/商业模式：[一句话]
技术前提：[关键前提或约束]
```

然后问：**① 方向是否对齐？② 需要调整吗？** 未确认不得进入阶段 3。

### 阶段 3 — 范围冻结

逐项复述待冻结内容（核心用户 / 功能域清单 / 页面结构 / 本版不做 / 处置结论），要求用户显式回复"确认"。范围变更 → 回到阶段 2 重新对齐。

### 阶段 4 — 逐域落地

一次一个域：**先出域大纲 → 确认 → 出正文 → 自审六件套完整性**。
全部域完成后做**全局收口**：写 `README.md` 追溯总表 + 更新全局 `prd.md` 的功能架构与范围处置 → 跑校验（§7）→ 交独立审查（§8）。

**收口后自检**（不另做章节展示）：
页面结构完整 · 异常路径完整 · 状态机完整或已声明不适用 · 字段规范完整 · 六类文案齐全 · 流程含分支。

## 6. 质量机制

### 零占位符

禁止 `TODO` / `待补充` / `TBD` / `待定` / `视情况而定` / `后续补充` / `[FIELD:]`。

**两个合法值，不算占位符**（2026-09-26 补）：

- `未覆盖（沿用实然）`——`变更（增量起步）` 下**有意**不重述的部分（见 §3 最小必填集）。
- `不适用（理由：<一句>）`——该节对本产品整体不成立（沿用 §4「状态机」的既有手法）。

两者都必须**带具体指向或理由**；只写「未覆盖」或「不适用」四个字仍按占位符处理。

缺失信息只有三个合法出口：
1. 写**建议默认值**：`建议默认值：<具体值>` —— 必须给出具体值，不能是"待定"。
2. 进 **Assumptions & Defaults**：写清假设内容 + 采用的默认值 + 影响面 + 何时需要澄清。
3. 进 **待决策登记表**（全局 `prd.md` 置顶一节）：当该事项**不是信息缺失，而是产品方尚未决定**时使用。每行必须含 **议题 / 现状取证 / 建议默认值 / 影响面 / 决策人**。这是**结构性待定**，不属于占位符。

**门控规则（重要）**：待决策登记表非空时，**只产出全局 `prd.md` 与追溯总表，不产出域级 PRD**——产品定位、功能范围、产品形态未定之前写域级细节等于写完就废。域级 PRD 在相关待决策清零后逐域补。

**取证与应然必须分开表述**：现有实现（`structure/legacy`、`structure/current`）里读到的东西是**参考基线**，不是本产品的应然。写成「参考基线（取证：<路径>）」，不得写成结论。

### 应然资产自身修订的粒度与清单落点（2026-09-26 补）

本环常被用于「**无需求卡**」的修订（对照截图 / 评审反馈改 PRD 与 E2E 用例）。该形态的完整定义与四条粒度纪律在 `apply/reference.md` §3.2，本节只声明与本环相关的两点：

- **清单落 `product/reviews/<日期>-<主题>/`**（`README.md` = 缺口清单 + 决策表 + 验收标准；`plans/` = 分域修订方案）；**不逐条开任务、不得用子任务树**。
- **切到「优化」的时机 = 用户显式宣布收齐**（不用自动阈值）。

### 镜像字段先取证（2026-09-26 补）

当字段的**取值域由外部系统决定**（TTS / LLM / 存储 / 协议 / 第三方 SDK 等）时，**定稿前必须对该外部系统取证**，不得凭「常见做法」写词表。

- **范围**：参数的**名字**与**取值域**（枚举集合、数值范围、单位、互斥关系）。
- **落点**：取证结果写进该域 §六 Assumptions & Defaults，并**注明被取证系统的版本**。
- **理由**：§6「零占位符」逼字段给出**具体取值**，而契约原先没有「先查引擎」这一步 ⇒ agent 会**自编**一套看起来合理的词表。实测（众声，引擎 `IndexTTS-2.5`）：域级 PRD 写了「情绪 = 任意枚举 / 强度 = 0–10 整数 / 倍速 = 合成后变速」，而引擎实际是 `emo_vector` 8 维固定向量 + `emo_alpha` 0–1 + 原生 `duration_factor` 0.5–2.0 ⇒ **字段无参数可映射、AC 不可判定**，还选了一条变调伤音色的实现路径（`3509 §B9`、讨论 `3508 §32`）。
- **本条只作纪律、不进校验器**：机器只能判「有没有出现外部系统参数名」，判不出「有没有取过证」——那正是误报工厂（§8 末注）。

### UI 文案与真实状态一致（2026-09-28 补）

**界面上任何面向用户的文案**（状态行 / 操作反馈 / 提示 / 徽标）**不得宣称未发生的行为**：写了「已保存 / 已写入 / 已合成 / 已导入 / 已同步」就必须真的发生；仅作会话内模拟或尚未接入的动作，文案必须如实标出边界。

- **理由**：该要求原落在**原型环**（§5 硬纪律 / §9 人工门 / §13 维度⑥，落地物见 `3509 §B44`）；原型环 2026-09-27 退役（`3508 §92`）后 canonical 再无等价条款。它拦的正是最容易被遗忘的一类缺陷 —— 实测出现过「状态行宣称已写入而 handler 什么都没写」（存量原型 `projects.html` 的批量间隔 / 正文编辑两处，由两环基线审查报为 Critical）。
- **落点与判据**：语义项、**不进校验器**（机器判不出「文案是否属实」，只能判文案形态）；人工维度 = §8 维度 5「文案与术语一致性」并入本项。
- **实现期纪律**（前端 UI 文案）：`09-22-polyvoice-mvp/implement.md` §5「原型转来的实现项」。

### AC 可观测终态（2026-09-23 补）

**写类 AC**（含保存 / 提交 / 写入 / 新建 / 增删 / 绑定 / 改绑）的 `Then` 必须给出**刷新后可观测的终态**（「刷新后…仍是 / 仍在 / …」）；**权限 / 拒绝类 AC** 必须给出**用户看到什么**（逐字文案或明确的显示位置）。

理由：只说「被写入」「被拒绝」「抽屉关闭」的 AC，E2E 无从判定该断言什么 —— 机器门只会在无关用例上误报、在真缺口上漏报（`3509 §B18`；取证 `AC-PROJECT-007` / `AC-ROLE-011` / 已删的 `E2E-LOGIN-003`）。**本条只作纪律、不进校验器**：2026-09-23 试过机器化（按 `Then` 是否含「刷新后/仍/显示…」这类词近似），**实测 20 条命中全部为误报** —— 被命中的 AC 其实都给了可观察终态（用「标为 / 消失 / 为空 / 不在 / 保留 / 列出 / 不变」这类措辞），判据无法与「真薄」区分。按 §8 末注「语义判不了的项不进校验器」，**撤回**该检查（`3509 §B18`、`3508 §42`）。

### 需求四准则

每条需求必须通过：**完整**（够建够测）、**无歧义**（只有一种解释）、**一致**（不与其他需求冲突）、**可测**（可验证）。不通过则与来源方澄清后重写。

### 需求类别（PMBOK 式）

每条需求恰属一类：`功能性` / `非功能性` / `迁移性` / `约束`。

- **迁移性（Transition）必带 `owner` 与 `结束条件`**——否则临时迁移态会永久化。
- 迁移性需求额外登记在全局 `prd.md` 的「范围与处置 → 迁移性需求」。

### 双向追溯（硬约束）

- 每条规则**必须**至少有一条 AC（**机器门**：§7 参数 4 的「规则→AC 覆盖」）。
- 每条 AC **必须**回指至少一条规则。
- **AC 回指的规则必须能从该规则的文本读出该 AC 的被测属性**（2026-09-26 补，依据 `3509 §B32`）。域内没有语义同族的规则时，**新增一条专属规则**（列在该域 Rule Set 末尾），**不得**并入语义无关的既有规则——凑一个格式合法的 ID 会让追溯链失效，而且这正是「就近凑」的成因（`3509 §B29`）。**本条只作纪律、不进校验器**（语义判断，按 §8 末注）。
- 每个功能**必须**至少有一条 AC —— 判据经「功能 → 规则（§四 `所属功能` 列）→ AC（§五 `回指规则` 列）」**传递**（机器门，§7 参数 4）。
- 页面结构里**每个页面必须**归属到至少一个域；每个域级文件必须出现在全局功能架构里。

### 内容归属（禁止重复）

| 内容 | 唯一落点 |
|---|---|
| 产品定位 / 用户 / 场景 / 功能架构 / 页面结构全景 / 非功能 | 全局 `prd.md` |
| 功能交互细节 / 状态机 / 文案 / 异常 / Rule Set / AC | 域级 `<domain>-prd.md` |
| 技术表结构与字段技术约束 | `structure/*/data-models.md` |
| 跨域共享术语 | 全局「术语表」；域内术语留在域内 |

### 体量预算（2026-09-28 补，`3509 §100`）

域级 PRD 的「功能详细说明（六件套）+ Rule Set + AC」合计**超 9500 字符**（与结构事实区同一基准值）⇒ **触发「拆分 / 精简」评审**：域太大 ⇒ 拆域，或六件套逐条精简；**不得静默膨胀**。超限只在报告里记一行待评审项。

- **理由（实测）**：开户轮六件套占域级体量的 **74%**；`adopt` 全量外推 ≈ **2000 行 / 110 KB**（≈ 众声整套 PRD 的 89%），而六件套在开户时**无处可依**（只能从代码反推产品意图 ⇒ 写进应然文档后还得先与这份虚构基线对账）。
- **不新增声明字段**：产出分级仍随 `apply` 模式（`adopt` = 开户最小集 / `greenfield` = 全量）；超限不得触发新的必填字段。

## 7. 确定性校验器

脚本 `.atlas/validators/validate_prd.py`，4 类参数，输出 **PASS / WARN / FAIL**。

> **2026-09-26 改**：原「参数 5 Waste Test」实测是一条**恒 PASS 的空门**——代码里 `warn` 列表从头到尾没被写过一次，6 条判据一条都没实现。「一道永远绿的门比没有门更坏」（会让人以为检过了），故按决定：**可机器判的那条并进参数 4**，其余**语义项**明确转为 §8 的人工审查维度，参数 5 的外壳删除。

| # | 参数 | 通过条件 |
|---|---|---|
| 1 | 文档头完整 | 每个文件有合法 frontmatter（域/版本/日期/状态） |
| 2 | 零占位符 | 命中数 = 0（描述规则的行本身豁免） |
| 3 | 链接可解析 | 域间引用、`structure/` 引用 100% 可达 |
| 4 | 追溯完整 | ① **功能 → 规则 → AC 链路**（每条规则在 §四 声明 `所属功能` 且所引功能必须存在于 §二；每个功能被 ≥1 条规则服务；每条规则被 ≥1 条 AC 回指。2026-09-28 补：原写作「FN→AC」但**无链路可算**，实为空头条款）、域清单↔域级文件一一对应（`增量起步` 下缺文件的域改由 ⑥ 判，见下）；② **范围形态声明合法**（闭集；`变更` 必带 `覆盖度` / `基线`；`首建` 不得带 `增量起步`）；③ **声明与 §六 表形态一致**（§六 内表头含 `处置` 列 ⇔ `变更`）；④ **最小必填集**（`增量起步` ⇒ 五/六/七；否则 ⇒ §3 全部章节且 `十一` 正文非空）；⑤ **追溯总表计数对账**（`product/prd/README.md` §二 表里的 功能/规则/AC 计数 == 按该域 `domain_code` 去重的实际数；实测七域全过期，2026-09-28 补）；⑥ **追溯总表行形态 + 未覆盖登记**（每行要么是「已覆盖」（`<slug>-prd.md` + 数字），要么是「未覆盖」（`—（未覆盖）` + `—` + 摘要含 `未覆盖（沿用实然）`）；`增量起步` 下未覆盖行数必须 ≥ 缺域级文件的域数，2026-09-28 补，`3509 §B75`）；⑦ **§五 AC 表列头**（同表含 `AC ID` 与 `回指规则`，且不得含 `样例类型`；2026-09-28 补，`3509 §B74`）；⑧ **域间依赖**（域级 frontmatter `depends_on` ⇔ 全局 §五 mermaid **实线**边集：悬空引用 / 实线子图成环 / 两者不一致 ⇒ FAIL；虚线不入判据；无声明或无 mermaid ⇒ N/A。2026-10-04 补，`3509 §B186-1`） |

**判定**：4/4 → `PASS`；3/4 → `WARN`（列整改项）；≤2 或参数 2 失败 → `FAIL`（**拒绝交付**）。

**能力覆盖的判据边界（重要）**：`变更` 形态要求「基线能力都有结论」，但基线的**能力条目没有 ID 体系**（`structure/legacy/*` 按小节组织，上一版实现更没有）⇒ 机器比对只能做到「按小节标题近似」，**误报率高**。故本条**不进校验器**，归 §8 维度 8（人工）。**落一道门之前先问「语料能不能满足它」**：`3508 §74/§75` 两次因为跳过这一步而把门落成了长期不可满足的红门。

**Waste Test（原 6 条，拆成「机器」与「人工」两栏）**：

| 原判据 | 现在归谁 |
|---|---|
| 每条规则都有 ≥1 条 AC，且每条 AC 都回指 ≥1 条规则 | **参数 4**（机器，双向） |
| 域清单与域级文件一一对应，无孤立域、无未登记域 | **参数 4**（机器） |
| 每个功能都在页面结构里有入口与结果落点 | §8 维度 9（人工） |
| 每个功能的用户流程都包含异常路径 | §8 维度 9（人工） |

## 8. 独立审查（`atlas prd review`）

本实例**按名引用** `.atlas/shared/independent-review.md` 的**骨架条款**（只审不改 / 独立结论 / 分级 / 留痕双份 / 硬口径 / 维度封闭 + 兜底 / 门禁语义 / 执行器 / §6 成本约束 / §7 校准环）——**不在此复制**；本节只声明本实例自己的四项：**维度 / fan-out / 回退环取值 / 权威输入**。

| 项 | 本实例取值 |
|---|---|
| fan-out 单位 | **不扇出**（单审查者）。理由：本节的维度 1 / 2 本身就是**跨域一致性判据**，拆开审会把它们判不了；对象是全局 `prd.md` + 域级 PRD 的**一组文档** |
| 回退环取值（闭集） | 生成阶段四段：`诊断` \| `定位对齐` \| `范围冻结` \| `逐域落地`（即 §5 的四段式；每条 finding 必须打其中一段） |
| 权威输入（缺则不得给「通过」） | `.trellis/spec/structure/` 的结构事实 + 范围冻结结论（§5 阶段 3） |
| 报告落点 | `product/prd/reviews/<日期>-<范围>/`（`README.md` + `review.json`，形态见共享契约 §3） |

**审查维度**：

1. 全局 ↔ 域级一致性（域清单、页面归属、术语、处置结论）
2. 域间联动一致性（依赖对称、共享字段口径、跨域闭环）
3. 规则 ↔ AC 双向追溯完整性
4. 需求四准则抽查（完整/无歧义/一致/可测）
5. 文案与术语一致性（**含 §6「UI 文案与真实状态一致」**：文案不得宣称未发生的行为）
6. 页面结构覆盖（每个功能都有入口与结果落点）
7. 与 `structure/` 的事实一致性（不与之矛盾）
8. **基线能力覆盖**（`变更` 形态）：基线（外部旧系统 或 本产品上一版）的每个能力在 §六 表里有结论；输出**覆盖矩阵**（机器判不了，见 §7 判据边界）
9. **Waste Test 语义项**（原参数 5 转入）：每个功能在页面结构里有入口与结果落点；用户流程含异常路径；每条 AC 是可判定的确定断言（无"适当/合理/尽快"）

**输出**（双份，形态见共享契约 §3）：人读 `README.md` 按三段式（审查总结 / 问题清单 / 优化建议），机读 `review.json` 对齐 `{ok,status,checks[]}`；每条 finding 的 `回退环` 字段取上表的四段闭集。

**本实例专属附加产物**：

1. 追溯覆盖矩阵（功能 → 规则 → AC 的落点与结论）——属人读 `README.md` 的一部分
2. **基线能力覆盖矩阵**（`变更` 形态）：基线（外部旧系统 或 本产品上一版）的每个能力在 §六 表里的结论

## 9. 与其它环的接口

| 下游 | 接口 |
|---|---|
| `atlas e2e` | 全局「页面结构全景」→ 索引页面表；「文案规范」→ 用例分片文案断言 |
| `atlas e2e` | **页面 → 分片键**；**AC → 用例上游**（用例 `prd_ref` 回指 AC ID） |
| `atlas apply` | 需求增量时**只改受影响的域 PRD 章节 + 追溯总表 + 全局范围节**，不重写全量 |

**`README.md` 追溯总表列（建议）**：
域 ｜ 域级文件 ｜ structure 模块 ｜ 页面 ｜ 功能数 ｜ 规则数 ｜ AC 数 ｜ E2E 分片 ｜ 范围摘要

**行形态（硬，2026-09-28 定，`3509 §B75`）**：每行恰属两种之一 ——

- **已覆盖**：域级文件列 = `` `<slug>-prd.md` ``，三个计数列 = 数字（机器判据 = 参数 4 ⑤）。
- **未覆盖**：域级文件列 = `—（未覆盖）`，三个计数列 = `—`，范围摘要列 = `未覆盖（沿用实然）· 基线：<取证路径或来源>`。

判据（参数 4 ⑥）：行形态非法即 FAIL；`覆盖度：增量起步` 下，**未覆盖行数必须 ≥ 缺域级文件的域数** —— 否则「本轮没覆盖哪些域」没有唯一登记点，下一条需求接手时看不出上一轮的边界。

## 10. 幂等

- 已存在的域级文件**默认不覆盖**；刷新需显式确认（`--force`）。
- 全局 `prd.md` 的刷新只允许增补与修订，不得静默删除既有章节。**显式写成 `不适用（理由：…）` 不算删除**（§3「十一」）；把整节删掉才不合法。
