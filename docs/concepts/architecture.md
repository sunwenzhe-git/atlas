# 两层正交模型：践行 Project Harness

## 原创概念：为什么我们需要 Project Harness？

在 AI 编程的理论探索与工程实践中，Atlas 原创提出了 **Project Harness（项目级工程线束）** 的概念。

* **Agent Harness 及其边界**：  
  在现代 AI 开发中，业界已经发展出针对模型会话层的 Agent Harness（围绕单次任务组装 System Prompt、工具调用链、任务状态机与短期记忆）。Agent Harness 聚焦于“如何让模型更好地完成某一个具体的编码任务”。
* **为什么项目层级必须有 Project Harness？**  
  真实的软件工程生命周期远比单次模型会话漫长。仅有工人（Agent）层级的线束，无法守护复杂软件长达数月的历史资产与系统秩序。在项目层级，开发者同样需要一套专属于人类视角、直接铸造在代码库内部、守护软件全生命周期的工程线束 —— **Project Harness**。
* **两者极少重叠，正交互补**：  
  * **Agent Harness 关注工人**：单次任务如何思考、如何调用工具；
  * **Project Harness 关注工程**：项目级应然资产（PRD/E2E/结构）如何沉淀、机器硬门禁如何把关、人机体验如何终验；
  * 两者之间只有极少部分的薄接触面（例如通过路径薄桩和工作流锚点注入规则），其余完全正交、各自独立演进。无论外部选用何种 Coding Agent，项目内部的 Project Harness 始终如一地守护代码库的秩序。

---

## 架构拓扑：两层正交平面

```
┌─────────────────────────────────────────────────────────────┐
│             项目级：Project Harness（Atlas 辖区，资产与秩序）     │
│  结构基线（代码图谱逆向） ──► 项目级 PRD（业务 AC） ──► E2E 验收总索引与分片 │
└──────────────────────────────┬──────────────────────────────┘
                               │  单向编排原语：atlas apply <需求ID>
                               ▼  （应然资产先长出来，前置而非后补）
┌─────────────────────────────────────────────────────────────┐
│             需求级：Agent Harness（执行器辖区，如 Trellis）      │
│      需求卡 (Task) ──► 业务代码编写 ──► 单元测试 ──► 任务归档      │
└─────────────────────────────────────────────────────────────┘
```

---

## 1. 项目级：应然资产层 (Atlas 辖区)

* **定义**：“这个软件是什么、业务规则有哪些、怎么算做对”；
* **内容物**：
  * **结构基线**（`.trellis/spec/structure/`）：通过 AST 与代码图谱自动抽取的实然事实；
  * **项目级 PRD**（`product/prd/`）：业务叙事与验收标准（AC）单一真相源；
  * **E2E 验收总索引与页面分片**（`product/e2e/`）：真实靶场可证伪用例；
* **特性**：
  * **跨需求持久化**：不会随着某个任务完成而被归档隐藏；
  * **机器可校验**：受 280+ 项出厂测试与门禁守护；
  * **只定应然，不写业务实现**：Atlas 契约严格约束自己“不产出业务业务代码”。

---

## 2. 需求级：任务执行层 (执行器辖区，如 Trellis)

* **定义**：“这一次迭代具体改什么、哪个 Agent 来改、怎么一步步改”；
* **执行体**：由宿主任务系统（如 Trellis、Claude Code 等）承担；
* **特性**：
  * 任务卡（`prd.md`、`implement.md`）随着开发结束而归档；
  * 会话上下文随着任务完结而重置；
  * 任务只对当前具体修改负责，没有项目全局视野。

---

## 3. `apply` 单向衔接：应然资产先行

在传统的任务执行流中，开发者常常“先写代码，写完随手写两句说明”；在 Atlas 中，这个流程被严格逆转：

1. **Phase 1.6 强约束**：需求卡被批准后、动手写代码之前，强制触发 `atlas apply <需求ID>`；
2. **三问门分流**：
   * 改动了既有系统能力？
   * 需要人类确认新的 UI 交互？
   * 该功能需要可重复自动化验收？
3. **编译应然资产**：
   * 若有任一为“是”，必须先在 `product/prd/` 中更新受影响域的 AC，并在 `product/e2e/cases/` 生成用例分片；
   * 只有应然资产编译就绪并通过全部前置门禁，Agent 才被允许进入代码编写阶段。
