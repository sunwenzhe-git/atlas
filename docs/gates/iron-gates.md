# 门禁系统 (Gates)

在 Atlas 中，“代码写完了”从来不是靠开发者或 Agent 的自述，而是取决于一套**机器对账门禁（Hard Gates）**。

## 门禁输出四态与退出码纪律

`atlas check` 逐门一行输出（格式：`ok|FAIL|WARN|SKIP|N/A  <名称>  <一句摘要>`）。**FAIL 是唯一置退出码 1 的失败态**，任一门 FAIL 即阻断流水线；而 `SKIP` 则是防「永久红门」与「静音门」的关键机制——把「还没走到这一步」与「判了不通过」彻底解耦：

| 取值 | 退出码 | 含义 | 关键纪律 |
|---|---|---|---|
| `ok` | 0 | 走到判据且通过 | —— |
| `FAIL` | **1** | 判据硬阻断（如缺少必填字段、用例语法错误、集合不相等） | **任一 FAIL 即流水线阻断退出**，不得掩盖或绕过 |
| `WARN` | 0 | 判据不置红，但必须在总览里显式可见（如结构语义列留空、影响面多报） | 不影响退出码，但不允许被就地静默掉 |
| `SKIP` | 0 | **没走到这一步**（前置未声明，如 `app_base_url` 为空、结构环未跑） | **不是通过、也不是失败**，必须带明细原因 |
| `N/A` | 0 | **整门不适用**（如无 backend app 时的后端维度门） | **不是通过**；子项 N/A 只进 detail，整门不适用才显示此行状态 |

> 💡 **“三态前置”的真实意图**：源码纪律（`3509 §B110`）强调 `生成物最新` 具有三态语义：**未就绪**（`SKIP`）≠ **生成物过期**（`WARN`）≠ **生成失败**（`FAIL`）。前置缺失只会如实给出 `SKIP` + 原因，既不报假红，也绝不当成绿灯放行。
>
> **子项 N/A（D153）**：行级仍是上表四态；校验器内部 `[N/A ]` 子项只进 detail（例如后端维度门在「当前栈不适用」时），**整门不适用**时 `atlas_check` 行状态显示 `N/A`（退出码 0）。N/A 不是通过，detail 会带原因。

## 核心对账门禁详解

> 💡 **核心对账门禁（代表性节选）**：机器侧全量总账见 `.atlas/shared/gates.md`；运行 `atlas check` 时会聚合执行全部登记校验器。

### 1. `testid` 双向集合对账门 (`validate_testids.py`)
* **断言**：用例分片中声明的应然 `testid:` 清单，与前端源码中真实扫描出的 `data-testid` **按页面双向集合严格相等**；
* 前端代码漏写了必要埋点 ──► **FAIL**；
* 前端代码多写了无用埋点 ──► **FAIL**；
* 只有集合完全相等才允许放行，杜绝测试代码与前端实现脱节。

### 2. 实例 ⑤：实现代码独立审查门（防漏审；机制与对账门已定形，外部执行器接入中，见 shared/gates.md）
* **运行机制**：需求实现完成后、归档收口前，由独立的外部只读进程执行 `git diff` 审查（Fresh Context 隔离；契约与转换器见 `scripts/cli_review_convert.py`）；
* **应审 N / 实审 M 严格对账**：
  * 实测证明：大模型在审查数十个文件的大 Diff 时，会**悄悄跳过文件**（静默少审）；
  * 审查器启动时先提取预审文件数 `N`，审查结束后统计给出 findings 的文件数 `M`。**一旦 `M < N`，不论结论多好一律报红拦截**！
  * 发现任何 `Critical` 级缺陷，一票否决收口。

### 3. 后端/全栈测试用例 ⇔ AC 跨语言对账门 (`validate_ac_alignment.py`)
* 校验后端与全栈测试用例中挂载的验收标记与 PRD 声明的 AC 集合严格对齐；具体标记语法由 `adapters/ac/` 的 extractor 定义（示例见 `docs/guide/backend-test.md`）。
* D153 起另对账测试记录的 `dims` 与 PRD 第 5 列 `后端适用覆盖维度`：缺维度 / 仅弱证据 / 零测试 / 未知 / 孤儿 ⇒ **WARN**；无 backend/fullstack app ⇒ 整门 **N/A**；未声明 `backend_test` ⇒ **N/A**；多 backend app 用统一 `test_dir` 做全局对账；apps 缺失 / 未注册 extractor ⇒ `[UNVERIFIED]` **WARN**（enforce 下 **FAIL**）；parse_errors ⇒ `[PARSE]` **WARN**（enforce 下 **FAIL**）；零挂载 ⇒ `[ZERO-COVERAGE]` **WARN**（enforce 下 **FAIL**）；扫描面非空 ⇒ `[SCAN]` **WARN**。
* 防止核心业务逻辑在实现后漏测或假挂载，支持 `advisory` 预警与 `enforce` 硬阻断模式——**`enforce` 只管 AC 挂载，维度缺口恒 WARN**。

### 4. `impact` 影响面预测对账门 (`impact_reconcile.py`)
* 在需求规划阶段，模型通过代码图谱和 AST 预测本次改动的影响面文件集合；
* 在任务收口归档时，将该预测集合与真实的 `git diff --name-only` 产生的文件列表进行自动差集比对；
* 持续暴露出模型的盲区，防止漏测边缘修改。

### 5. 设计档案豁免对账门 (`validate_design_exemptions.py`)
* 前端视觉设计若要豁免某条检测规则（例如色彩对比度特殊定制），必须在 `product/design.md` 登记 `detect:<rule-id>`；
* 校验器要求设计档案里的豁免列表与 `.impeccable/config.json` 中的实际忽略规则**双向严格相等**；
* 关掉报警必须有台账，有台账必须改配置，杜绝无台账的私自关闭。

### 6. 装配版本完整性门 (`.atlas/VERSION`)
* 目标项目中的装配态与 Atlas 源包内容摘要实时哈希比对；
* 源包升级或本地改动脱节时，自动亮出 `WARN`，防止跨项目版本漂移。

### 7. 架构决策记录对账门 (`validate_adr.py`)
* 项目级长效架构决策唯一落 `<资产根>/adr/NNNN-<slug>.md`（默认 `product/adr/NNNN-<slug>.md`，ADR 根可由 `atlas.config.yaml` 的 `layout.adr` 覆盖）；校验编号唯一、状态枚举合法、演进链闭环（`superseded` 必指有效后继）、核心章节（Context / Decision / Consequences）完整，杜绝决策散落多处或私自改写。

### 8. 独立审查报告形态与处置门 (`validate_review_report.py` + `_support/review_policy.py`)
* **形态对账**：`review.json` 与 `README.md` 双份留痕、必备键类型、分级闭集、每条 finding 带非空回退环、应审 N / 实审 M 对账；
* **v2 处置语义**（单源内核 `_support/review_policy.py`，校验器 / CLI 转换器 / 脚本生成器三方共用同一实现，杜绝两门各判各的）：
  * `fingerprint`：剥掉行号的稳定哈希——**同一问题跨轮不得重复贴**（行号漂移后指纹必须不变、内容不同指纹必须变，两侧都有钉子）；
  * `pre_existing`：存量代码缺陷**不阻断本次收口**，但状态下限抬为 `WARN`（可见、不静默放行）——实测评审约 59% 的发现落在改动前就存在的代码上；
  * `disposition`：`fixed` / `false_positive` 必须带**签字人 + 取证**才生效，否则照常阻断（防止模型自审一句话就把 Critical 关掉）；
  * **轮次收敛**：第 4 轮起必须登记 `escalation` 升级到人/架构复议——治「Agent 作者 ⇔ Agent 评审」互相忙到天亮的死循环；
  * **历史兼容**：缺省 `schema_version = 1` 沿用旧「任一 Critical 即 FAIL」语义且**不回扫存量报告**（回扫 = 永久红 = 静音门）。

### 9. AC × 覆盖维度门 (`validate_e2e_index.py` 内的一行)
* 域级 PRD §五 可选第 4 列声明每条 AC 的适用维度（`C01`–`C14` E2E 闭集），用例分片 `覆盖维度:` 声明打击面，校验器算差集；
* 缺维度 ⇒ `WARN` 点名；写了词表外形态（如 `C15`）⇒ `WARN` 出声；**未声明 ⇒ `N/A`**，不给存量项目凭空造红门；
* **第 4 列 = E2E 通道；后端列 `后端适用覆盖维度` 归 `validate_ac_alignment`（D153），本门不读、不并集**；
* 它补的是「反向覆盖门」的语义盲区：从「有没有用例」升级到「失败面有没有被覆盖」。

## 人侧收口清单（`shared/closeout.md`）：机器判不了的那些

机器侧总账回答「门还在不在、咬不咬」，人侧清单回答「还有哪些事没人做」。两者必须在**同一轮**跑完。

* **步骤 3 变更风险定档**：低 / 中 / 高三档按**改动面而非作者**定档；`auth / permission / routing / CI / package deps / shared contracts` 属 **Always-Human 路径**——无论什么需求类型，一律禁止 Agent 代勾放行；
* **步骤 4 缺陷修复验证 7 检查点**：含 **Red First**（先有一条会失败的测试，再写修复代码）、「最小 diff」、「关闭的证据在哪」；
* **步骤 11 事故追问**：每个逃逸缺陷必须回答「**哪一层本该接住它？为什么没接住？**」，并落成一条 E2E 回归用例或一条 M 系列变异钉——事故就此变成永久评测集。
