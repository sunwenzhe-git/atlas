# 技术纵深：语义透镜 (FRAS) —— 仓内语义行替代外部图谱

跨文件影响分析的经典做法，是外挂一个静态图谱引擎（AST 解析 + 图数据库）。Atlas 走过这条路，然后在真实采纳仓的前后端实测中把它退役了：**AST 调用边在前端与现代后端两条主栈上同时失效**——前端 JSX 组件的渲染引用不产生调用边（改组件报不出「哪些页面在用」），现代 Java 后端被 Spring DI / 泛型 Mapper / 线程池异步 / RPC 四重截断。图谱引擎买来的拓扑，覆盖不了最需要它的地方。

退役之后，影响分析的输入换成了**仓内两级轻量语义行（Scope-Aware FRAS）**：

* **业务域内**：`current/<域>/cognition.fras`；
* **跨切面共享设施**：`global/cognition.fras`（axios、auth、hooks、router 等被各域引用的公共件——此前它们是「孤儿」，没有任何域能收编）。

每行是 `路径[TAG]: F:功能 | R:依赖 | A:预期 | S:硬约束` 的紧凑语义行，由采纳仓的评测管线 / 人工增量维护，**atlas 只读不产**。单源分工：apis/models 维持实体事实，FRAS 专管穿透拓扑（R）与防改崩硬约束（S）。

```
  .atlas/spec/structure/ 两级语义行
    global/cognition.fras        ← 跨切面共享设施（auth / axios / hooks / router）
    current/<域>/cognition.fras  ← 各业务域语义行
       │  F/R/A/S 紧凑行，atlas 只读不产
       ▼  反向 1-hop：谁的 R 边指向本次触达的文件集（adapters/_graph.py）
  impact_report 候选面（aoci_candidates 独立字段，不入传统对账集）
       │
       ▼  收口时
  impact_reconcile 对账门：预测集 ⇔ 实际 diff 双向差集，漏报/多报 WARN 逐文件指名
```

**能力边界照实讲**：

* **一跳就停**：多跳传递面归 agent 语义判断，机器只给候选不替人拍板；
* **语义行漏写 ⇒ 反查漏报**：由收口对账门兜底（双向差集 WARN 指名，不得静默对账）；
* **未维护透镜行 ⇒ `not_ready`**：影响面基准退化为需求卡声明集——诚实缺省，不装有。

---

## 为什么不是「更好的图谱」

实测结论不是「图谱引擎不够好」，而是「调用边这个抽象在这个问题上是错的」：真正决定「改这里会不会坏那里」的穿透关系（DI 注入、异步投递、渲染引用），恰恰是 AST 静态分析看不见的那部分。与其维护一个昂贵的低覆盖索引，不如把**高价值的少量穿透关系显式写成语义行**，再配上对账门保证它不说谎——覆盖度人工控，正确性机器审。

退役也不等于删子系统：`adapters/_graph.py` 保留为透镜辅助层（解析 + 反查 + 旧引擎兼容探测），两个消费者（影响面候选面、收口对账）与对账门纪律原样运转——换的是「图的来源」，不是治理面。
