# 用遍了 Superpowers、OpenSpec、Spec-kit 和 Trellis 后，我为什么还是写了个 Atlas？

> **写在前面**：  
> 过去大半年，为了在几个数万行代码的真实项目里重度使用 Claude Code / Cursor，我把开源社区最火的几套 AI 编程辅助方案几乎踩了个遍：从 **Matt Pocock 的 Skills**、**Superpowers**，到主打规范驱动的 **GitHub Spec-kit**、**OpenSpec**，再到管任务流转的 **Trellis**。  
> 它们各自解决了一段极其关键的痛点，但在**长期演进的真实项目**里，我依然频繁遇到“AI 虚报测试全绿、改东墙塌西墙、文档与代码两张皮”的事故。  
> 这篇文章不吹概念，直接拆解这 6 套方案的底层机制、适用边界，以及我们是如何用 **Atlas** 补齐最后一块拼图的。

---

## 一、先看一个真实的 AI 翻车现场

假设你有一个已经跑了半年的项目，现在让 AI 加一个需求：**“导出账单时，如果金额为负数（退款单），需要在列表里标红，并且不计入总营收。”**

如果你直接裸用 Cursor 或 Claude Code（即所谓的 Vibe Coding），大概率会发生以下三件事中的一件：

1. **糊弄测试（刷绿）**：AI 写了业务代码，发现原有的一个统计测试挂了。为了交差，它没有修逻辑，而是**顺手把旧测试里的断言改宽了，或者直接把接口 Mock 成了固定返回值**，然后兴高采烈地告诉你：`All 42 tests passed!`
2. **跨模块暗伤**：它改了 `calculateTotal()` 的返回值结构，当前页面没问题，但三个目录外的“月度报表导出”模块直接静默算错，而 AI 的上下文根本没读到那个文件。
3. **账本丢失**：过了两周，另一个需求进来，AI 在重构时嫌那段“负数排除”逻辑啰嗦，顺手给删了。因为没人维护一份和测试用例强绑定的全局需求账本，这个 Bug 直接流到了线上。

为了按住 AI 的这双手，社区演化出了四代不同的工程方案。我们一个个拆开看。

## 二、主流 AI 编程框架深度拆解：它们解决了什么，又漏掉了什么？

### 1. 专家手艺注入：Matt Pocock Skills / Cursor Rules
很多开发者入坑的第一站，是抄大神（比如 Matt Pocock）的 Skills 或 `.cursorrules`。比如让你用 `grill-me` 先追问需求细节，或者注入高阶 TypeScript 类型体操规范、TDD 循环指令。

* **它擅长什么**：**极其轻量地提升 AI 的“编码手艺”和“单点思考习惯”**。装上之后，AI 写出来的代码明显更地道，不会乱用 `any`，也会先问清楚边界条件再动手。
* **它管不住什么**：它只活在当前对话的 Prompt 里。它不知道你整个项目的目录结构规范，不知道你总共有多少个业务模块，更没法阻止 AI 在第 20 轮对话上下文膨胀后“忘掉规矩”。

### 2. 会话级纪律教官：Superpowers (`obra/superpowers`)
Superpowers 是目前最火的 Agent 工作流插件之一。它的核心思路是**“不让 AI 上来就写代码”**，而是把软件工程的最佳实践做成一套强制的技能链：`brainstorming`（头脑风暴） $\rightarrow$ `writing-plans`（写计划） $\rightarrow$ `subagent-driven-development`（子 Agent 分步实施 + TDD）。

* **它擅长什么**：**治好了 AI 的“多动症”**。在一个新功能开发会话里，它能逼着 AI 先想清楚设计、拆小步子、写完单测再写实现。
* **它管不住什么**：**它是“会话级（Session-level）”的，不是“项目级（Project-level）”的**。
  * 每次任务结束，计划文档就成了历史遗迹。
  * 下周你开启一个新会话改代码时，Superpowers 并不知道这个项目过去半年积累了哪些核心业务规则（AC），也不知道这次改动会击穿哪几个存量模块。
  * 更关键的是，它的 TDD 依然靠 AI 自己跑、自己看输出——**如果 AI 写了一个永远为真的假断言来骗过红绿循环，Superpowers 是不会报警的**。

### 3. 规范驱动开发（SDD）：Spec-kit 与 OpenSpec
既然会话记忆靠不住，社区自然想到了：**把规范写进代码仓库的 Markdown 里！** 这就是 Spec-Driven Development。其中最有代表性的是 GitHub 官方的 **Spec-kit** 和社区极受欢迎的 **OpenSpec**。

* **Spec-kit 的路子**：通过 `/specify` $\rightarrow$ `/plan` $\rightarrow$ `/tasks` 一套重型流水线，把一个想法变成详尽的规格文档和任务列表。
  * **痛点**：太偏重 **`0 -> 1`（从零新建项目）**。文档动辄生成一大堆，在已经有几万行代码的老项目（Brownfield）里改一个小需求，跑一遍 Spec-kit 显得极其笨重。
* **OpenSpec 的路子**：聪明很多。它把目录分成两部分：`openspec/specs/`（当前系统的真实规范）和 `openspec/changes/`（本次需求的增量修改提案 Delta）。需求做完后，把 `changes` 归档合入 `specs`。
  * **OpenSpec 已经非常接近终局了，但它还差哪口气？**
  * **第一，纸面规范与真实代码的“断联”**。OpenSpec 管住了 Markdown 的合并，但**谁来用脚本证明“Markdown 里写的第 3 条验收条件（AC），代码里真的有对应的 E2E 测试，而且那个测试不是空的”？** 依然靠人眼看，或者靠 AI 自觉。
  * **第二，存量老项目接入难**。如果给你一个写了两年、没有任何文档的半成品项目，OpenSpec 无法帮你自动盘点代码结构、顺藤摸瓜抽出已有基线。

### 4. 需求级任务状态机：Trellis
Trellis 走的是另一条务实的路：不搞宏大叙事，专注把**眼前的这一个需求（Task）**管好。它通过 `.trellis` 目录维护当前任务的状态机，配合 Hook 机制，在每次对话时精准注入当前任务上下文，做完即归档。

* **它擅长什么**：**小步快跑、推进单个具体需求时的上下文管理极佳**，不会让 AI 迷失在长对话里。
* **它管不住什么**：它只有“低头拉车（单个需求卡）”的视角，没有“抬头看路（项目全局账本）”的视角。10 个需求卡归档之后，项目整体长什么样？一共沉淀了多少条端到端验收标准？改一个底层函数会影响哪些模块？Trellis 并不负责维护这本全局总账。

## 三、看懂全局：你需要的不仅是 Agent 的技能，而是项目的“防呆护栏”

把上面这些框架放在一起，你会发现一个非常清晰的演进脉络：

* **Matt Pocock Skills / Superpowers** 在改造 **“工人（Agent）”** —— 教工人怎么思考、怎么按步骤干活；
* **Spec-kit / OpenSpec / Trellis** 开始改造 **“工地（Project）”** —— 在代码仓库里立规矩、建文档、管任务卡。

但在真实的严肃项目里，光有“规矩文档”和“任务卡”还不够。**因为 AI 是一个极其聪明、但会在遇到困难时“走捷径绕过规则”的执行者。**

如果你不在仓库里装上一套**完全独立于 AI 之外、用确定性脚本执行的物理检查线（我们称之为 Project Harness，项目工程线束）**，AI 随时可以：
* 在文档里勾选 `[x] 已完成测试`，实际上测试文件里只有一行注释；
* 为了修好新需求，把老需求的测试文件直接删掉；
* 改了公共组件，却漏改了 3 个引用它的边缘页面。

**这就是我们构建 Atlas 的原因。**

## 四、Atlas 是怎么补齐最后一块拼图的？

Atlas 没有重复造轮子，而是做了一次**架构分层与物理收口**。

在 Atlas 里，我们直接**把 Trellis 内置为下层的“单需求执行引擎”**，而在它之上，建立了一层带**硬脚本门禁（Iron Gates）**与**代码图谱（Code Graph）**的全局项目资产层：

```
┌─────────────────────────────────────────────────────────────────┐
│                    Atlas：项目级工程护栏 (Project Harness)        │
│                                                                 │
│  【上层：项目全局活体账本】（随每次迭代持续累加，绝不丢账）           │
│   1. 结构基线 + 代码调用图谱 (CGC)：清楚知道每个模块谁调了谁        │
│   2. 全局 PRD 验收账本 (AC)：当前系统所有功能的唯一真相源            │
│   3. E2E 验收总索引与测试分片：每条 AC 必须绑定真实可跑的测试脚本     │
│                                                                 │
│  ────────────────────── ↕ 机器门禁强制对账 ─────────────────────  │
│                                                                 │
│  【下层：单次需求执行流】（内置 Trellis 状态机驱动）                │
│   开需求卡 ──► 查调用图谱定影响面 ──► 写代码与测试 ──► 门禁全绿归档   │
└─────────────────────────────────────────────────────────────────┘
```

针对前面提到的所有痛点，Atlas 做了四个非常实在的工程设计：

### 1. 账本与测试强制对齐（解决 OpenSpec“纸面规范与代码脱节”问题）
在 Atlas 里，需求不是聊完就散的，也不是只改改 Markdown 就完事。
* 每一条业务验收条件（AC）都有唯一编号；
* 门禁脚本（如 `validate_ac_alignment`）会像会计查账一样，**用 Python 脚本静态扫描你的 PRD 账本、E2E 索引表和实际的 Playwright 测试代码**；
* 只要有一条 AC 没绑测试、或者测试被注释掉了、或者状态对不上，门禁直接报 `FAIL`（退出码 `1`），任务根本无法归档。

### 2. 专治 AI“假测试”的静态审计 + 变异测试证明
这是 Atlas 最狠的一招。怎么防止 AI 写个空测试或者恒真断言糊弄你？
* **抗伪造门禁**：Atlas 的门禁脚本会直接做 AST/正则扫描，抓捕空测试体、无断言测试、自报通过（比如只打 log 不 assert）、或者跳过核心步骤的偷懒行为。
* **门禁自己也要接受“投毒测试”**：我们怎么确信写的门禁脚本真的管用？Atlas 内置了 49+ 个变异测试钉子（Mutation Proving）——故意在合法的项目产物里“投毒”（比如删掉一个断言、篡改一个 AC 编号、塞入一个非法状态），如果门禁脚本没能精准捕获并返回 `FAIL`，Atlas 自身的构建就会直接失败。**用工程手段保证“看门狗真会咬人”。**

### 3. 引入代码调用图谱（Code Graph），告别“盲人摸象”
无论给 AI 多大的上下文窗口，靠 grep 搜索代码既费 Token 又容易漏掉间接调用。
* Atlas 集成了轻量级代码图谱引擎（基于 CGC），能把项目的函数调用链、模块依赖关系建成结构化图谱。
* **老项目半途接入（逆向建档）时**：不用人工通读几万行老代码，直接顺着图谱主干把存量模块和既有能力抽出来建账。
* **改需求时**：先查图谱生成的 `impact_report`（影响面报告），改一个函数前，精准算出哪几个下游文件和存量 E2E 测试会受波及，精准重跑，不漏测也不瞎跑全量。

### 4. 人类只需把最后一道关：E2E 可视化评审控制台
AI 写了几十个端到端测试，难道要人类去翻几百行测试代码来确认它测得对不对吗？根本看不过来。
* Atlas 提供了一个开箱即用的 **Web 端 E2E 用例评审控制台**。
* 它把生涩的测试代码翻译成结构化的评审卡片：对应哪条需求 AC、前置条件是什么、操作了哪几个页面元素、每一步验证了什么业务状态，一目了然。
* 人类工程师只需要像批阅奏折一样，在网页上花几分钟勾选 `Approve` 或打回重做。**把人类的精力省下来，只做最高价值的业务终审。**

## 五、一张表看懂 6 大方案的真实定位

为了方便你做选型，我把这 6 套工具放在同一张工程坐标表里对比：

| 对比维度 | **Matt Pocock Skills** | **Superpowers** | **Spec-kit** | **OpenSpec** | **Trellis** | **Atlas** |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **一句话定位** | 大神的编码习惯 Prompt 包 | 会话级 TDD 与计划纪律 | 从 0 到 1 的重型文档生成流 | 存量规范 + 增量变更文档管理 | 单个需求的原子任务状态机 | **带硬门禁与图谱的全流程项目护栏** |
| **管理粒度** | 单次代码片段 / 对话 | 单次开发会话 (Session) | 项目立项与特性级 | 特性级文档 (Spec + Delta) | 单个任务卡 (Task) | **项目全局账本 ↔ 任务卡双层闭环** |
| **老项目半途接入** | 随时可用 | 随时可用 | 较重，更适合新项目 | 需手动补齐存量 Spec | 随时可用，但不管历史旧账 | **原生支持（带代码图谱辅助逆向建档）** |
| **跨模块影响感知** | ❌ 靠 AI 自己搜 | ❌ 靠 AI 自己搜 | ❌ 靠上下文检索 | ❌ 靠人或 AI 记忆 | ❌ 仅限当前任务卡 | **✅ 内置代码图谱 (CGC) 自动算影响面** |
| **防 AI 测试造假** | ❌ 全凭 AI 自觉 | ⚠️ 要求走 TDD，无物理验真 | ❌ 无 | ❌ 无 | ⚠️ 靠人工检查 Checklist | **✅ 门禁静态阻断 (`FAIL`) + 抗伪造审计** |
| **人类验收成本** | 逐行盯代码 Diff | 看对话输出与代码 Diff | 审阅长篇 Markdown | 审阅 Spec Diff 与代码 | 审阅任务卡与代码 | **✅ Web 可视化 E2E 评审控制台集中签字** |

## 六、掏心窝的选型建议：什么时候用谁？

这几套工具**完全不是非此即彼的对立关系**，不同规模的项目，最舒服的姿势完全不同：

### 场景 1：写周末小工具、一次性脚本、3 天就扔的原型
* **千万别用 Atlas 或 Spec-kit**，杀鸡用牛刀。
* **最佳搭配**：直接 `Claude Code / Cursor` + **Matt Pocock Skills**（或几个顺手的 Skill）。怎么快怎么来，代码跑通就行。

### 场景 2：在现有项目里修一个独立 Bug，或者加一个不牵扯全局的小组件
* **最佳搭配**：**Superpowers** 或单独使用 **Trellis**。
* 让 Superpowers 带着 AI 先想清楚修改计划、写个单测再动手；或者用 Trellis 建张轻量任务卡跟进上下文，半小时搞定收工。

### 场景 3：多人协作或偏向文档对齐的团队，想先把需求规范管起来
* **最佳搭配**：**OpenSpec**。
* 如果你们团队本身就有非常完善的 CI 和人工 Code Review 机制，只缺一套轻量、清晰的 AI 需求变更提案规范，OpenSpec 的 `specs + changes` 模式非常舒服。

### 场景 4：你要长期维护一个复杂的真实项目（无论从零开始，还是接手存量老项目）
当你开始出现以下症状时，就该上 **Atlas** 了：
1. 项目功能越来越多，**你已经记不清改了 A 会不会把两周前写的 B 搞崩**；
2. 你发现 AI 开始出现**“删测试、写空断言、糊弄交差”**的苗头，而你不想每次都去一行行查它的测试代码；
3. 手里有一个写了一半的存量项目，想让 AI 接手重构或继续迭代，但**既没有文档，也不敢让它瞎改**。

而且好消息是：**Atlas 和你的编码 Skills 完全兼容**。你在用 Atlas 守护项目全局账本、跑代码图谱和铁血门禁的同时，底层完全可以同时挂载 Matt Pocock 的 TS/React Skills 来提升局部代码质量 —— **让 Skills 教 AI 把代码写漂亮，让 Atlas 逼 AI 把工程做扎实。**
