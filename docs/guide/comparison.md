# AI 编程工程化：生态分层地图与选型指南

> **写在前面**：  
> 在真实的大中型项目里重度使用 Claude Code / Cursor 时，很多工程师都踩过类似的坑：AI 虚报测试全绿、改东墙塌西墙、换个会话就忘记历史约定。  
> 过去一年，开源社区涌现出了大量优秀的辅助方案：从 **Matt Pocock 的 Skills**、**Superpowers**，到 **GitHub Spec-kit**、**OpenSpec**，再到 **Trellis** 以及我们自己探索的 **Atlas**。  
> 很多文章喜欢用“一代淘汰一代”的公关话术来制造对立。但站在严肃工程视角，**这些工具切入的是软件工程完全不同的抽象层级，它们不是非此即彼的替代品，而是可以正交组合的积木。**  
> 本文旨在抛弃拉踩与营销词汇，客观拆解各方案的定位、解决的核心问题、非设计目标与真实代价，并给出务实的选型建议。

---

## 一、真实痛点：为什么单靠对话容易在长周期项目里翻车？

让 AI 辅助开发一个小脚本或新页面通常非常流畅，但当项目演进到数万行、维护了几个月之后，让 AI 接手一个改动时，往往会遭遇三类典型事故：

1. **测试造假与虚假安全感**：AI 修改了业务逻辑，发现原有的某个回归测试挂了。为了完成当前会话，它可能会悄悄**改宽旧测试的断言、把接口 Mock 掉，甚至写出无断言的空测试**，然后向你汇报 `All tests passed`。
2. **跨模块隐式暗伤**：修改了一个底层通用模块的返回结构，当前页面表现正常，但三个目录之外依赖该接口的报表逻辑被静默破坏，而 AI 单次调用的上下文根本检索不到那个文件。
3. **长期约束与账本丢失**：经过几周、数十轮迭代后，AI 在重构时误删了某条早期沉淀的业务边界规则。因为缺乏全局可对账的业务真相源，这个疏漏很容易直接流入生产环境。

针对这些问题，社区在不同层面上探索了各自的解法。

## 二、AI 编程工程生态的四层架构分层

为了看清各工具的真正分工，我们可以将当前的 AI 编程工程化实践划分为四个正交的层级：

```
┌─────────────────────────────────────────────────────────────┐
│  L4. 全局治理与机器门禁层 (Governance & Machine Gates)         │
│      关注：全局 PRD/AC 账本对账、影响面反查、硬脚本物理阻断           │
│      代表：Atlas、团队自建的严格 CI/ArchUnit/变异测试流水线      │
├─────────────────────────────────────────────────────────────┤
│  L3. 规范与任务状态机层 (Spec & Task State Machine)            │
│      关注：规范变更提案 (Spec Delta)、单任务上下文隔离与状态流转    │
│      代表：OpenSpec、Trellis、Spec-kit                       │
├─────────────────────────────────────────────────────────────┤
│  L2. 会话纪律与思维链层 (Session Discipline & TDD)           │
│      关注：单次开发会话内的思考步骤，强制先想后写、小步 TDD 步长      │
│      代表：Superpowers (obra/superpowers)                   │
├─────────────────────────────────────────────────────────────┤
│  L1. 代码工艺与工匠规则层 (Language Craft & Rules)             │
│      关注：单次代码生成的品味、类型收窄、反向需求追问               │
│      代表：Matt Pocock Skills (grill-me 等)、.cursorrules    │
└─────────────────────────────────────────────────────────────┘
```

* **L1 改变的是“工人的手艺”**：教模型写出规范的 TypeScript，或者在动手前反向盘问；
* **L2 规范的是“工人的动作”**：约束单次会话里必须走头脑风暴 $\rightarrow$ 写计划 $\rightarrow$ 单测驱动开发；
* **L3 沉淀的是“施工的图纸与任务单”**：把需求落盘为 Markdown 规范，或用任务卡做上下文隔离；
* **L4 建立的是“工程的物理安全网”**：用可执行的机器门禁与影响面对账，强制对齐全局资产，防止敷衍实现。

## 三、主流方案深度拆解：解决什么、放弃什么、代价是什么？

### 1. 代码工艺层：Matt Pocock Skills / Cursor Rules
以 TypeScript 领域知名专家 **Matt Pocock** 开源的 Agent Skills（如名噪一时的 `grill-me`）和社区各路 `.cursorrules` 为代表。

* **它解决的核心痛点**：
  * **单兵代码质量立竿见影**：通过专业的 Prompt 指令，立竿见影地提升局部代码品味，减少 `any` 滥用或低级语法失误；
  * **反向刺破隐式假设**：通过类似 `grill-me` 的追问模式，在动手前反向逼问用户边界条件，避免想当然的设计。
* **它的非设计目标（故意不做的事）**：
  * 它不维护项目级长效账本。Skill 本身是持久落盘的配置，但它注入的是**通用的工艺规则**，不包含当前项目沉淀了哪些具体的业务验收标准（AC）或架构决策（ADR）；
  * 它属于提示词维度的软性引导，本身不自带退出码（Exit Code 1）级别的物理阻断（如需硬拦截，需另行搭配 Hooks 或 CI）。
* **主要代价**：依赖模型的遵守概率，上下文过长时容易稀释；纯靠 Prompt 反问有时会抛出过多常识性问题，带来交互疲劳。

### 2. 会话纪律层：Superpowers (`obra/superpowers`)
Superpowers 专注于规范单个开发会话的思维与执行链，核心理念是“不让 AI 上来就写实现代码”。

* **它解决的核心痛点**：
  * **治愈 AI 的“多动症”**：强制按照 `brainstorming` $\rightarrow$ `writing-plans` $\rightarrow$ `subagent-driven-development` 步长推进；
  * **强制落实 TDD**：要求 AI 先写出失败的单元测试，再编写实现代码让其变绿。
* **它的非设计目标（故意不做的事）**：
  * 它是**会话级（Session-level）**的工具，聚焦单次任务的高质量交付。任务归档后，它不负责在跨周期的多会话间维护全局系统的活体依赖与跨模块波及面；
  * 它的 TDD 依然依赖 AI 在会话内的自主解释，没有外挂专门针对“假测试/空断言”做 AST 级别的抗伪造静态审计。
* **主要代价**：开发流程相对严谨，对于简单的单行修复会有一定的流程开销。

### 3. 规范驱动开发：Spec-kit 与 OpenSpec
将软件工程实践中的规范驱动（Spec-Driven Development）引入 AI 时代。

* **Spec-kit**：通过完整的规格定义到任务拆解流程，适合新项目从 0 到 1 的顶层规格设计。在老项目小迭代中相对较重。
* **OpenSpec**：设计非常巧妙，将目录划分为 `specs/`（存量规范）和 `changes/`（增量变更提案 Delta）。
  * **优势**：轻量优雅，天然支持团队协作中的规范审阅（Spec Review），用标准的 Markdown 建立了清晰的需求版本化机制。
  * **非设计目标**：OpenSpec 的定位是**规范文档的生命周期管理**，它本身不提供代码级静态分析工具去自动验证“某条 Markdown AC 是否在代码里对应了真实的测试脚本”。代码与规范的对齐仍需人眼 Review 或团队自建 CI。（2.0 的扩展工作流提供可选的 `openspec-verify-change` 技能，由 AI 以关键词搜索与推断检查实现完成度与场景覆盖，但它自身定位为建议性：缺测试覆盖只记 WARNING，不阻断归档。）
* **主要代价**：需要团队形成书写和维护 Spec 的习惯；老旧项目如果没有任何文档，前期补齐 Spec 成本较高。通用模板为广泛适用而刻意保持精简，落到需要 AC 编号、测试映射这类细粒度约束的项目时，需要团队自行加厚；我们早期实际采用时也观察到：改动一旦不走提案流程，specs 会逐步与代码漂移。

### 4. 任务状态机：Trellis
Trellis 专注于管理**“当前进行中的这一个需求（Task）”**，通过 `.trellis/` 维护任务状态机与任务卡片。

* **它解决的核心痛点**：
  * **上下文精准隔离**：在复杂长对话中，防止无关信息污染模型窗口；
  * **小步快跑体验极佳**：开卡、执行、检查、归档，流转非常丝滑，极大地降低了单次人机协作的心智负担。
* **它的非设计目标（故意不做的事）**：
  * Trellis 的核心设计哲学是**轻量与低摩擦**。它刻意不去做跨任务的全局调用图谱计算，也不维护全系统维度的业务验收总账。
* **主要代价**：随着归档任务越来越多，它不直接回答“这 30 个任务做完后，全系统目前到底有哪些活体业务规则，改动 A 会影响哪个旧任务的功能”。
* **现状（2026-11-19 核实）**：Trellis 已停更——最后一次 push 为 2026-09-29，89 个 open issues 未收（仓库未 archive）；其 fork mini-trellis 转向记忆管理，工作流这半边无人接手。另需注意其采用 **AGPL** 协议：fork 不能换证，企业推广场景通常一刀切回避。上文对其设计的评价依然成立（流程编排半边它打磨得最好），但已不宜作为新项目的选型。

## 四、Atlas 是什么：补上「判分」这半边

把上面几层放在一起看，生态其实已经分成两半：**流程编排这半边——拆任务、管流转、注入上下文——已有成熟产品，Trellis 是打磨得最好的**；但**判分这半边——资产账本、机器对账门、门禁自证、真跑终验——至今没有产品。Atlas 做的就是这半边。**

### 1. 为什么不是「把开源工具组合起来」
这三条路我们都真走过：
* **纯开源组合**（OpenSpec 管 spec、Superpowers 管会话、Skills 管工艺）：每个工具只专注一个环节，越专越通用；但环节之间的组合适配要使用方自己付，而且是持续成本——任意一环被替换或大版本升级，全流程的接缝都得重新适配。更关键的是，每个工具在自己的辖区里都「看起来做对了」，而第一节那三类事故恰好发生在接缝处。逐工具的缺口是各自的**设计边界**，不是 bug；而这些工具的输出全是文档和纪律、消费全靠人和模型的自觉——**组合 N 个自觉，得到的还是自觉，不会凭空长出判分面**；
* **宿主在开源上打补丁**：Atlas 一代版本以 Trellis 为下层任务执行依赖，光挂在它 workflow 上的补丁包就有四个。Trellis 停更后（见 §三.4），补丁面随之报废——移除它时，依附它的六条设计决策一并作废（D205）；AGPL 在企业推广与法务合规场景中通常被一刀切回避；
* **只自建缺的那块判分面**（即现在的 Atlas）：Playwright、AST 工具沿用开源，模型用现成的；判分三件——账本由资产先行强制、退出码卡在收口点、变异自证进合入门禁——必须长在流程骨架上，插件补不上，所以流程半边由自建执行层接管。

### 2. 架构定位：自建执行层 + 两道全局护栏
Atlas 不再依赖 Trellis，需求级执行由内置的 **`atlas workflow`** 四步闭环承担（干净室自建）：
* **单任务流转**：`plan`（拆卡，任务账本落 `.atlas/tasks/`）→ `dispatch`（出派工单，按改动路径只注入命中的结构事实、testid 薄桩与约定规范）→ `verify`（独立审查）→ `finish`（收口）；`status` / `run` 负责查账与串联。写码本身由宿主 Coding Agent（Claude Code / Cursor 等）完成，Atlas 不侵入业务实现；
* **Atlas 的判分职责**：在任务的开始和结束点，套上两道全局护栏：
  1. **开工前**：经 `atlas-apply` 先把需求编译进 PRD/AC 账本（资产先行）；影响面候选由仓内两级语义透镜 **FRAS** 反查（`global/cognition.fras` + `current/<域>/cognition.fras`；atlas 只读不产，由采纳仓维护；未维护则诚实报 `not_ready`，影响面基准退化为需求卡声明集）。早期的外部代码调用图谱集成已退役（D202）；
  2. **收口前**：`verify` 由只读、fresh context 的独立进程审 diff（应审 N / 实审 M 对账）；`finish` 归档前检查审查报告 PASS 且范围新鲜、E2E red 阻断、结构事实新鲜度；impact 对账在收口环节运行，漏报/多报为 WARN，不自动阻断 `finish`；PRD 验收标准（AC）与真实测试的对齐问题以退出码 `1` 显式暴露（如无主 AC、无豁免跳过）。

在四层图里，Atlas 的本体在 L4（判分半边），同时自带 L3 的需求落点与任务状态机（被宿主停更逼着接下的执行层）。

```
┌─────────────────────────────────────────────────────────────────┐
│                 Atlas：Project Harness（判分面）                  │
│                                                                 │
│  【项目全局活体资产】                                           │
│   • 全局 PRD 验收总账 (AC) ── 业务单源事实                      │
│   • E2E 验收总索引 ── 每条 AC 必须绑定真实可跑的测试脚本         │
│   • 语义透镜 (FRAS) ── 仓内语义行反查影响面（atlas 只读不产）    │
│                                                                 │
│  ──────────────── ↕ 机器门禁强制对账（退出码级）──────────────── │
│                                                                 │
│  【单任务执行层】（自建 atlas workflow 四步闭环）                │
│   plan ──► dispatch ──► 编码与测试 ──► verify ──► finish 归档    │
│   拆卡     按路径注入    宿主 Agent     独立审查    收口检查      │
└─────────────────────────────────────────────────────────────────┘
```

### 3. Atlas 的具体机制
* **AC 与测试强制对齐**：门禁分两条轨。后端轨由 `validate_ac_alignment.py` 对测试做 AST 级挂载对账——测试挂载不存在的 AC ID、或被 skip/xfail 却无豁免理由，直接 `FAIL`（退出码 `1`）。Web 轨由 `validate_e2e_index.py` 与脚本生成器守护用例与 AC 的关联：「这条 AC 有没有用例指向」的 AC 反向覆盖目前仍为 `WARN` 级（豁免落点定形后升 FAIL）；在此之上叠加 **AC × 覆盖维度矩阵**（闭集 `C01`–`C14`：正常流 / 异常流 / 边界值 / 权限 / 并发 / 重试 / 审计 / 会话恢复 / 数据一致性 / 依赖容错 / 幂等 / 输入校验 / 状态转换 / 安全）——PRD 验收标准表第 4 列 `适用覆盖维度` 已声明但用例未全覆盖 ⇒ `FAIL` 逐条点名缺口，词表外写法（如 `C15`）⇒ `FAIL`，未写第 4 列的项目 ⇒ `N/A` 兜底；后端通道（第 5 列）的维度缺口只 `WARN`。
* **抗伪造审计与门禁自证**：在用例账本与脚本生成链路上拒绝无断言、纯跳转、瞬时断言类用例；同时采用变异测试证明（Mutation Proving）机制验证自身门禁的拦截能力——每条新门禁必须附带「故意注入脏数据、它必须报红」的变异钉才能合入。
* **本地 E2E 评审控制台**：`atlas console`（`127.0.0.1:4190`，纯 Python 标准库）在真实应用上有头慢动作回放用例；脚本执行通过才解锁「人工 Review」（状态机锁）；评审绑定内容指纹，用例内容一变勾就作废；人确认提交后，用例沉淀为黑盒回归。

### 4. 客观承认：Atlas 的边界与代价
Atlas 绝不是一个银弹，它带来了非常显著的工程代价：
1. **心智负担极重**：要求对每项需求维护严格的 AC 编号与测试映射，多人协作和轻量修改时**摩擦力极大**；
2. **浏览器级 E2E 是 Web 单轨，「自动化验收」却是双通道**：端到端用例与评审控制台基于 Node + Playwright、面向 Web UI；CLI / 移动端 / 嵌入式没有浏览器级 E2E 联动。但后端与全栈项目走独立的 **AC 对账门禁**（`validate_ac_alignment.py`：无主 AC 与无豁免跳过直接 `FAIL`、覆盖对账、差量防退化；提取器由 `adapters/ac/` 注册，当前内置 pytest、Vitest/Jest、JUnit 5，并支持外部 extractor 命令，其它栈未注册时报 `[UNVERIFIED]`），且纯后端项目的前端 testid 门会因无前端抽取源自动进门控态放行（`N/A`）——账本、结构事实、ADR、语义透镜等治理能力全栈可用；
3. **依赖栈较多**：运行需要 Node.js 18+ 与 Python 3.10+ 两个环境；可选维护语义透镜行（cognition.fras）以启用影响面反查，不维护则该平面诚实 `not_ready`；
4. **开箱整合度仍在追赶**：流程编排半边是被一代宿主的停更逼着接管的，开卡、流转、归档的开箱整合度仍在追 Trellis 当年的水准——这是已认的差距；
5. **项目成熟度**：目前处于 `0.4.0-beta.9` 阶段（以 `package.json` 为准），beta 成熟度，属于探索性开源工程，生态和稳定性与主流项目仍有差距。

## 五、生态选型权衡与代价矩阵（Trade-offs Matrix）

| 方案 | 核心定位与设计目标 | 核心优势 | 故意放弃的非设计目标 | 主要代价与反噬 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Matt Pocock Skills** | **L1 工艺层**<br>大神编码手艺与反思规则 | 极轻量，即插即用，显著提升 TS 等语言的局部单次输出品质 | 不维护项目级需求账本，不提供退出码物理阻断 | 随长上下文可能稀释，多轮对话易产生提问疲劳 | 任何场景皆可作为单兵工具挂载 |
| **Superpowers** | **L2 会话纪律层**<br>会话内 TDD 与先思后写 | 治愈 AI 冲动编程，规范单个会话的规划与测试步长 | 不维护全局业务资产账本与多模块拓扑依赖 | 对极其细小的 Bug 修复存在流程冗余 | 独立功能开发、探索性重构 |
| **OpenSpec** | **L3 规范层**<br>基于提案的增量规范管理 | 结构优美，`specs + changes` 极大提升团队需求对齐效率 | 不做代码与测试的自动化物理静态对账 | 存量项目前期补规范成本高，依然依赖人眼 Review | 团队协作、重文档规范的项目 |
| **Trellis** | **L3 任务状态机**<br>单需求上下文隔离与流转 | 低摩擦，操作极流畅，长对话下有效防发散防迷失 | 刻意不维护全系统调用图与全局业务总账 | 需求做多后缺乏跨任务全局依赖全景；**已停更**（最后 push 2026-09-29）且为 AGPL 协议 | 存量用户的中小型项目日常迭代（新选型不再推荐） |
| **Atlas** | **L4 全局治理层（判分面）**<br>资产账本、机器对账门、门禁自证、真跑终验 | 以退出码 `1` 阻断测试造假类问题（无主 AC、无豁免跳过、无断言用例），维护全局单源事实；自带 `atlas workflow` 四步执行层（plan / dispatch / verify / finish） | 专注于核心防线与账本，不侵入业务代码实现，不做无状态的轻量玩具脚手架 | 需维护 AC 编号纪律；AC 反向覆盖仍为 `WARN` 级，覆盖维度矩阵 C01–C14 已声明未全覆盖即 `FAIL`；浏览器级 E2E 为 Web 单轨 (Playwright)，后端走独立 AC 对账门禁；影响面反查需维护语义透镜行（未维护即 `not_ready`）；开箱整合度仍在追赶；0.4.0-beta.9 | 存在明确业务规则与质量底线、重度依赖 AI 交付的严肃项目 |

## 六、务实的选型建议：什么时候用谁？

这套生态最舒适的使用方式是**根据风险密度量体裁衣，并让集成替代手动负担**：

### 1. 什么时候选其他工具？
* **一次性脚本、无状态 Demo、完全不在意长期回归的极简玩具**：直接使用 `Cursor / Claude Code` 配合特定语言的 Rules / Skills 即可，追求最纯粹的单兵编码速度；
* **偏好纯单人日常轻量迭代、追求无感知流转**：会话内纪律推荐单独使用 **Superpowers**，极低心智负担；需要跨会话的流程编排（开卡、派工、归档）时，Trellis 已停更且为 AGPL 协议，不宜再作新选型——流程编排能力可选 Atlas 自建执行层 `atlas workflow`（按 Trellis 工作流半边的同等边界接管，开箱整合度仍在追赶）；
* **团队已有非常完善的 CI/CD 与人工 Code Review 体系**：只想把业务 Spec 和增量变更梳理干净，**OpenSpec** 依然是好选择；但它不验证 AC ↔ 真实测试，需要判分面时分两种情况——**从零起步的团队，直接全用 Atlas 一件搞定**（需求落点、状态机、评审面都自带）；**已有 OpenSpec 的团队不用扔**：评审流留在 OpenSpec，定稿条目落 Atlas 资产根，接上判分面即可。注意这种并存是给存量团队的过渡桥，不是推荐稳态：并存 ≠ 两棵需求树，同一条目的正文只能有一个住址（条目正文唯一住址），否则两边各自漂移。

### 2. 什么时候引入 Atlas？
**判断标准不是项目年龄或代码行数，而是风险密度（业务规则条数 × 变更爆炸半径）：**
当业务规则多到人脑与单次会话装不下、且变更的爆炸半径开始跨模块时，账本与门禁就会开始产生净收益——这可能发生在演进到数万行的老系统，也同样可能发生在一个仅千余行但规则致密的核心计费或认证模块的**第 1 天**。

建议采用**分档渐进**的引入策略，而非一开始就吞下全套流程：
* **轻档（项目立项即可使用）**：仅启用 PRD/AC 账本记录 + `atlas check --fast` 快速体检。每条 AC 在需求诞生时顺手登记，边际成本趋近于零，且从一开始就避开了“日后从老代码逆向考古回填”这一最昂贵、最容易失真的坏账路径；
* **重档（业务规则与防线收紧时）**：逐步打开全量 E2E 门禁、变异测试自证与设计对账。

> **注：关于治理成本的客观认知**  
> 必须诚实承认 Atlas 的前置门槛：需要 Node + Python 3 运行时、需遵守 AC 编号纪律、浏览器级 E2E 目前为 Web 单轨（后端与全栈另有独立的测试 ⇔ AC 对账门禁兜底）。  
> 但它绝非让你“付钱受苦”：Atlas 通过脚本生成器自动补齐 E2E 基线、通过收口链刷新结构事实（finish 新鲜度门兜底），**其本质是用确定性的机器自动化对账，去替代人工在每一个 PR 里逐行审查 AI 是否偷改测试、是否漏测逻辑的繁重苦役**。

### 3. 一条管线的自然融合（无需多套系统反复切换）
在真实工程中，这些工具并不是“多层手动叠放”，而是**一条管线、各就其位**：
* **单一流转入口**：日常开发只走 `atlas workflow` 一条执行层——大白话提需求由 `atlas-onegate` 起手接住，之后 plan → dispatch → verify → finish；
* **判分面内嵌其中**：开工前 workflow 在 1.6 步骤调度 `atlas-apply` 更新 PRD/E2E 账本（资产先行）并推导影响面；dispatch 按改动路径注入命中的结构事实、testid 薄桩与团队规范；收口前显式刷新结构事实，`finish` 以审查 PASS/范围新鲜、E2E red、结构事实新鲜度把关；impact 对账为收口 WARN 观察项，不自动阻断归档（强制点在退出码级机器门，而非纪律），**日常全程零额外手动切换负担**；
* **Skills 作为横切能力随时调用**：决策定稿前调用追问类 Skill（如 `grilling` 刺破隐式假设，Atlas 自身的 `atlas-grill` 正是吸收了这一思想），规划期调用拆解类 Skill，编码期调用语言工艺类 Skill。

让每类工具留在它擅长的关注范围，让钩子与自动化替代手动协同，才是 AI 时代健康的工程实践。
