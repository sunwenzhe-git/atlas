# 实测砍掉 71.7% CLI 噪音！从 KV Cache 原理到 Coding Agent 的五维上下文工程实践

> **为什么你用 Coding Agent 写代码，越到后面越慢、越贵、还越容易“脑血栓”？**  
> 很多人以为省 Token 就是“把 Prompt 写短一点”。但在真实的多轮 Agent 研发场景中，真正吃掉你数百万 Token 甚至击穿上下文窗口的，从来不是你输入的那几句需求。  
> 本文将从底层 **Prefill / Decode 机制** 与 **KV Cache 物理特性** 展开，以 **Pi Agent + Atlas** 生产架构为例，拆解一套具备确定性收益的**五维 Token 节流工程体系**。

---

## 一、 破除迷思：大模型处理“输入”与“输出”的算力与计费真相

要优化 Token，首先必须看清大模型底层的算力消耗模型。一次完整的 LLM 推理，在物理层面划分为两个截然不同的阶段：

```text
[ 输入 Prompt (N Tokens) ]
       │
       ▼
┌─────────────────────────────────────────────────────────┐
│ 1. Prefill（预填充阶段 / 计算输入）                      │
│ • 计算本质：高度并行矩阵乘法（Compute-Bound，算力受限）   │
│ • 耗时特性：吞吐极高，成千上万 Token 往往数秒内并行完成   │
│ • 核心产物：为每个 Token 生成 Key/Value 向量并写入显存    │
└──────────────────────────┬──────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────┐
│ 2. Decode（解码阶段 / 自回归输出）                       │
│ • 计算本质：逐 Token 串行生成（Memory-Bound，显存带宽受限）│
│ • 耗时特性：生成速度受限，随并发与上下文拉长逐字吐出     │
│ • 计费特征：各大模型 API 单价通常是输入 Token 的 3 ~ 5 倍 │
└─────────────────────────────────────────────────────────┘
```

### 1. 输入阶段（Prefill）：吞吐高，但架不住 ReAct 循环的 $O(N^2)$ 滚雪球
大模型的输入是并行计算的。但在多轮 Coding Agent（如 ReAct 或 Plan-and-Solve）中，每一轮工具调用的执行结果、文件读取内容都会全量追加到上下文中：
- 第 1 轮：输入 5K Tokens；
- 第 5 轮：输入 25K Tokens；
- 第 20 轮：堆积了大量文件全文和测试日志，单次输入膨胀到 80K~120K Tokens。  
**整个会话的累积输入消耗呈二次方爆炸增长。**

### 2. 输出阶段（Decode）：速度慢、单价极高
在自回归生成阶段，每吐出一个新 Token，GPU 都需要将庞大的模型权重与历史上下文全部轮巡一次。因此云厂商输出 Token 的定价往往是输入的 3 到 5 倍。

> **💡 核心原则**：
> - **优化输入（Input）**：核心是**严格抑制体积膨胀**与**最大化吃满 Prompt Cache 折扣**；
> - **优化输出（Output）**：核心是**掐断礼貌性废话**与**限制无意义的 CoT（思维链）发散**。

## 二、 KV Cache 的本质与 API Prompt Caching 的“生存铁律”

在 Decode 阶段，模型计算新 Token 与历史 Token 的注意力时，不需要重复执行 Projection 矩阵乘法，而是直接读取显存中已存好的历史 Key 和 Value 向量，这套显存结构即 **KV Cache**。

各主流厂商（Anthropic、DeepSeek、OpenAI 等）在此基础上开放了 **Prompt Caching（前缀缓存）** 机制：
- **命中缓存（Cache Hit）**：输入成本大幅下降 **80% ~ 90%**（例如 DeepSeek 缓存命中仅需原价 1/10，Anthropic 仅需 1/10），首字时间（TTFT）大幅缩短。

但在工程落地中，必须严格遵循两条物理铁律：

### 铁律 1：严格的最长公共前缀匹配（Prefix Matching）
Prompt Cache 必须从第 1 个 Token 开始逐字严格匹配。**只要前缀发生 1 个字符的变更，该变更点之后的所有历史缓存全部失效（Cache Miss）！**

```text
❌ 典型错误做法（在 System Prompt 头部注入动态变量）：
[System: 当前时间 14:00:01] + [5,000 字固定规范] + [历史记录]
[System: 当前时间 14:00:15] + [5,000 字固定规范] + [历史记录]
                 ▲
        第 8 个字符变更！导致后方 5,000 字规范与历史缓存全部击穿！

✅ 正确架构（静态前缀完全冻结，动态状态置于尾部）：
[System: 5,000 字静态规则 + 稳定工具 Schema] + [会话历史] + [动态上下文/时间戳]
└──────────────────────────┬───────────────────────────┘
                稳定命中 90% 折扣缓存前缀！
```

*注意：主流厂商通常存在最小缓存门槛（如 Anthropic 需 1024 或 2048 Tokens 以上，DeepSeek 按 64-token 块对齐）。会话前缀必须高于该基线才能享受缓存折扣。*

### 铁律 2：5 分钟闲置过期（TTL）与冷启动惩罚
GPU 显存资源受限，主流厂商的动态 KV Cache 存活时间（TTL）通常为 **5 分钟**。  
一旦用户停顿阅读代码或切换窗口超过 5 分钟，原有的几十万 Token 缓存将被服务集群自动释放。下一次交互将触发全量冷启动，产生高昂的计算延迟与全额重算费用。

## 三、 五维 Token 节流架构实践

针对上述物理特性，我们在 **Pi Agent** 底座与 **Atlas** 工程线束中建立了一套闭环的节流方案。

### 第一维：极简 Harness 原语 —— 消除开局的“公摊底噪”

许多重型 Agent 框架在初始化时，便塞入了大量复杂的元协议、全量 MCP 工具 Schema 与冗长礼貌性指令，未发一言先消耗 10K~15K 基础 Token。

Pi Agent 采取了极度克制的极简核心设计：
1. **零冗余协议开销**：只保留最纯粹的系统约束与工具交互格式；
2. **严禁无意义输出（No Negative Echo）**：通过 Prompt 显式剪枝，杜绝模型在调用工具前输出“好的，我已经理解了您的意图，接下来我将……”这类昂贵的 Decode 废话；
3. **能力按需挂载**：全局仅暴露精简路由接口，业务级规范和复杂工具以按需激活形式加载，不常驻全局上下文。

---

### 第二维：分层模型路由 —— 隔离脏上下文，终结“原地切模型”的缓存雪崩

很多开发者直觉上认为：*“搜文件这种简单活切便宜小模型，写复杂架构再切旗舰大模型，能在同一对话中省钱。”*

**这是在工程上极易踩中的重度负优化陷阱。**

#### 1. 为什么不能在同一长对话中“反复横跳”切模型？
KV Cache 是与特定模型的物理权重矩阵强绑定的，**跨模型绝对无法复用**。  
当你在累积了 40K Tokens 的对话中从模型 A 切到模型 B 时，客户端必须将整整 40K 历史作为纯文本发送给模型 B。模型 B 必须执行一次完整的**全量冷启动 Prefill**；几轮后切回模型 A，若已超过 5 分钟 TTL，模型 A 也需重新全额计算。**你不仅没省钱，反而同时为两个模型的冷启动双重买单。**

#### 2. 架构破局：用 Subagent 实现无状态上下文隔离
正确的做法是：**主模型不动如山，耗费 Token 的脏活派生独立 Subagent 处理。**

在 `settings.json` 中定义角色工种的分层路由：

```json
{
  "defaultModel": "zai-coding-cn/glm-5.3",
  "subagents": {
    "agentOverrides": {
      "scout": { "model": "gemini/gemini-3.8-flash-high", "thinking": "off" },
      "reviewer": { "model": "zai-coding-cn/glm-5.3" }
    }
  }
}
```

```text
主会话 (旗舰主力模型, 保持 40K 稳定前缀，锁定 90% 缓存折扣)
  │
  ├──► 派生独立 Subagent (scout: Gemini Flash, 独立生命周期)
  │      ├── 1. 仅分发单次任务目标（不携带主会话历史，冷启动成本极小）
  │      ├── 2. 关闭 Thinking 思维链，高速检索过滤，产生 20K 过程日志
  │      └── 3. 提炼出 300 字精简事实报告，任务结束即刻销毁临时上下文
  │
  ◄── 主会话仅接收这 300 字结论（作为一条单次 Tool Result 写入）
      主模型的 KV Cache 前缀完全未被 20K 过程垃圾污染！
```

通过这一隔离机制，海量的中间搜索日志在高速轻量模型中自生自灭，主力模型的上下文水位得以保持极度干净。

#### 3. 硬约束：Subagent 汇报契约（防“二手信息失真”）

Subagent 隔离了过程噪音，却也引入了新风险：主模型拿到的是**二手摘要**——一旦摘要把字段名或依赖关系说错（例如把 `net_amount` 误报为 `amount`），主模型就会基于错误事实继续写代码。因此这套隔离机制必须锁定一条汇报契约：

1. **证据回传**：Subagent 的每条结论必须携带 `文件路径:行号` 与关键代码片段，禁止只回一个孤立结论；
2. **低置信度回交原文**：当结论存在多义、或 Subagent 自身不确定时，必须回交原始片段交由主模型复核，不得代替主模型裁决。

### 第三维：CLI 透明拦截代理（RTK）—— 实测砍掉 71.7% 命令行噪音

Coding Agent 上下文膨胀的最大来源往往是**终端命令的原始输出**。`pytest` 的海量通过日志、`ls -laR` 的重复权限行、编译器的滚动日志，往往瞬间吞噬数万 Token。

我们在 Pi Agent 扩展中挂载了 Rust 编写的高性能 CLI 过滤中间件 **RTK**：

```typescript
// extensions/rtk.ts: 命令行透明拦截代理
pi.on("tool_call", async (event, ctx) => {
  if (!isBashToolCallEvent(event)) return

  const cmd = event.input.command
  // 静默重写为具备压缩语义的 RTK 指令
  const rewritten = await rewriteCommand(pi, cmd, ctx.signal)
  if (rewritten && rewritten !== cmd) {
    event.input.command = rewritten
  }
})
```

**工作机制与优化表现：**
- **智能日志提取**：`pytest` 仅保留失败用例与核心堆栈，全绿用例压缩为单行摘要；
- **目录树去噪**：剔除文件权限与时间戳冗余字段，转为紧凑路径树；
- **逃逸机制（Fail-safe）**：若 Agent 连续遇到未预期执行结果，或显式声明 `--raw` 标识，自动回退到原生未裁剪输出，杜绝排障信息丢失。

> **实测数据（rtk gain 生产统计）**：  
> 在总计 8,748 次命令调用中，原始终端输出折合 **6.7M Tokens**，经 RTK 智能压缩后进入上下文仅 **1.9M Tokens**，在命令行调用这一单一维度**净节省 4.8M Tokens（降幅达 71.7%）**。

### 第四维：KV Cache 智能保温 —— 别被“1 个 Token”忽悠，算清缓存续期的真实账本

针对云端 5 分钟 TTL 过期导致的冷启动问题，许多人会想到用定时探针做“缓存保温（Keep-Alive）”。
在 Pi Agent 的 `warm-cache.json` 中也有类似配置：

```json
{
  "intervalMs": 240000,
  "maxIdleCycles": 3,
  "minCachedTokens": 2048,
  "warmPayload": "Reply with exactly: OK.",
  "maxOutputTokens": 1
}
```

很多人看到 `maxOutputTokens: 1`，会误以为“我只花了 1 个 Token 的成本就保住了全量缓存”，**这是对云厂商计费模型的严重误解**。

#### 1. 探针保活的真实账本算术题
以一段累积了 **50,000 Tokens** 的真实 Agent 会话为例：
- **输出端**：探针确实把最昂贵的生成输出压到了极限（仅 1 个 Token）；
- **输入端**：云厂商依然会按 **Cache Read（通常为正常输入价的 10%~20%）** 收取缓存读取费。
  
也就是说，每发一次探针，你实际支付的是 **50,000 × 10% = 等效 5,000 个输入 Token 的成本**。

#### 2. 保温心跳的“盈亏平衡点”
既然每次保温都有成本，那什么时候该保温，什么时候该放弃？

| 场景策略 | 闲置 8 分钟（离开接水 / 短暂思考） | 闲置 60 分钟（离开开会 / 外出午饭） |
| :--- | :--- | :--- |
| **完全不保温** | 触发 1 次全量冷启动<br>💸 **付出 50,000 原价计算费 + 漫长 TTFT 延迟** | 触发 1 次全量冷启动<br>💸 **付出 50,000 原价计算费** |
| **无脑持续保温** | 心跳 2 次<br>✅ **付出 5,000 × 2 = 10,000 成本（净赚 80% 费用与零延迟！）** | 心跳 15 次<br>❌ **付出 5,000 × 15 = 75,000 成本（反噬！比不保温多亏 50%！）** |

#### 3. 工业级保温的必备防御：短时续期 + 超时硬熔断
因此，真正的缓存保温工程绝不能无限期常开，必须建立两大铁律：
1. **只抗短时停顿（Max 2~3 周期熔断）**：
   设置 `maxIdleCycles: 3`（最多保活 12 分钟）。专为开发者阅读代码、写思考文档这几分钟的碎片时间续命；一旦超过 12 分钟无交互，立即**主动休眠放弃缓存**，避免造成严重的空刷资损。
2. **生命周期隔离（严禁污染历史）**：
   心跳探针必须完全在客户端网络层吞吐，**物理隔离于会话持久化历史之外**，绝不能作为对话轮次追加到主历史里，否则会直接破坏真正的业务前缀。
