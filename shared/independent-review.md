# atlas 共享契约 — 独立审查

> 「独立审查」这一机制的**骨架正文**：四类实例（PRD / E2E 用例 / 实现代码 / 设计决策）共同遵守。
> 正文只此一份；各实例按路径引用 `.atlas/shared/independent-review.md`，**不得复制骨架条款**。
> 各实例**只声明自己的**四项：**审查维度** / **回退环取值** / **权威输入** / **fan-out 单位与阈值**。
>
> 决策依据：`3507` **P14–P22**；讨论与取证：`3508 §46–§49`（历史卷）与 `3509 §C12`。

## 2. 骨架条款（硬，五类实例共同遵守）

1. **只审不改**。审查者**不落笔改动被审对象**；发现的问题映射回生成阶段，改完**必须重跑全部维度**（改动即作废旧结论）。
2. **独立结论 —— 先独立得出，再比对**。审查者在**不看**生成者自评 / 推荐答案的前提下给出结论，之后才与推荐比对。禁止「你同意吗」式提问：同源推荐 + 同框评审会让「一致」失去证据力。
3. **分级**（只此三档，取值写死）：
   - **`Critical`** —— 会让**下游产出建立在错误事实上**的缺陷，或**断言通过而行为不存在**的假绿通道。有 `Critical` ⇒ 门禁阻断。
   - **`Major`** —— 不影响下游可执行性，但让产出与依据脱节：覆盖缺口、维度冲突、术语漂移、回退环指错。
   - **`Minor`** —— 一致性、措辞、可读性。
4. **每条 finding 必带 `回退环`**，取值从该实例的闭集里选（见 §1 表）。同一 finding 可跨环：**`首改环` = 必须最先动的那一环**，其余环按全链路列出。
5. **留痕双份**：人读 `README.md` + 机读 `review.json`（形态见 §3）。**被审对象的正文不得写入审查意见**——审查报告是**记录类**，被审对象是**交付面**，只写被接受的最终状态。
6. **硬口径**：缺**权威输入**（§1 表第 5 列，或该实例自己声明的等价物）时，**明确说明无法判定完整性，不得给出「通过」**；**不得以「文档内部自洽」代替完整性结论**。
7. **维度封闭 + 兜底出口**：审查者只按该实例的固定维度填结论表；另有**可选**字段 `other`，契约要求它**默认留空**，且 `other` 报出的问题**不计入门禁**（只作人工参考）。理由：完全封闭会把荒谬但真实的问题挡在「不在维度内」；全开放则退化为无界探索。

## 3. 输出契约（双份）

**人读** `<报告目录>/README.md`，三段式：

1. **审查总结**：`通过` / `需修改` / `需重大调整`
2. **问题清单**：按 `Critical` / `Major` / `Minor` 分级，每条含 `问题描述` / `涉及文件与位置` / `修改建议` / **`回退环`**
3. **优化建议**（含参考小节：`other` 字段的产出）

**机读** `<报告目录>/review.json`，**对齐校验器既有输出契约** `{ok, status, checks[]}`：

```json
{
  "ok": true,
  "status": "PASS",
  "root": "<项目根>",
  "scope": "<本次范围>",
  "unit": "<扇出单元键，如 页 slug / 用例 ID 区间>",
  "round": 1,
  "expected": 4,
  "reviewed": 4,
  "budget_exceeded": false,
  "checks": [
    { "id": "D1", "level": "Critical|Major|Minor",
      "check": "<维度名>", "target": "<用例 ID / 页 slug / ...>",
      "detail": "<问题描述>", "rollback": "<回退环>" }
  ],
  "other": []
}
```

- **`unit` / `round`**（2026-09-27 补）：单元产物的扇出单元键与**第几轮**。每复审一次 `round` +1；两者都落进文件，供「未改动单元复用上轮结论」（§6 第 5 条）与 §4「复审落点」使用。
- **`expected` / `reviewed` / `budget_exceeded`**（2026-10-06 补，`3509 §B112` 残留清偿）：**应审 N / 实审 M 对账的机器落点**（§6 第 8 条）——**必填**（单审查者实例记 `1 / 1`）；`reviewed < expected` 或 `budget_exceeded: true` ⇒ 报告级 `status` 至少 `WARN`（状态映射复算含此下限，`cli_review_convert` 同规则）。实例 ⑤ 由 `cli_review_convert` 写入；①②④ 由聚合器写入。**报告落盘当轮必跑** `scripts/validate_review_report.py --dir <报告目录>`（形态 + 对账门，登记 `shared/gates.md` 2.1）。

- **`status` 与分级的映射（写死）**：存在任一 `level == "Critical"` ⇒ `status = "FAIL"`；否则若存在 `Major` ⇒ `"WARN"`；否则 `"PASS"`。
- **`ok = status != "FAIL"`**；**退出码 1 ⟺ `status == "FAIL"`**——与 `validators/*.py`、`scripts/*.py` 完全同源，门禁因此**不需在门口信任模型结论**（读文件即可判）。
- **`checks[]` 带用例级 / 页级内容哈希**（实例可选，见 §6 第 5 条）时，键名固定 `target_hash`。

## 4. 门禁语义（两层载体，均**不在门口信任模型结论**）

| 层 | 载体 | 触发条件 |
|---|---|---|
| **严重性** | 审查器自身退出码（`review.json` 的 `status`） | 有 `Critical` ⇒ 非零退出 |
| **存在性** | 下游**写盘动作**的前置检查 | 报告缺失 ⇒ 下游动作**拒绝执行**；dry-run 只报状态、不改退出码 |

- **既不阻断人工评审，也不阻断用户确认门**：审查意见是给设计者 / 用户的**输入**，不是它的替代。
- **报告定位（写死）**：取报告目录下**目录名日期前缀最大**的那一份 `review.json`（落点形态固定为 `<YYYY-MM-DD>-<范围>` ⇒ 可机器排序；范围后缀不参与排序）。不引入指针文件，避免第二处状态。
- **复审落点（写死，2026-09-27 补）**：同一报告目录内的**单元产物**落 `findings/<unit>.r<round>.json`（`round == 1` 时允许写作 `findings/<unit>.json`）。**同一 `(unit, round)` 已存在即不得覆盖，`round` 必须递增** —— 「第几轮」必须体现在**文件名**里，否则新一审会**静默覆盖上一审的原始结论**（而该目录通常尚未入库，无版本控制可回滚）。报告级结论取「该 unit 存在的**最大** `round`」；未改动单元（§6 第 5 条内容哈希未变）**不重审、不新增文件**。
- **报告不存在** = **未审**，不是「通过」。

## 5. 执行器（框架与模型无关）

- 契约**只写「独立审查」这道动作 + 维度 + 输出格式 + 回退环 + 门禁语义**；**执行器归 `product/stack-profile.yaml`**（各实例在自己的段下声明，`null` = 会话环境默认子代理机制）。契约**不写任何具体工具名、模型名**（`global-rules.md` §1）。
- **两条硬要求**（与具体执行器无关）：
  1. 审查者必须 **fresh context** —— 不得继承生成时的上下文。子代理的价值在于**独立视角**，不在于「多一个模型」；自己批改作业会把生成期的自我辩护带进审查。
  2. 审查者**档位不得低于生成者**（允许更高）。
- **fan-out 形态与并发数**：契约只写**形态**（扇出单位 + 超阈值再切 + 全局审查者）与**阈值**（阈值是审查**语义**的一部分，故进契约）；**并发实现细节归执行器**。
- **上下文最小化**：审查者的输入按 §9 的**指针清单**取，只拿该扇出单元所需的文件，不喂整仓。

## 6. 效率与成本约束（九条，`3507 P17` + `3509 §100`）

| # | 机制 | 做法 | 代价 / 风险 |
|---|---|---|---|
| 1 | **增量审查**（最大节约） | 审查范围 = **本轮变更**的对象；未变更者按**内容哈希**跳过并复用上轮结论；**首次基线审查必须全量** | 抓不到「跨轮漂移」⇒ 由**全局审查者跑全量元数据**补 |
| 2 | **分轮按对象级条件化** | 第一轮（致命维度）全跑；第二轮（质量维度）**只跑第一轮判为「有效」的对象** | 无（这些对象改完复审时自然走第二轮）。注意是**对象级**，不是片级——片级表述会误伤整片 |
| 3 | **档位分级** | 第一轮（致命维度）用**强档**；第二轮与全局审查者用**中档** | 要求执行器支持**多档**而非单值 |
| 4 | **上下文最小化** | 扇出单元审查者只拿三样：该单元文件 + 该单元的元素清单（**非整页源码**）+ 该单元相关的上位依据（**非整份上位文档**） | 依赖「按页抽依据」的能力 |
| 5 | **一致性复用** | 对象未改动（哈希未变）⇒ 复用上轮结论，不重审 | 要求 `review.json` 带对象级哈希（§3） |
| 6 | **熔断** | 每轮审查设预算上限（轮次 / 时长 / 花费）；超限即停并报「已审 N/M」 | **第 6 条不能省**：无熔断的自动重试是有真实代价记录的下场（`3505` 引用的 E2E 工具调研 A12：数百次重试 / 有花费 / 零产出） |
| 7 | **fan-out 并发上限 = 4**（2026-09-28 补，`3509 §100` 定形） | 上限入契约（**机制仍归执行器**）；实测：一次性并发 13 ⇒ provider 返回 **429×8**；并发 ≤4 时全部跑完 | 上限不是「省一点」，而是**结果集完整性**：429 会让部分单元静默未审（见第 8 条） |
| 8 | **429 退避重试 + 「应审 N / 实审 M」对账**（2026-09-28 补） | 遇 429 必须**退避重试**（不得当成「审完了」）；报告**必须**写「**应审 N / 实审 M**」，**M < N 即 WARN** | 实测事故（`3509 §B100`）：第一次按契约宽度跑就撞限流 ⇒ 结果集不完整，而门只看「报告存在 + 无 Critical」⇒ **静默少审**（与 `§B92`/`§B95`/`§B96` 同族） |
| 9 | **审查者产物必须可解析**（2026-09-28 补） | 每个 fan-out 单元的产物必须过 `json.loads`；解析失败 ⇒ **重发**，不得静默当「已审」 | 实测：1 个单元因 `fix` 字段内层引号未转义 ⇒ 聚合器静默判「未审」（已完成的审查被丢掉） |

- 六条是**独立审查这一机制的公共约束**，五类实例共用 ⇒ 正文只此一份。
- **另一类节约（与第 1 条并列）**：审查者反复报**同一形态项**时，应把它**升格为确定性机器门**，然后停掉这份 LLM 工作（实例见 `3507 P14` 的落地过程）。

## 7. 校准：收敛的控制环，不是固定比例（`3507 P20`）

「低风险 + 一致 ⇒ 自动通过」这一侧的**证据力**必须用人类判定去校准，否则永远不知道审查者是不是橡皮图章（对齐机器规则「**护栏只通过不算数**」）。

| 项 | 取值 |
|---|---|
| 学习期 | 前 **3 轮**决策 **100% 人工复核**（起点值，实跑后按证据调） |
| 学习期后 | 一致侧**抽样 20%** 人工复核（起点值）；降抽样前提 = 未触发行 ② 的验证轮，或已触发且该轮漏报 = 0（`3507 BM`） |
| 三条指标 | ① **一致率**（审查者独立结论与推荐一致的比例）；② **漏报率**（抽样人工复核发现审查者漏掉的问题 ÷ 抽样数）；③ **分歧率**（进入人工的比例） |
| 回退到全人工（三条触发） | ① **漏报率 > 阈值**；② **分歧率连续 3 轮为 0** = 监控信号，**不单独回退**（`3507 BM` 消歧，原 `§B117`）：触发**加强抽样验证轮**复核漏报率——该轮漏报 > 0 ⇒ 橡皮图章坐实、回退全人工；漏报 = 0 ⇒ 判真收敛、按「学习期后」行降抽样；③ 决策升格为 `global-rules.md §7` 高风险（该情形本就全人工） |
| 恢复 | 回退后**恢复抽样需用户显式确认**，不自动恢复（避免「漏报 → 回退 → 恢复 → 再漏报」的振荡） |
| 留痕 | `<项目根>/product/reviews/calibration.jsonl`（**append-only**，跨实例共用的单一账本）+ 三条指标 |

> **已裁决（2026-10-09，`3507 BM`，原 `3509 §B117`）**：「分歧率连续 3 轮为 0」曾有相反两解（橡皮图章 ⇒ 回退全人工 vs 收敛 ⇒ 降 20% 抽样）。定案 = **联判消歧**：0 分歧为**监控信号**，连续 3 轮即触发**加强抽样验证轮**（提高抽样比例复核一轮漏报率）——该轮漏报 > 0 ⇒ 橡皮图章坐实、回退全人工；漏报 = 0 ⇒ 判真收敛、按上表「学习期后」行降抽样。判据锚 = 本节关键判据（**漏报率说明能力；一致 / 分歧率只说明同源，只作监控**）。

- **关键判据（不要搞反）**：**漏报率**才说明审查者有没有能力；**一致率高只说明两个模型同源**。故一致率是**监控用**，漏报率是**门禁用**。
- **漏报率阈值**：学习期内**任何一次抽样漏报即回退**（保守默认）；学习期满后的阈值在**首次回退时依证据**定，未定前仍按「漏报率 > 0 即回退」。**不预填未取证的数字**。
- **适用范围**：校准环只对**低风险侧**生效。决策本身属 `global-rules.md §7` 高风险时**一律人工**，正常走完即结束，**不记 `calibration.jsonl`**（否则一致 / 分歧率恒 0，会假日触发第 ② 条的加强抽样验证轮——白付一轮复核成本）。

## 8. 实例 ④：设计决策（`3507 P18 / P21 / P22`）

> **为何语义条款就地**：实例 ①②③ 各自有环契约承载维度；④ 的对象是**设计决策本身**（跨四环与 `apply`，也含 atlas 自身的设计），没有哪个环是它的家。若日后出现归属，本节整体迁出，接线表按 §1 末条处理。

### 8.1 分级线（写死）

| 决策类型 | 处理 |
|---|---|
| **低风险**：可逆、只影响单个项目的 `product/` 产物、不动通用契约 | 审查者独立复核**一致** ⇒ **自动通过** |
| **高风险**：`global-rules.md §7` 四条（覆盖已有产物 / `stack-profile.yaml` / `.trellis/workflow.md` / 通用模板·校验脚本·契约变更） | **一律人工**；审查者只**压缩阅读量**（把结论压成一行「已独立复核，同意 / 不同意，理由 X」），**不替代确认** |

> **关键区分**：审查者可以替人「**读**」，不能替人「**签**」。§7 的四条是**签名级**动作。

### 8.2 与 `global-rules.md §6`「设计歧义先 grill」的关系：串行两道

```
atlas-grill（提炼刺痛代价与致命冲突） → 用户拍板关键抉择
  → 审查者复核「该轮拍板主张」 → 一致：通过 / 不一致：人工
```

| 项 | 定案 |
|---|---|
| 能力分工 | atlas-grill 产**冲突与代价摊牌**（刺透隐式假设 = 探索）；审查者判**主张**（判断一个主张站不站得住 = 验证）。两种能力不可互替 |
| 审查者**不生成问题** | 硬约束（让它生成问题 = 又变成无界探索，与 §6 第 6 条同源） |
| 介入粒度 | **按 frontier 轮次**（一轮问答收口后审一次）。按单题 = N 次调用且树上反复返工；按整棵树 = 拓扑一改就得全部重审 |
| 与 §6 第 2 条的关系 | §6 第 2 条是**同一批对象、两类判断**；本节是**不同批次的对象**。两者不冲突，可叠加 |

### 8.3 替代方案

审查者**可以**给替代方案，但（a）**不得自行采纳**——不一致**一律人工**，替代方案只是人工决策的**输入**，与「同意 / 不同意」同为意见、不构成行动；（b）**必须带代价说明**（新增调用 / 新增人工 / 新增产物）；**无代价说明的替代方案不计入报告**。理由：否则会给出「看起来更优但更贵」的方案。

### 8.4 留痕落点

- **项目级设计决策** ⇒ `<项目根>/product/reviews/<日期>-design-review-<主题>/`（§3 双份）。
- **atlas 自身的设计**（项目根 = 工作区，无 `product/`）⇒ 知识库 `atlas/` 的讨论纪要；**不记 `calibration.jsonl`**（见 §7 适用范围）。

## 9. 审查输入清单（指针化，不复制）

- 审查输入用 `scripts/make_review_inputs.py` 产**内容指纹清单**（`MANIFEST.json`：`{path, sha256, bytes, lines, 取样时刻}`），落 `<报告目录>/inputs/`。
- **不产副本**：审查者按清单读**当前**文件；要冻结某次审查的基线用 `sha256`，不拷文件（拷贝会与现状脱节 —— 实测踩到快照 24 条 vs 当前 35 条）。
- 这也是 §6 第 4 条的落点：清单即「该拿哪些文件」的显式声明。

## 10. 实例 ⑤：实现代码（2026-09-29 补）

> **对象**：一条需求在实现阶段产生的 diff（Trellis Execute 之后、收口之前）。**为何语义条款就地**：与 ④ 同理——对象跨四环与 `apply`，没有哪个环是它的家。`apply/reference.md` §6 原口径「实现阶段 atlas 不设门」由本实例修订为「**收口侧设门，实现过程仍不介入**」。
>
> **动机**：Trellis 2.2 的 check 子代理只对本任务需求卡负责（视野不含域内 AC 全集）、且边审边改（修复者，非独立审查者）⇒「实现代码 ⇔ 应然资产」平面此前无承载者；E2E 真跑未发生时，本实例是该平面**唯一不依赖真栈**的语义检查。

### 10.1 执行器与输出

- 执行器 = **CLI 式独立审查进程**（读 git diff 出结构化 findings）：fresh context 由**进程边界**保证（比子代理更彻底）；**无落盘修复能力** ⇒ 骨架第 1 条「只审不改」天然成立。具体工具与模型归 `product/stack-profile.yaml` 的 `impl_review` 声明（CLI 执行器与审查模型解耦，null = 使用默认值；契约不写死特定模型）。
- 业务上下文（「这次该干什么」）由**调用方组装后注入**（CLI 的 background 类参数）：内容 = 需求卡摘要 + 受影响域的 AC + 相关用例断言——这是 §6 第 4 条上下文最小化的落点，**不喂整仓**。
- 输出经 `scripts/cli_review_convert.py` 转**本契约 §3 的 `review.json`**（CLI 原始 JSON 作为输入侧证据留报告目录）：CLI 的 JSON 是给通用 CI 用的形态，门禁读它 = 在门口信任模型结论。严重度四档→三档**写死**（critical→`Critical`；high / medium→`Major`；low→`Minor`；**未知档位 ⇒ 转换器显式失败**，不猜）；category 闭集（bug / security / performance / maintainability / test / style / documentation）外的归 `other`（骨架 §2.7，不计门禁）。

### 10.2 应审 N / 实审 M（硬；§6 第 8 条在此实例的落地）

- N = **CLI `--preview` 的 Will review 数**（`.md` 等不支持扩展名会被 CLI 排除——契约与文档面本就不属实例 ⑤ 的对象，**不得**用 git diff 全量计数，会假 `WARN`）；M = CLI 汇总的实审文件数。**M < N 或预算击穿 ⇒ `WARN` 起步**；CLI 不报实审数 ⇒ 转换器**拒绝产出**（缺权威输入不得给「通过」，骨架 §2.6）。
- 动机：实测取证——CLI 会对超大 diff **静默跳过文件**，属「静默少审」族（`3509 §B100`）。对账不是附加项，是**接入前提**。

### 10.3 门禁与回流

- 有 `Critical` ⇒ **域不收口**（完成门侧，与「E2E 全 green」并列）。已接入（2026-09-29）：完成门与 `closeout.md` 步骤 10 已挂；**`impl_review.llm` 为 null ⇒ 审查 `SKIP` + 原因**（不阻断 E2E 侧结论，也不算已审）。
- 修复**回流 Trellis Execute**，改完重跑（round +1）；**不走 CLI 自身的修复通道**（若有）。
- finding 的回退环**默认 `implement`**；triage 判明「AC / 断言本身错」⇒ 改判 `prd` / `e2e` 并登记 backfill 队列（`apply/reference.md` §5.2「发现」入口之一）。
- **报告落点**：`product/reviews/<日期>-impl-review-<范围>/`（与 ④ 的 §8.4 同惯例；CLI 原始 JSON 留档为输入侧证据）。

### 10.4 审查焦点三问（2026-10-09 补，`3507 BP`，ATLAS-UPSTREAM #190）

细节归机器门（lint / 类型 / 测试在目标项目侧），实例 ⑤ 的审查者只聚焦**架构判断**——判断类维度机器判不了（与 apply 三问门「门是语义判断」同源口径）。三问随 §10.1 的 background 注入（`closeout.md` 步骤 10 引用本节，**不复制正文**）：

1. **影响辐射面**：本次 diff 是否改变了本需求范围之外的模块所依赖的行为（接口契约、共享数据、公共语义）？
2. **职责归属**：复杂逻辑是否堆积在不该承载它的层？本应在公共定义 / 数据源头一次解决的，是否被复制散落到了多个消费点？判例形态（2026-10-10 补，`3507 BQ`）：**单调用者的抽象层、无人设置的配置项**——为尚未到来的需求预留的层与旋钮，同样是堆积。（**展示层的防御性兜底不在此列**——保可用性的韧性设计不是堆积；用户 2026-10-09 纠正）
3. **特例与退役模式**：是否存在只为通过验收用例而写的特例路径？是否把已标记退役（legacy）的旧实现模式复制进了新代码？

- **`Critical` 判级硬口径（2026-10-10 补，`3507 BQ`）**：`Critical` 的 finding 必须在 `detail` 内附**证据链**——diff 中的具体位置 + 从权威输入到缺陷结论的推理路径；给不出证据链的至多判 `Major`（无证据不配阻断收口门，与骨架 §2.6「缺权威输入不得给通过」同源）。
- **边界（同轮定案）**：实现期的代码规范（「在正确的层解决」类准则）**不进本契约**——atlas 不介入实现过程（§10 引言既定边界），代码规范由目标项目自己的 lint / typecheck / test 机器门承担；本节只是**收口侧的审查焦点**。
- 措辞纪律：不写任何框架名与语言特性（`global-rules.md` §1）。

## Guidance

动手做任何一处独立审查前，先读本文件（骨架 + §6 成本约束 + §7 校准环），再读该实例自己的契约拿**维度**与**回退环取值**。**不得**把骨架条款复制进环契约（`single-source.md` §1）；**不得**在报告里写被审对象的正文；**不得**让审查者替代 `global-rules.md §7` 的确认门。改本契约时同步环契约的接线、`3507` 决策记录与知识库（按 `shared/knowledge.md`）。
