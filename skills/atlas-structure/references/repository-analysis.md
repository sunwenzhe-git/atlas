# 仓库分析

目标：先发现项目**真实的**架构，再写规范。不要从模板反填空白。

## 分析顺序

1. 盘点 `.atlas/spec/` 现状：哪些是结构事实、哪些是约定、哪些是陈旧或模板残留。
2. 读包清单、workspace 配置、构建脚本、顶层文档，划出包与运行时层。
3. 走一遍主链路：入口（CLI / 路由 / 任务）→ 核心服务 → 数据落点 → 失败路径。
4. 看测试：哪一类测试是「值得抄」的范例（单测 / 组件 / E2E / 契约）。
5. 把每条候选规则回到**源码或测试**核对后再落笔。

## 要抓什么

| 面 | 问题 |
|---|---|
| 包边界 | 每个包拥有什么？哪些 import 跨边界？ |
| 运行时层 | CLI / 后端 / 前端 / worker / 共享库 / 工具分别在哪？ |
| 核心抽象 | 哪些类型、服务、store、命令、路由、适配器定义了系统形状？ |
| 数据流 | 输入从哪进、在哪校验、状态落在哪？ |
| 错误处理 | 失败如何表示、记录、暴露、测试？ |
| 配置 | 默认值、环境变量、生成物、模板分别在哪？ |
| 测试 | 新代码应该模仿哪些既有测试？ |

## 工具

- GitNexus：执行流、模块簇、依赖枢纽、影响面。
- ABCoder / 语言原生工具：签名、类型、类边界、实现示例。
- 直接读源码与测试：最终真值。

工具输出只用来**定位文件**；规则必须由源码 / 测试背书。用法见 `mcp-setup.md`。

## 分析笔记

边分析边记四件事：

- 包 / 层名与负责范围；
- 体现该模式的真实文件路径；
- 规范应该教会未来的 agent 什么；
- 找到的反模式（旧实现、注释、迁移残留）。

笔记直接决定下一步的 spec 文件划分。
