# 受控批次 2×2 — 影子差分矩阵（E2）

> **性质**：`research/` 非 canonical 证据存档；不进装配、不作为执行契约。
> **日期**：2026-10-23。**证据等级**：E2「受控注入」——在**真实项目的隔离副本**里注入已知坏状态，不是真实任务自然发生。
> **用途**：补上真实批次 01 缺的「影子 FAIL / 正式不失败」「影子 PASS / 正式 FAIL」「两者都 FAIL」三种形态，校准影子试点的判定规则。
> **安全**：所有改动只在 `/tmp/atlas-controlled-copy`；真实项目未动；副本已删除；本文不含产品名、绝对路径、业务 case ID。

## 1. 夹具与基线

- 从真实采用方项目复制一份隔离副本（排除 `node_modules` / `dist` / `.git` / 测试产物），保留 `.atlas/`、`product/`、`.trellis/` 与源码。
- 基线：副本上跑项目装配编排器 + `validate_e2e_index` 影子，复现真实批次 01 的 **0 FAIL / 5 WARN / 3 SKIP / 8 ok**；影子 **WARN**（0 FAIL / 1 WARN / 2 N/A）。
- 每个变体改完后都从快照还原；副本最终删除。

## 2. 三个受控变体

| 变体 | 注入（抽象） | 正式编排器 | 影子 `validate_e2e_index` |
|---|---|---|---|
| **A 独立信号** | 从副本编排器的 `VALIDATORS` 摘掉 `validate_e2e_index`（模拟门未接线 / 旧装配）+ 索引主表少一列 | **不失败**（4 WARN，0 FAIL） | **FAIL**（3 条 FAIL） |
| **B 盲区** | 在一条用例分片的 `testid:` 清单里加一个源码不存在的 testid | **FAIL**（`validate_testids`） | **WARN**（0 FAIL / 1 WARN / 2 N/A） |
| **C 冗余** | 只做 A 的索引列头注入，编排器保持全部门接线 | **FAIL**（`validate_e2e_index`） | **FAIL**（3 条 FAIL） |

**基线（对照）**：正式不失败（5 WARN）、影子 WARN（0 FAIL / 1 WARN / 2 N/A）。

## 3. 2×2 读数

|  | 影子 WARN/PASS | 影子 FAIL |
|---|---|---|
| **正式不失败** | **基线**：一致 WARN，无独立信号 | **A**：独立信号——影子抓到了正式编排器没跑的门 |
| **正式 FAIL** | **B**：盲区——影子门覆盖不到 testid 缺陷 | **C**：冗余——影子与已接线的正式门重复 |

**四条判定规则（与真实批次报告 §3 对齐）：**

1. **影子 FAIL + 正式不失败 ⇒ 独立信号**：这是最值得保留的形态；查「门是否未接线 / 旧装配 / 只在某个入口跑」。
2. **影子 WARN/PASS + 正式 FAIL ⇒ 盲区**：影子门不能替代正式门；它只覆盖自己那条判据面。
3. **影子 FAIL + 正式 FAIL ⇒ 冗余**：查重叠门；影子没有额外价值，除非正式门只在某些入口跑。
4. **影子 WARN + 正式 WARN ⇒ 对齐**：没有独立信号，但也不代表门无用；只是这个状态没有需要它单独拦的东西。

## 4. 耗时

- 影子 `validate_e2e_index`：基线 81ms；A 66ms；B 76ms；C 56ms。受控变体下稳定在 56–81ms，与真实批次 01 的 52–62ms 同量级。
- 正式侧：受控变体用的是项目装配编排器（beta.4，无 P2 计时），所以 `duration_ms=None`；真实计时以 `research/2026-10-23-ablation-real-batch-01.md` 的 3 轮为准（`validate_testids` 中位 845ms）。
- 这说明影子工具本身的成本很低；真正的大头仍是 `validate_testids`。

## 5. 这组受控数据证明什么

**能证明：**

1. 影子工具能产生**独立信号**（A）：当正式编排器没跑某道门时，影子能把它抓出来——这正是「门未接线 / 旧装配」类风险的观测面。
2. 影子工具有**明确盲区**（B）：testid 缺陷它看不到；不能拿它当全量门。
3. 影子工具在门已接线时是**冗余**的（C）：它的价值在覆盖缺口，不在重复正式门。
4. 判定规则 1–4 在受控状态下都能被触发，规则不是空话。

**不能证明：**

- 不能给出真实任务中的独立信号频率：A 的「门未接线」是人为模拟的，真实项目当前 9 个门都接线。
- 不能替代真实批次 02/03：受控注入是 E2 证据，真实任务自然发生的 FAIL/WARN 才是 E1。
- 不能证明 `validate_testids` 的 845ms 是浪费：它在本轮抓住了 B 的 testid 缺陷，正是正式门该做的事。

## 6. 对下一批的真实采集建议

- 真实批次 01 已经证明「门都接线时影子冗余」；受控 A 证明「门未接线时影子有独立价值」。
- 所以下一批真实任务的重点不是再证明影子有用，而是：
  1. 记录 `validate_testids` 的耗时是否仍占约 70%；

  3. 如果出现「某个门在项目装配态缺失 / 版本漂移」，优先用影子补观测，而不是直接重装。
- 若一直等不到新的真实任务状态，受控 2×2 已足够支撑「影子工具保留、但不作为正式门」的结论；不需要再人为造更多变体。
