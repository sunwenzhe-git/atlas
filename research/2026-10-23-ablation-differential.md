## 0. 结论速览

1. **不要照搬整线束 on/off。** Atlas 的「门」不是同质的：有的是只读判据，有的会写产物，有的是编排器，有的是人侧流程（`shared/gates.md` §2.1–§2.5）。整包摘除会把「守卫价值」与「生成能力 / 观测能力」混在一起——摘掉 `.atlas/tests` 的同时也摘掉了发现回归的手段（`scripts/atlas_check.py:224`）。
2. **分层信度排序：L2 单判据 > L1 单门 > L0 整线束；成本相反。** 首跑选 L1 / L2 / L3 的**回溯归因**，不选 L0。
3. **实验形态：回溯反事实做首跑（1–2 天、零代码改动）；前瞻首选「影子模式」**（门照跑、判据照出、只记录不阻断）。物理摘除只留给无法影子化的判据 / 生产者，且只在隔离副本里做。
4. **与变异证明分工：** 变异证明回答「门会不会咬」（存在性）；消融回答「门值不值得留」（必要性 / 边际价值）。两者共用「基线绿 → 注入 → 观察 → 逐字节还原 → 复绿」四段协议（`scripts/mutation_proof.py:7-21`），但**不互相替代**。
5. **指标：** 收益面 6 项、成本面 7 项。首跑能直接算的只有「事后补钉率 / 漏因分布 / 返工代理 / 部分误拦」；逐门耗时、token、阻塞率**当前不可得**，首跑如实记 `N/A`，不拿文件大小或提交时间冒充。
6. **「从未红过」当前只有 1 行**：完成门（`shared/gates.md:83`）。清零路径 = 触发可见 → 真跑暴露 → 隔离副本受控注入；三种证据分级记录，**不在活仓制造假红**。
7. **安全：** 项目外快照 + 逐字节还原 + 冲突拒绝写入 + 残留门 + `install.sh --update` 互锁；**不依赖 git 保护未跟踪的 `.atlas/`**（`install.sh:23`、`:130-131`）。
8. **首跑交付物不是「净收益数字」**，而是 4 张表 + 1 张数据缺口表；判定标准 = 每个案例有锚点、每个结论有分母、每个缺口有去向。

## 1. 问题与证据基线

### 1.1 已有「微观证明」，缺「宏观差分」

- **微观证明已闭环**：每道自动门要求「喂坏输入必红」+ M 系列变异钉（`shared/gates.md:5-7`）；变异工具强制四段协议，且报告必须含**注入 diff**（`scripts/mutation_proof.py:7-21`、`:116-122`）。
- **取证等级已登记**：出厂级（本轮 / 历史实测）、真跑级、待复核、从未红过（`shared/gates.md:22-30`）。当前表内 `待复核` 已清零（`shared/gates.md:134`），`真跑级` 仅 E2E 真跑一行（`shared/gates.md:65`），`从未红过` 仅完成门一行（`shared/gates.md:83`）。
- **但「门的运行账」不存在**：`atlas_check.run()` 只返回退出码与输出，不带计时（`scripts/atlas_check.py:144-152`）；`Row.add()` 只存名称 / 状态 / 摘要（`:102-117`）；失败日志每次覆盖写（`:633-658`），成功则删除（`:653-658`）；唯一的耗时字段是 E2E 汇总里的 `duration_ms`（`:546`、`:572-600`）。因此「哪道门花了多少时间、误拦了多少次、拦住了什么」没有历史。
- **结论**：当前能证明「门会咬」，不能证明「门值不值」。本方案补的是后者。

### 1.2 四个已有半成品（不要另起炉灶）

| 半成品 | 现在回答什么 | 本方案怎么用 |
|---|---|---|
| RFC-20261022-01 §2.1「消融锚」 | 五件流程件「摘除后坏法」（`proposals/RFC-20261022-01-route-shaped-criteria-to-machine.md:56-66`） | 把「摘除后坏法」从 5 件扩成**逐门字段**，作为消融假设与受控注入的输入 |

| `shared/closeout.md` 步骤 11 | 单事故追问「哪一层本该接住 / 为什么没接住」（`:119-141`，核心问句在 `:138`） | 升级为**系统性归因台账**的入口；触发器沿用既有，不新增日常仪式 |
| `duty-review/bugs.md` | 按环分类的存量缺陷工作面（`:3`） | 首跑案例索引；**不是完整历史**（见 §3.5） |

### 1.3 术语（首次出现即解释）

- **消融（ablation）**：临时摘掉一道门 / 一条判据，观察「没有它时什么会漏过去」。
- **差分（differential）**：有它 vs 没它两组观察的差。
- **反事实（counterfactual）**：不真的摘除，而是根据历史证据回答「如果当时没有这道门，会怎样」。
- **影子模式（shadow mode）**：门照常运行、判据照常产出，但**只记录、不阻断**；用于测量「本来会被拦下多少次」。
- **消融事务（ablation transaction）**：把「摘除 → 运行 → 还原」做成一个可验证、可拒绝、可追责的事务；借鉴 Trellis `ablate / restore` 的项目外恢复思路。
- **受控注入（controlled injection）**：在**隔离副本**里故意喂一个坏输入，证明门会红；证据等级低于「真实缺陷自然咬合」。

## 2. 设计题一：消融对象分层

### 2.1 四层对象与它们各自回答的问题

| 层 | 对象 | 回答的问题 | 分析单元 | 信度 | 成本 | 主要混淆 | 首跑用不用 |
|---|---|---|---|---|---|---|---|
| **L0** | 整线束 on/off（`.atlas/` + 门 + skill + 接线） | 「Atlas 作为研发方法整体值不值」 | 一个项目 / 一组任务 | **低** | **高**（2 倍开发量 + 环境） | 守卫价值 vs 生成能力 vs 观测能力 vs 学习效应 | **不用** |
| **L1** | 单道门摘除（一个 validator / 一个 gate row） | 「这道门的**边际净贡献**是多少」 | 门 × 任务或历史案例集 | **中** | **中**（一次任务或一次回放） | 上下游依赖、触发面 SKIP、门的副作用 | 首跑只做**回溯归因**，不做物理摘除 |
| **L2** | 校验器内单判据摘除（一条检查项） | 「这条判据是否承重」 | 判据 × 产物语料 | **高**（隔离度最好） | **低–中**（跑语料 / 测试） | 语料覆盖不足会被误读成「判据无用」 | **是**（归因到判据面） |
| **L3** | 流程 / 语义门（`gates.md` §2.5） | 「这条人侧纪律该不该保留」 | 一个案例或一族案例 | **中–低** | **低** | 无法物理摘除，只能政策对照；归因靠人 | **是**（归因面） |

**信度与成本的方向相反**：L2 最干净但只能回答局部；L0 最接近「整体」但混淆最多。**不要用 L0 的低信度去否定 L2 的高信度结论，也不要用 L2 的局部结论去替代 L0 的项目级判断。**

**L3 不是物理层，是归因层**：`gates.md` §2.5 的 9 行大多不设机器判据（`shared/gates.md:86-98`），无法像代码那样摘除；它们只能进入回溯台账，用「这类事故如果当时有人按纪律做，会不会被接住」来评估。把它单列，是为了防止把「流程门的缺失」误算进「代码门不承重」。

### 2.2 可消融性分类（先分类，再选层）

只看目录名会误判：`validators/` 下并非全是只读判据——`validate_testids.py` 会**自动补薄桩**（`:529-543`），`validate_ac_alignment.py` 会**写基线快照**（`:323-329`）。因此按「有没有副作用」分四类：

| 类型 | 代表 | 摘除后的直接效果 | 能否影子化 | 能否物理摘除 |
|---|---|---|---|---|
| **A. 纯判据型** | `validate_prd` / `validate_e2e_index` / `validate_structure` / `validate_stack_profile` / `validate_design_exemptions` / `validate_adr` | 只少了判红 / WARN | **能**（输出旁路即可） | 能；但前置未声明会触发 `SKIP`（`scripts/atlas_check.py:63-89`） |
| **B. 带副作用判据型** | `validate_testids`（补桩）、`validate_ac_alignment`（写基线） | 判据 + 状态写入一起消失 | **不能直接影子化**；需指向副本 | 能，但**状态面也必须进快照** |
| **C. 生产型** | `gen_e2e_scripts`（写脚本 / README / manifest）、`gen_testid_stub`、`refresh_structure`、adapters、`backflow` | 产物不再生成 / 不再更新 | **不能** | 只能在**隔离副本**里摘；活仓摘 = 改变任务 |
| **D. 编排 / 流程型** | `atlas_check`（聚合 + 写日志 / 汇总）、`gates.md` §2.5 人侧门 | 编排或纪律消失 | 编排器可「降档行」；流程门不能代码化摘除 | 不建议物理摘除；用回溯归因 |

锚点：生产型写入见 `scripts/gen_e2e_scripts.py:978`、`scripts/gen_testid_stub.py:109`、`scripts/refresh_structure.py:346`；编排器写日志见 `scripts/atlas_check.py:572-600`、`:633-658`；流程门见 `shared/gates.md:86-98`。

### 2.3 与既有变异证明（微观）的分工

| 维度 | 变异证明 | 消融差分 |
|---|---|---|
| 靶子 | 门的**实现** | 门的**必要性 / 边际价值** |
| 输入 | 一个已知坏输入 | 真实任务或历史案例语料 |
| 问题 | 「它会不会咬」 | 「没有它，什么会漏过去；有它，付出了什么」 |
| 输出 | 红 / 绿 | 逃逸集合 + 成本 |
| 分析单元 | 一个门 | 门 / 判据 / 任务 / 案例 |
| 成本 | 秒级 | 分钟到人日 |
| 性质 | **存在性证明**（必须逐门做） | **必要性 / 边际证明**（抽样做） |

**五条不打架的规则：**

1. **变异证明仍是每道新门的强制义务**（`shared/gates.md:142`）；消融**不替代**它，也不因为它而降低它的要求。
2. **消融是抽样，不是普查**：只对「成本可疑 / 覆盖重叠可疑 / 长期零命中 / 新增判据存疑」的门或判据做。
3. **共用四段协议**：基线绿 → 摘除 / 注入 → 观察红或逃逸 → 逐字节还原 → 复绿（`scripts/mutation_proof.py:7-21`、`:99-105`、`:108-114`）。
4. **分账**：变异证明记「会咬」；消融记「值得」；一张门可以「会咬但冗余」，也可以「独特但很少触发」——两种结论不能互相推导。
5. **零逃逸 ≠ 判据无用**：必须报告语料规模与覆盖范围；小语料只能得出「本次未观察到逃逸」，不能得出「可删」。

### 2.4 分层结论

- **L2 是首选**：隔离度最高、成本最低，能直接回答「这条判据承不承重」。适合首跑的归因与后续的判据级消融。
- **L1 是二期**：需要先有「门依赖图」，否则摘掉上游门会让下游 `SKIP` / `FAIL`，把「判据缺失」误读成「门无用」。依赖关系可从 `_GATE_PRECONDITIONS`（`scripts/atlas_check.py:63-89`）与门册「触发物」列（`shared/gates.md:19`）推导。
- **L0 只在最后考虑**：它回答的是项目级问题，不是门级问题；且当前没有足够的样本与盲法设计。见 §3.1。

**一个具体例子（同一道校验器，三种问法）：** 以 `validate_e2e_index` 为例——L2 = 只摘掉其中一条判据（例如某条查询键白名单），其余判据照跑，看坏分片能否漏过；L1 = 摘掉整道校验器，看是否还有别的门接住同一坏分片；L0 = 摘掉整包 Atlas，看同一需求的产物与返工是否变化。三者的分析单元、成本和混淆完全不同，不能用一个实验回答三个问题。

## 3. 设计题二：实验形态取舍

### 3.1 前瞻 A/B（同一任务，带线束 / 裸跑）

**形态：**

- **L0**：同一任务做两遍，一遍完整 Atlas，一遍去掉 `.atlas/` + 接线 + skill。
- **L1**：同一任务做两遍，只摘一道门。
- **L2**：同一产物跑两遍，只摘一条判据（最接近纯函数对照）。

**优点**：因果识别最强；能直接看到「有它时被拦下、没它时漏过去」的同一任务对照。

**代价与致命混淆：**

1. **不是同一个任务**：摘掉生产型门（`gen_e2e_scripts` / `refresh_structure` / `gen_testid_stub`）会改变产物集合，不只是去掉守卫（`shared/gates.md:46`、`:49`、`:50`）。L0 的「裸跑」是另一种研发方法，不是「同一方法去掉门」。
2. **观测能力也被摘掉**：`atlas_check` 的「对齐测试」行跑的是 `.atlas/tests`（`scripts/atlas_check.py:224`）；L0 裸跑同时失去发现回归的手段，两组不是对称的。
3. **学习效应**：同一人 / 同一模型做第二遍会更快、更少犯错；单任务配对无法区分「门的作用」与「第二遍变熟练」。
4. **样本太小**：一个项目内很难凑出统计上可信的同类任务数；3–5 个任务的 A/B 只能当案例研究，不能当统计证明。
5. **无法盲法**：执行者知道自己有没有线束，行为会变。
6. **成本翻倍**：L0 是 2 倍开发量；L1 至少多一次任务回放。

**如果将来一定要做 L0**（不建议首跑）：预登记 3–5 个可比任务、随机顺序、同一时间盒、同一模型 / 同一人、盲评产出；报告写成「案例研究」，不写成「净收益证明」；「裸跑」组用项目自带测试保底，不依赖 Atlas 的测试。**这不是本方案推荐的第一步。**

### 3.2 回溯反事实（拿存量事故做归因台账）

**形态：** 对每个已确认缺陷，回答四个问题：

1. 事发时**有没有**一道门该接住它？
2. 如果有，那道门**当时跑没跑**（触发面是否被 `SKIP` / 未运行）？
3. 如果跑了，它**为什么没红**（判据不足 / 被绕过 / 预算太晚）？
4. 事后补了什么（测试 / M 钉 / 新判据 / 契约条款）？

**优点：**

- **零代码改动、零真跑**：只用 `duty-review/bugs.md`、`DESIGN.md` §12 决策行、`git log`、`shared/gates.md`。
- **直接产出「哪一层漏了」**：这正是 closeout 步骤 11 的问句（`shared/closeout.md:138`）。
- **天然覆盖流程 / 语义门**：这些门无法物理摘除，但可以在案例里归因。
- **成本低**：1–2 天可完成 20–30 个案例的首轮分类。

**代价与偏差：**

1. **后见之明**：修完之后说「哪道门本该接住」很容易；必须用固定判据，并要求「那道门在事发时已经存在」。
2. **幸存者偏差**：`bugs.md` 出库即删（`:3`），只留开放 / 待复验；正式记录在 `DESIGN.md` §12 / `gates.md` / CHANGELOG（`duty-review/README.md:66`）。因此案例全集要**从 D 行 + git 重建**，`bugs.md` 只作索引。
3. **时间信息缺失**：`bugs.md` **无日期字段**（`duty-review/README.md:28`）；「首次发现时刻 / 修复时刻」只能用提交日期与 D 行日期近似。
4. **成本信息缺失**：没有 token、人工时长、逐门耗时；只能给代理指标（提交数 / 文件数 / 返工轮次）。
5. **归因是语义判断**：需要固定 rubric，并对 20% 样本做 48 小时后的二次复核，降低单人分类漂移。

**三种归因结果（必须互斥）：**

| 结果 | 含义 | 对应处置 |
|---|---|---|
| **有门·会咬** | 门在事发时存在，且按判据本应红 | 查「为什么没跑 / 为什么被绕过」——触发面或纪律问题 |
| **有门·不够** | 门跑了但判据太弱，放过了坏产物 | 补判据 + 变异钉（假绿族） |
| **无门** | 事发时没有对应判据 | 建门 / 建契约 / 明确接受风险 |

**三态是粗判；T1 的六类漏因（A1–A6，Attribution）是三态内部的细分**：`A1 无门` = 无门；`A2 未触发` / `A4 被绕过` / `A5 预算晚` = 有门·会咬（问题在触发面或纪律）；`A3 判据不足` = 有门·不够（问题在判据强度）；`A6 不可归因` = 证据不足，既不冒充有门，也不冒充无门。**用 A 前缀是为了不与变异钉的 M 编号撞名。**

### 3.3 影子模式（前瞻的低风险替身）

**定义：** 门照常安装、照常运行、照常产出判据；但编排器**只记录、不阻断**（或把 FAIL 降为 WARN 写进影子账本），工作流不受影响。

**适用：** A 类纯判据型门；B 类带副作用门只能在副本上影子化；C 类生产型门不适用。

**为什么它是前瞻首选：**

- **零破坏**：不需要摘文件、不需要恢复事务，不存在「忘了装回」。
- **可高频**：每个真实任务都能跑，样本积累快。
- **直接给出「本来会被拦多少次」**：这是 A/B 里「带线束组」的拦截计数，且不需要第二组。
- **可与成本同采**：影子运行同样能计时（若已插桩）。

**它不能回答什么：**

- **威慑效应**：门存在本身会让人 / 模型提前规避；影子模式测不到这部分。
- **行为偏差**：如果执行者能看到影子警告，会主动修，污染「本来会漏」的计数。因此影子输出**不得进入工作回路**，只写私有账本，任务结束后再分析。
- **生产者副作用**：B / C 类门照跑会写文件；要么指向副本，要么只影子化其判据输出。

**实现边界：** 最小形态是在 `atlas_check` 外再跑一次目标校验器、把**计数 / 状态 / 耗时**写入**项目外** `~/.atlas-shadow/<gate>.jsonl`（不存校验器原文，零业务上下文），不改校验器、不改编排器。已落地为 `research/shadow_pilot.py`（research 工具，不进装配；默认拒绝已知有写副作用的门）。若将来进编排器，必须新增显式开关 + 响亮标记 + 残留门，且**不得**成为 CI 的静默旁路。

### 3.4 与 closeout 步骤 11 的关系

**现状：** 步骤 11 是「按需复盘」，触发器为 ≥2 次同类纠偏 / 用户点名 / 里程碑（`shared/closeout.md:121-124`）；核心问句是「哪一道检查才是接住它的正确位置？为什么没接住？」（`:138`）。它是**单事故追问**，不是系统台账。

**建议升级（拍板项，不在本次落地）：**

**仓内没有的（不要假装有）：**

1. **仓外台账 3508 / 3509 的正文**：仓内只有引用（例如 `shared/gates.md:3`、`proposals/RFC-20261022-01-route-shaped-criteria-to-machine.md:22`），没有文件。缺的是：逐轮真跑记录、人工纠偏原话、事故时间线、成本数字。
2. **逐门运行账**：`atlas_check` 不记逐门耗时（`scripts/atlas_check.py:144-152`），失败日志覆盖写（`:633-658`），成功即删（`:653-658`）；`.atlas/runs/` 在当前工作区为空。
3. **token 账**：Atlas 不采集宿主 token；仓内无任何 token 日志。宿主 UI 可能有，但不在仓内。
4. **误拦账**：`bugs.md` 的「未解观察」与 D 行里的假红修复只能提供**部分**样本（例如 `duty-review/bugs.md:17`、`:37`、`:38`），不是全量误拦日志。
5. **案例日期**：`bugs.md` 无日期字段（`duty-review/README.md:28`）；只能从 D 行 / 提交日期近似。
6. **完整历史**：`bugs.md` 出库即删（`:3`）；它当前是工作面，不是全量历史。

**因此，首跑的结论边界：**

- **能得出**：漏因分布、事后补钉率、返工代理、哪些门 / 判据是「事后才学会」、哪些族反复出现、哪些指标完全缺数据。
- **不能得出**：整线束的净收益、单门的「节省了多少人时 / token」、绝对误拦率、统计显著的 A/B 结论。
- **不能把**「仓内找不到反例」当成「门无用」；那只是**样本不足**。
- **根本限制：无事件的预防不可见。** 台账只记录「发生了并被发现」的缺陷；门提前阻止、从未进入任何台账的缺陷，在回溯数据里**不存在**。因此 B1 / B2 的分母是「已发生缺陷」，不是「所有潜在缺陷」；不能用它估计门的**绝对预防率**。影子模式能看到「本来会拦下」的一部分，但仍看不到威慑效应。

### 3.6 推荐组合

| 阶段 | 形态 | 目的 | 成本 |
|---|---|---|---|
| **首跑** | 回溯反事实（L1 / L2 / L3 归因） | 建立案例台账 + 漏因分布 + 数据缺口 | 1–2 人日，零代码改动 |
| **可选加餐** | 影子模式（1 道 A 类门） | 首次「本来会被拦下多少次」的前瞻计数 | 半天 |
| **二期** | 判据级物理消融（隔离副本） | 验证「某条判据是否承重」 | 每判据 0.5–1 天 |
| **三期** | 门级物理消融（隔离副本） | 验证「某道门是否冗余」 | 每门 1–2 天 + 依赖图 |
| **只在最后** | L0 整线束校准 | 项目级方法评估 | 数天到数周，样本要求高 |

## 4. 设计题三：指标体系

### 4.1 收益面

| ID | 指标 | 定义 | 数据源 | 首跑可得性 |
|---|---|---|---|---|
| **B1** | 事前拦截数 | 修复提交前，由既有门判红并导致修复的案例数 | 提交历史 + 门日志 | **代理**（多数为「未知」） |
| **B2** | 事后补钉率 | 修复同批 / 次批新增判据、测试或 M 钉的案例数 ÷ 案例总数 | D 行 + git | **直接**（文本证据） |
| **B3** | 假绿纠正数 | 门曾放行坏产物、后由新判据补上的案例数 | D 行含「恒绿 / 假绿 / 形态满足」 | **直接**（有文本证据的） |
| **B4** | 逃逸数 | 在门的最迟发现时刻之后才被发现的案例数 | `bugs.md` 的 `[逃逸]` 标记（`:3`）+ D 行 | **代理** |
| **B5** | 返工轮次 | 每案例的 fix 提交数 / 触达文件数 | git | **代理** |
| **B6** | 覆盖增量 | 每案例新增的判据 / 测试 / M 钉数 | D 行 | **直接** |

- **B2 是首跑的主指标**：它直接回答「门是事前防线还是事后学习」。高 B2 = 门在追赶缺陷，而不是在预防缺陷。
- **B3 是「门曾经假绿」的证据**：比「拦住了多少」更能说明判据强度；它对应 `shared/gates.md:98` 的「可执行性判据本体」族。
- **B4 的分母必须写清楚**：是「全部案例」还是「有门可归因的案例」；两种分母不能混。

### 4.2 成本面

| ID | 指标 | 定义 | 数据源 | 首跑可得性 |
|---|---|---|---|---|
| **C1** | 单门耗时 | 每次运行中一道门的 wall time | 需插桩 | **不可得** |
| **C2** | 总检查耗时 | `atlas_check` 整轮 wall time | 外部 `time` | **可得**（整轮） |
| **C3** | 人工处置时长 | 人阅读 / 判断 / 修复门报错的时间 | 操作者计时 | **抽样可得**（自报） |
| **C4** | token | 每次任务的 token 使用 | 宿主 UI | **不可得**（仓内） |
| **C5** | 误拦数 | 判红但事后判定非缺陷的次数 | 台账 / D 行 | **部分可得** |
| **C6** | 阻塞率 | 有 FAIL 且阻塞推进的运行数 ÷ 总运行数 | 需运行账本 | **不可得** |
| **C7** | 复发数 | 同族在 30 天内复现次数 | `families.py` / DR4 | **可得** |

**误拦必须分四类，不能混成一个数：**

1. **判据错误**：门判错了（真正的 false positive）。
2. **环境 / 前置缺失**：门因缺依赖、缺前置而红（`scripts/atlas_check.py:63-89` 的 `SKIP` 是合法降级，不是误拦；但把「环境缺失」报成 `FAIL` 就是误拦）。
3. **产物过期**：门没错，产物确实旧（例如「生成物最新」的 `WARN`）。
4. **已知噪声**：重复出现的已知告警，读的人已经麻木。

### 4.3 指标的采集缺口与最小插桩（提案，不实现）

**当前最大的缺口是「逐门耗时」和「运行历史」。** 最小插桩方案：

1. 在 `Row.add()` 增加可选 `duration_ms`，由 `check_validators` 等调用点计时（`scripts/atlas_check.py:102-117`、`:178-205`）。
2. 每轮结束向 `.atlas/runs/check-events.jsonl` 追加一行：时间戳、HEAD、`git_dirty`、每行的 `name / status / duration_ms`。**只写门名与状态，不写业务内容**（零业务上下文，`shared/global-rules.md:121`）。
3. 这与 RFC-20261022-01 的可选轻件 M4′ 同址（`proposals/RFC-20261022-01-route-shaped-criteria-to-machine.md:97`）——**不要造第二份运行账**；如果 M4′ 先落地，直接复用。
4. **字段必须有消费者**：本方案的台账 / 成本表是消费者；没有消费者就不要加字段（避免「为指标而指标」）。
5. **token 不进 Atlas 核心**：宿主无关是 Atlas 的设计前提（`proposals/RFC-20261022-01-route-shaped-criteria-to-machine.md:69` 的「统一形态」第 1 条）；token 由操作者从宿主 UI 手工记录，字段允许为空。
6. **误拦账单独建**：不要塞进 `bugs.md`（那是缺陷工作面），也不要在 `atlas_check` 里自动判定「这是误拦」——误拦是语义判断，只能人记。

### 4.4 判定规则：不要用「零命中」直接删门

这是本方案最重要的护栏。**零命中可能是「不需要」，也可能是「保险」**；两者不能靠一个计数区分。

**降档 / 删除候选必须同时满足：**

1. **失败模式可逆或低严重度**：不是权限、鉴权、数据持久化、外部契约、CI 配置这类高风险面（参考 `shared/closeout.md:61-66` 的 Always-Human 路径）。
2. **覆盖重叠已被证明**：另一道门或测试能接住同一坏输入；不是「我觉得应该能」。
3. **成本是实质性的**：例如单门耗时占整轮 > 10%，或每次收口都要人处理 > 30 秒；阈值是拍板项，不是本文定的硬数。
4. **消融 / 影子证据支持**：在同一语料或同一任务上，摘掉后没有新增逃逸；或影子观察 N 次没有 would-be block。
5. **不是「从未触发」**：从未触发可能是项目还没走到那个阶段（例如完成门只在域收口时触发，`shared/gates.md:83`）；要区分「未触发」与「触发了但没红」。

**必须保留的「保险型」门：**

- 失败模式是灾难性且低频（权限 / 数据丢失 / 契约破坏）；
- 即使零命中，也应保留，并在台账里标 `保险`，写明「保费 = 每次 X 秒 / 每次收口 Y 分钟」；
- 不能因为「今年没出事」就删。

### 4.5 「从未红过」门的真跑清零路径

**当前清单（只读核对）：**

- **完成门**（`shared/gates.md:83`）：唯一当前标 `从未红过` 的门。它的触发物是「域实现收口」，不是每次检查；仓内也没有以「完成门」命名的独立运行时行——`atlas_check.main()` 只调用校验器 / 出厂测试 / 生成物 / 审查报告 / 串行 / 漂移 / 版本 / 真跑（`scripts/atlas_check.py:613-631`），没有这一行。它若由收口流程或控制台状态机承担，也同样需要独立的运行事件才能被观测。没有域收口事件，它就没有可观测的运行记录。
- **E2E 真跑**（`shared/gates.md:65`）：已是 `真跑级`，不属于本清单；但它的「真跑级」只覆盖它自己，不外溢到其他门（上限声明，`shared/gates.md:32`）。
- **`待复核`**：当前为 0（`shared/gates.md:134`）。

**命名口径提醒：** 现有 `真跑级` 的定义是「在**真实靶场**（真前端 + 真后端）跑过」（`shared/gates.md:29`），它天然偏向 E2E 运行期门；对静态校验器，「在真实项目工件上跑过」不等于「真栈跑过」。下表用 **E1/E2/E3** 三个中性等级；若将来要写回 `gates.md`，需要决定是扩展现有等级定义，还是为静态门新增「实战级（真实项目工件）」——**这是拍板项**，不要在首跑里擅自改词表。

**清零阶梯（三级证据，分开记）：**

| 级 | 名称 | 怎么做 | 证据强度 | 能写什么 |
|---|---|---|---|---|
| **E1** | 实战级（自然红） | 真实项目、真实触发物、真实缺陷，门在预算内红 | **最强** | 可升 `真跑级`（若该门适用该定义）或 `实战级`（静态门） |
| **E2** | 实战级（受控注入） | 在**隔离副本**里注入与「摘除后坏法」一致的坏输入，门红，逐字节还原 | 中 | 只写「受控注入」，不冒充自然红 |
| **E3** | 触发但未红 | 门在真实项目里被触发 N 次，均绿，记录 N 与输入哈希 | 弱 | 证明「跑了」，不证明「会咬」 |

**具体步骤：**

1. **先让触发可见**：完成门当前没有「每次收口写一行事件」的发射点。没有发射点，「从未红过」与「从未运行」不可区分。第一步是加一个**运行事件行**（不是新判据）：收口时记录 `gate / trigger / verdict / reason / artifact hash`。**若它被实现为 `atlas_check` 的新行**，按新门义务登记 + 喂坏输入必红 + M 钉（`shared/gates.md:142`）；**若只是事件写入**，至少配一条单测钉，防止「静默丢写」——不要因为它不是判据就无测试上线。
2. **真跑暴露**：在下一次真实域收口时，让完成门按正常流程跑；无论红绿都记账。如果自然红，直接升 E1。
3. **受控注入**：如果 N 次触发（建议 N=10，拍板项）都没有自然红，在一个**隔离副本**里构造「用例未全绿 / 审查有 Critical」的坏状态，确认完成门拒绝收口；还原并逐字节校验。标 E2，不标 E1。
4. **不要**：在活仓里故意制造坏状态；不要把单元测试的红当成「真跑级」；不要把 `SKIP` 当成绿（`scripts/atlas_check.py:9-10`）。
5. **对其他出厂级门**：用影子模式在真实项目里积累 E3，遇到自然红升 E1；没有自然红就保持出厂级，如实写「已触发 N 次未红」，不强行清零。

**为什么这条路径可信：** 它把「没红」拆成「没跑」「跑了没红」「跑了红了」三态，而不是一个二值标签；这与 `atlas_check` 已有的三态语义（`SKIP` ≠ 通过 ≠ 失败，`scripts/atlas_check.py:9-10`）一致。

## 5. 设计题四：安全设计

### 5.1 威胁模型：消融期间会怎么坏

| ID | 失败模式 | 后果 | 防护 |
|---|---|---|---|
| **F1** | 摘门跑完忘了装回 | 门静默失效，坏产物通过 | 项目外 active 标记 + 残留门 + `install.sh --update` 互锁 |
| **F2** | 装回了，但字节不对 | 门行为微妙改变，测试可能仍绿 | 逐字节 sha256 + 可执行位 + 还原后复跑 |
| **F3** | 消融期间有人改了同一文件 | 还原覆盖别人的在途工作 | 冲突拒绝写入（三方比对：baseline / ablated / current） |
| **F4** | 标记文件本身被 `git clean` / 重装擦掉 | 状态丢失，没人知道还在消融 | 项目外快照 + 项目外 `active.json` 为唯一真相源 |
| **F5** | 消融的是源包，跑的是装配副本 `.atlas/` | 实验测了个寂寞 | 先判宿主模式（源包仓 / 采纳项目），锁定运行路径 |
| **F6** | 运行日志与正常账混在一起 | 无法归因，污染指标 | `ATLAS_ABLATION_ID` 注入 + 运行目录隔离 |
| **F7** | 用被消融的门去验证还原 | 假绿（门还没装回就复绿） | 还原校验只信哈希 + 不依赖被消融门的冒烟测试 |

### 5.2 四条不变式（借鉴 Trellis restore）

**借三件事，不借一件事：** 借「项目外快照 + 逐字节还原 + 冲突拒绝写入」；不借「整线束默认可摘」——Atlas 的门异质，整包摘除会改变任务本身（§2.1、§3.1）。下面四条是借来的部分在 Atlas 语境的落法。

1. **项目外真相**：唯一权威状态是项目外的快照 + manifest；仓内标记只是提示，不是真相。理由：`.atlas/` 在采纳项目里可能未跟踪（`install.sh:23`、`:130-131`），`git clean` / 重装会擦掉仓内标记。
2. **逐字节还原**：每个文件比 sha256（含可执行位；`scripts/backflow.py` 已把可执行位保留作为判据，`shared/gates.md:54`）；不接受「语义上等价」。
3. **冲突拒绝写入**：如果当前文件既不是 baseline 也不是 ablated 版本，说明消融期间有人改过；**停下、给出 diff、拒绝覆盖**。这是 Trellis「消融期改动冲突时 restore 拒绝写入」的 Atlas 版。
4. **独立验证**：还原验证不得依赖被消融的门；用哈希 + 一个不碰该门的最小冒烟测试。

### 5.3 Atlas 版消融事务协议

```text
ablation begin --id <ID> --target <项目根> --scope <门/判据> --timebox <分钟>
  1. 识别宿主模式：源包仓 / 采纳项目（看 .atlas/VERSION、.atlas/ 是否为装配副本）
  2. 预检：列出待触达面；run git status；**已跟踪文件**有未提交改动 ⇒ 拒
     （除非 --allow-dirty 并登记既有脏文件）；**未跟踪文件** ⇒ 登记后纳入快照，不当作脏
  3. 快照：把「代码面 + 状态面」复制到 ~/.atlas-ablation/<ID>/before/
     manifest.before.json = {path, sha256, mode, size}
     记录 HEAD / branch / .atlas/VERSION / Python 版本
  4. 写 plan.json：目标门/判据、期望变化、成功判据、时间盒、负责人
  5. 应用：补丁或配置开关；注入后断言字节确实改变（同 mutation_proof.py:99-105）
     manifest.after.json = 注入后的哈希
  6. 运行：所有输出写 ~/.atlas-ablation/<ID>/runs/；注入 ATLAS_ABLATION_ID
  7. 还原：逐文件三方比对
       current == after  ⇒ 写回 before
       current == before ⇒ 已还原
       其他              ⇒ 冲突：写 conflict.json + diff，拒绝写入，退出非零
  8. 校验：重算全部哈希 == before；跑不依赖被消融门的冒烟测试
  9. 关闭：result.json {status: completed|aborted|restore_failed, restore_verified, timings}
 10. 只有 8 通过，才删除项目外 active.json；否则保留快照与标记，等待人工处置
```

**崩溃恢复：** 进程被杀 / 机器重启后，`active.json` 仍在。下一次 `atlas_check` 报「消融残留」；操作者跑 `ablation restore --id <ID>`。**默认不自动还原**——自动还原可能在冲突时覆盖人的改动；只有在哈希完全匹配、无冲突时才允许 `--auto`。

### 5.4 防「摘门跑完忘了装回」的三道锁

1. **项目外 active 标记**：`~/.atlas-ablation/active.json`（唯一真相源）+ 项目内 `.atlas/ABLATION`（可见提示，不是真相）。
2. **`atlas_check` 新行「消融残留」**：检测 active 标记、manifest 不一致、超时未关闭。**出生 WARN**（符合「新判据先 WARN / N/A」的既有纪律），首次真实咬合后再评估升 `FAIL`。它本身必须按新门义务登记（`shared/gates.md:142`）+ 喂坏输入必红 + M 钉。
3. **`install.sh --update` 互锁**：检测到 active 消融 ⇒ 拒绝重装（除非显式 `--force` + 书面理由）。理由：`--update` 是「装回」的自然动作，不能在消融中途静默覆盖；同时也不能让它把项目外快照对应的仓内状态改掉（`install.sh:117-121`、`:157-158` 的脏工作区守卫是同一族思路）。

### 5.5 冲突拒绝写入规则

三方比对表：

| current | 含义 | 动作 |
|---|---|---|
| == before | 已经还原 / 从未被改 | 跳过 |
| == after | 是本次消融的结果 | 写回 before |
| 其他 | 消融期间有人改过 | **拒绝**；输出 conflict.json + diff；保留现场 |

**额外规则：**

- 冲突时**不删除**快照；不尝试「合并」；不自动 `git checkout`。
- 如果冲突文件是**运行时产物**（`.atlas/runs/`、`.adapter-out/`、生成物），先判断它是否在 `restore_exact` 清单里；运行时产物默认**隔离**而不是还原（见 §5.6）。
- 冲突处理后，`result.json` 必须写 `status: aborted`，该次实验数据**不得**进入指标分母。

### 5.6 消融面分三类（代码 / 状态 / 证据）

| 面 | 例子 | 处理 |
|---|---|---|
| **代码面** | `validators/`、`scripts/`、`shared/`、`rings/`、`_support/` | 快照 + 逐字节还原 |
| **状态面** | `.trellis/spec/conventions/testid.md`（薄桩）、`.atlas/runs/*.json`（AC 基线）、`.adapter-out/_drift*.json`、生成物 | 快照 + 还原或**隔离重定向**；按项目决定是否纳入 `restore_exact` |
| **证据面** | 消融运行日志、影子账本、耗时记录 | **只写项目外**，不写回仓；作为实验产物保留 |

**为什么状态面必须单列：** `validate_testids.py:529-543` 会自动写薄桩，`validate_ac_alignment.py:323-329` 会写基线快照；这些写入不随「判据摘除」消失，且可能在还原后继续影响下一次运行。只还原代码面 = 留下一个「半消融」状态。

### 5.7 两种宿主模式

| 模式 | 特征 | 消融面 | 关键差异 |
|---|---|---|---|
| **源包仓**（本仓） | `.atlas/` 只是运行态目录；源在 `shared/`、`rings/`、`validators/`、`scripts/`、`tests/` | 源目录 | git 保护已跟踪文件；`.atlas/` 不跟踪（本仓 `git ls-files .atlas` = 0） |
| **采纳项目** | `.atlas/` 是整包装配副本，可能未跟踪 | `.atlas/` + `product/` 产物 | git 可能完全保护不了 `.atlas/`（`install.sh:23`、`:130-131`）；必须用项目外快照 |

**判断方法：** 看 `.atlas/VERSION` 是否存在、`.atlas/` 是否是整包副本、源目录是否与 `.atlas/` 同构。**如果消融的是源包、跑的却是 `.atlas/`，实验无效（F5）。**

### 5.8 不要做的四件事

1. **不要在校验器里加生产级 `ATLAS_ABLATE` 开关**：那是给「静默绕过」开后门；影子模式或副本补丁已经够用。
2. **不要把备份放在仓内**（`.atlas/ablation-backup/` 之类）：会被 `git clean` / 重装 / 门自己扫到；必须项目外。
3. **不要在还原失败时自动「修」**：保留现场、退出非零、等人处置；自动修会把可诊断状态变成不可诊断状态。
4. **不要用被消融的门验证还原**（F7）：用哈希 + 独立冒烟测试。

## 6. 设计题五：最小首跑切片

### 6.1 目标与非目标

**目标（1–2 天）：**

- 建立第一份**案例归因台账**：每个案例回答「哪一层本该接住 / 实际何时接住 / 为什么没接住」。
- 产出**漏因分布**与**事后补钉率**。
- 产出**数据缺口表**：哪些指标仓内根本没有，下一期要不要插桩。
- 产出**候选清单**：哪些门 / 判据值得做影子或物理消融。

**非目标：**

- 不算整线束净收益；不算 token / 人时节省；不做统计显著性；不做真跑 E2E；不改任何代码 / 契约 / 脚本。

### 6.2 输入与范围

**输入：**

- `duty-review/bugs.md`（分段计数 30 个 `#NN`、全局去重 28；作为索引，不作为全集）。
- `DESIGN.md` §12（133 条 D 行；优先 **D100–D134 共 35 条**（已提交基线）；若首跑时 D135 已定稿则顺延纳入；时间不够时再从含「病灶 / 钉 / 变异」的行补选，案例总量上限 30）。
- `git log`（38 条 `fix` 提交；用于定位修复批次与返工代理）。
- `shared/gates.md`（45 行门登记 + 证据等级）。
- `shared/closeout.md` 步骤 11（归因问句）。
- **不在首跑范围**：3508 / 3509 正文（仓内没有）、任何产品仓、任何真栈。

**案例纳入标准：**

1. 有明确修复提交或 D 行（二者至少其一）；
2. 有可抽象的症状描述；
3. 不是「已知边界 / 非缺陷」（例如 `duty-review/bugs.md:48-51` 的图谱边界）；
4. 不是「未解观察、不计缺陷」（例如 `duty-review/bugs.md:17`、`:37`、`:38`）；
5. 去重：同一根因的多条引用合并为一个案例，保留最强锚点。

**预期样本量：** 去重后 25–40 个案例；首跑上限 30 个，按「有 D 行 + 有 fix 提交 > 有 `[逃逸]` 标记 > DR4 升室族 > 其他」排序。

### 6.3 时间盒

| 时间 | 动作 | 产出 |
|---|---|---|
| **Day 1 上午** | 建案例全集；去重；排除非缺陷；给每个案例分配 `C-01…` | 案例清单（含来源锚） |
| **Day 1 下午** | 逐案填 T1：事发时门状态 / 应接住的门 / 实际发现点 / 漏因 | T1 初稿 |
| **Day 2 上午** | 用 git 核对修复批次与事后补钉；填 B2 / B3 / B5 | T1 定稿 + T2 |
| **Day 2 下午** | 汇总 T3 / T4；写「结论与限制」；48 小时后抽 20% 复核 | 首跑报告 |

### 6.4 操作步骤（只读）

1. **建全集**：从 `DESIGN.md` §12 抽出所有含「病灶」或「钉」的 D 行；从 `bugs.md` 抽 `#NN`；从 `git log --grep=fix` 抽提交。三路合并，按根因去重。
2. **定时间**：每个案例的「首次可见时间」取修复提交日期与 D 行日期的较早者；没有日期就标 `未知`，不猜。
3. **判门状态**：查 `shared/gates.md` 当前行；用 `git log --follow -- <门文件>` 找该门实现的首次提交，`git log -S '<门名>'` 作辅助（它可能先命中文档而不是实现，别单凭它下结论）。若门是修复同批新增的，记「无门（事后补）」。
4. **判漏因**：用 §3.2 的三态 + 六类漏因子类（见 T1）填；每个判断必须带一个锚点（文件:行 / commit / D 号）。
5. **判事后补钉**：在修复提交及其下一批提交里找新增测试 / M 号 / 新判据；没有就写 `无`，不推测。
6. **算代理**：每案例的 fix 提交数、触达文件数；不做人时换算。
7. **汇总**：按漏因、按门层、按 DR4 族出分布；标注每个比例的分子 / 分母。
8. **自检**：随机抽 20% 案例，48 小时后不看初稿重判一次；记录不一致数（这是最低成本的信度检查）。

### 6.6 判定标准（验收）

1. **覆盖**：≥ 20 个案例（若合格案例少于 20，则覆盖全部并写明原因）。
2. **锚点**：100% 行有至少一个证据锚；`证据` 列为空的行数 = 0。
3. **未知率**：`事发时门状态 = 未知` 的案例 ≤ 20%；超过则说明案例选择或数据不足，需在报告中单列。
4. **分母**：每个百分比都写清分子 / 分母；禁止「约一半」这类无分母表述。
5. **三态**：`有门·会咬` / `有门·不够` / `无门` 三态都有案例，或明确写「本样本未出现某态」。
6. **保险案例**：至少识别 1 个「零命中但高风险、应保留」的门；若没有，写明「本样本未覆盖该形态」。
7. **数据缺口**：T4 至少列 5 项不可得指标，并给出下一期是否插桩的建议。
8. **可复现**：附录给出只读命令清单；另一个人按清单能重建案例全集。
9. **零业务上下文**：按 `shared/global-rules.md:121` 自检，不出现产品名 / 业务数据。
10. **不改代码**：首跑前后 `git status` 的已跟踪文件 diff = 0（只新增本文档 / 报告）。

### 6.7 预期产出与假设（待验证，不是结论）

首跑最可能得到的四个信号：

1. **事后补钉率偏高**：大量 D 行同时包含「病灶」与「钉 / 变异」，说明门更像「事后学习」而不是「事前预防」。这是 B2 的直接来源。
2. **A3「判据不足」是最大漏因**：`shared/gates.md:98` 的「可执行性判据本体」族（判据被形态 / 措辞 / 配置满足）已经在 bugs.md 的多个段出现；首跑应能把它量化。
3. **A1「无门」集中在流程 / 语义层**：`gates.md` §2.5 的 9 行大多不设机器判据；这些无法物理消融，只能用归因台账。
4. **成本面几乎全空**：逐门耗时、token、阻塞率都没有仓内数据；首跑的最大价值可能是**证明「现在还不能算净收益」**，并把插桩需求排出来。

**如果四个信号都出现**，下一期不应直接做物理消融，而应先做两件事：给 `atlas_check` 加逐门计时与运行事件行；对 A3 族做判据级消融（隔离副本），验证「补判据是否真的承重」。
